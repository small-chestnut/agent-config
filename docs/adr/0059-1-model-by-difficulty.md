# 0059-1 チームの各役割のモデルと effort を、SE が決めた仕事の難しさで割り当てる

状態: 提案
日付: 2026-11-10
対象: task-team-lead・task-team-se

## 決めたこと

チームの各役割のモデルと effort は、役割ごとに固定せず、SE が役割の仕事ごとに決めた難しさ(低・中・高)に、Sonnet 5.5 の medium・Opus 5.5 の medium・Opus 5.5 の high を割り当てる。

## 捨てた案

1. 役割ごとに固定する(SE と QA が Opus 5.5 の high、PG が Sonnet 5.5 の medium): 同じ役割でも、タスクによって仕事の難しさが違う。易しい仕事では性能が余って使用量を損ない、難しい仕事では足りない。
2. ADR を出す変更・本番に触る変更だけ、モデルを上げる: ADR を出すかが分かるのは、SE が壁打ちと設計の判断を済ませた後で、SE の仕事には間に合わない。ADR の有無は、難しさをざっくり切り分けた目安にしかならない。
3. 誤りを利用者より前に確かめる役がいない仕事(壁打ちをする SE・設計レビューをする QA)に、強いモデルを使う: 利用者が頼んだかとレビューの種類で決めることになり、案2 と同じく、難しさそのものを見ていない。
4. 高に Fable 5.2 の high を割り当てる: 理由2 の測定で、Fable 5.2 が費用に見合ったのは、長いコードの作業と大きな資料の作業だけ。このチームの仕事は、1つの会話に収まる短い仕事で、壁打ちと設計は調べものに近い。
5. 低に Haiku 5.5 を割り当てる: 同じページで、Haiku 5.5 が合うのは、結果を確かめられる大量の作業で、長いエージェントの作業ではない。PG と QA の仕事は、skill の手順に沿って道具を何度も呼ぶ作業。
6. 難しさを PL が決める: PL は、話題がどのタスクに当たるかまでを持ち、タスクの中身を読まない(ADR 0056-1)。難しさは、中身を読まなければ決められない。
7. PG と QA のモデルも、PL がチケットを読んで替える: SE が PG か QA に仕事を頼むのと、PL が替えるのが前後し、替わる前に仕事が始まることがある。替えた値が効くのは、次のターンから(`set_session_model` の道具の説明)。

## 理由

1. 性能が仕事の難しさに足りないと仕事が仕上がらず、余ると使用量を損なう。難しさは、タスクごとでなく、役割の仕事ごとに違う(決めるのは難しいが作るのは易しいタスクも、その逆もある)。
2. Anthropic が測った数字(コードの課題 SWE-bench Pro を1件解く費用と、解けた割合)では、Sonnet 5.5 の medium が約 $0.07 で約 81%、Opus 5.5 の medium が $0.21 で 92.8%、Opus 5.5 の high が $0.29 で 95.3%、Fable 5.2 の high が $1.39 で 96.3%。調べものの課題(DeepResearch Bench II)では、Fable 5.2 の high は、Opus 5.5 の medium より 1.9 ポイント下で、費用は 2.9 倍(https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence.md 。2026-11-10 に読んだ。数字は Anthropic の社内の測定で、目安)。
3. 同じページの勧めは、たいていのエージェントの作業は Opus 5.5 の medium から始め、high より上は、失敗が高くつき、伸びが測れた所だけにすること。3段の割り当ては、この勧めの始める値に沿う。
4. 難しさを決められるのは、タスクの文とリポジトリを読む SE だけ。PG と QA の仕事の難しさは、設計を書き終えた SE が、いちばんよく知っている。
5. 利用者のプラン(Max)の使用量の枠は、Fable だけ別の週の枠がある。割り当てに Fable を入れなければ、その枠は、利用者が手で上げた仕事にだけ使われる(2026-11-10 に `get_usage` で引いた)。
6. モデルを会話の途中で替えると、キャッシュが効かない(skill `claude-api` の `shared/cost-optimization.md` の 2.7)。PG と QA は仕事を始める前に替え、SE は同じモデルのまま effort だけを替えるので、途中でモデルが替わる会話が無い。
