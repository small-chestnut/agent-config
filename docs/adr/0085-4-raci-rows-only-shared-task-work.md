# 0085-4 RACI チャートの行は、2つ以上の役割が関わる、タスクの中の作業だけにする

状態: 採用
日付: 2026-11-14
対象: 全体

## 決めたこと

skill `task-team` の RACI チャートの行は、2つ以上の役割が関わる、タスクの中の作業(話題をタスクに分ける・要件定義・設計・実装)だけにし、作業が承認されたときに誰に知らせるかは、表の I で決める。PL だけがする作業(チームの開始と終了、main へのマージとインストール)は、行にせず、同じ skill の規則の1行で言う。

## 捨てた案

1. 元の ◯/✕ の表の行を、みな引き継ぐ(0085-1 の実装の18行): チームの管理(チームを作る・閉じる、かんばん、マージ)は PL が1人でして利用者は結果を見るだけで、役割どうしの関係が無い。利用者の許可が要るかどうかと、知らせ方は、作業の中身でない。
2. モデルと effort を替える行を置く: いつ・何を基準に替えるかの規則が skill に残り、誰が替えるかもその規則が言っているので、同じことを2か所に書くことになる。
3. 進み具合を SE が答える行を置く: 進み具合を見せるのはタスクの外のチームの管理で、PL の役割。利用者は、SE にはそのタスクの作業に集中させると決めた(ADR 0085-6)。
4. 作業が終わったときに誰に知らせるかを、今のまま役割の skill の行に書く: 表の I と同じことを2か所に書くことになる。
5. PL だけがする作業を、どこにも書かない: 全体の CLAUDE.md は、`small-chestnut` のリポジトリでは、どのセッションにも、終えた作業ブランチをマージさせる。PL の skill は PL しか読まないので、PG が、QA が通す前にマージしうる(設計レビューの指摘)。

## 理由

1. 利用者は、大事なのは各役割がタスクの中で何をするかで、利用者の許可が要るかどうかは残す観点でないと言い、1つの役割だけがして利用者は結果を見るだけの作業が表に残る理由を問うた。
2. RACI チャートは、役割どうしの関係を表す表。関わる役割が1つだけの作業は、表すものが無い。
3. 利用者は、表と重なる記述を役割の skill から消すと決めた。行を絞ると、役割の skill に残るのは、作業のやり方・基準・いつするかと、セッションの立て方と知らせ方になる。
