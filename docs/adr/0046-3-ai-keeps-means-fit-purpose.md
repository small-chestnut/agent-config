# 0046-3 規則・仕様・コードは目的を実現する今の手段とし、AI が目的に合わせて保ち、直したらずれと直し方を伝える

状態: 提案
日付: 2026-11-09
対象: 全体
置き換える: 0046-1

## 決めたこと

AI で開発するどのリポジトリでも、規則・仕様・コードは、作業するリポジトリの目的と、その中で利用者が合意した原則・目的・目指す状態を実現する今の手段として扱い、ぶつかったら目的と目指す状態に従い、規則を足す・直す前に反していないかを確かめ、作業するリポジトリの中の反する手段に気づいたら AI が自分で直すか消し、直したら目的に対してどうずれていてどう直したかを利用者に伝える(agent-config では PL が聞かずにタスクにして回す。詳しい文は全体の CLAUDE.md の原則3)。

## 捨てた案

1. 手段を規則だけにし、仕様は合わない所を利用者に伝える(ADR 0046-1 の形): 人が読む速さは AI が作る速さに追いつかず、仕様とコードのずれを判断する役が利用者に残る。
2. 機能を足す・変える・消す直しは、先に利用者に聞く: 利用者は、規則の調整に関わりたくなく、基本は AI に任せると答えた。知りたいのは、目的に対してどうずれていて、なぜそう直したか。
3. 全体の CLAUDE.md の原則・目的・目指す状態にも照らす: 全体の CLAUDE.md 冒頭の「リポジトリの決まりとぶつかったら、リポジトリの方に従う」(ADR 0004-1)と向きが割れ、ほかのリポジトリのフォルダの並びを、全体の目指す状態に反すると読んだ AI が自分で直してしまう。agent-config では全体の CLAUDE.md もリポジトリの中にあるので、照らす先に入る。

## 理由

1. 利用者の理由: AI が書いた規則・仕様・コードは、人が把握できる量を超えている。利用者が見られるのは目的と目指す状態だけなので、AI が手段を利用者の指示として守るだけでは、手段と目的のずれを誰も見つけられない。利用者が手段に目的を添えたのは、規則に無い場面でも AI が意図に沿って動けるようにするため(コマンダーズインテントの考え)。理想は、目的に反する規則をそもそも作らないこと。「違う」と言われたときだけ手を入れる今の形では、全部を見ていない利用者は見ていない規則に「違う」と言えず、タスク 0010 で入れた「仕様はモジュールごとに1つ」は、親の「1つの作業で読むものが、その作業に要るものに絞られている」に反したまま、利用者が気づくタスク 0045 まで残った。
2. 差は開き続ける: AI をよく使うチームではマージした PR が 98% 増え、PR のレビュー時間は 91% 延びた(Faros AI, 2025, https://www.faros.ai/blog/ai-productivity-paradox-report-2025)。AI が1人で仕上げられる作業の長さは約7か月ごとに2倍になっている(METR, 2025, https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)。
3. 照らす時を規則の「足す・直す前」に絞るのは、矛盾が入るのはその時で、既にある手段のずれには、ぶつかった時と、利用者に理由を聞かれた答え(ADR 0046-2)で気づくから。規則を読むたびに全部を照らすと、読む量を絞る目指す状態に反する。
4. AI が自分で直すのは規則・仕様・コードまでで、上の3段は今までどおり提案まで(skill `prompt-structure`)。ほかのリポジトリで気づいた全体の CLAUDE.md・skill の規則は、`~/.claude` の写しを直しても install で上書きされるので、自分で直す対象にしない。agent-config で PL に回すのは、規則がこのリポジトリの作るものそのもので、設計とレビューを通すため。
5. ADR 0040-2 の理由1にある「機能を消すかは、今どおり利用者が決める」は、目的に合わせる直しでは AI が決める前提に替わる。0040-2 の決定(消す前に伝えるのは git から戻せないものだけ)は変わらない。
