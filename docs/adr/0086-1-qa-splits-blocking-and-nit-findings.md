# 0086-1 QA の指摘は、直さないと通せないものと Nit に分け、直しを頼むのは直さないと通せないものだけにする

状態: 採用
日付: 2026-11-14
対象: task-team-qa・task-team-se・task-team-pg・task-team

## 決めたこと

QA は、要件・受け入れ条件・設計・規則に合わない所を直さないと通せない指摘とし、ほかの指摘は頭に「Nit: 」を付けて書き、直しを頼むのは直さないと通せない指摘だけにする。Nit を直すかは作業をした役割が決め、直しの確かめで QA が見るのは直しを頼んだ指摘だけ(詳しい文は skill `task-team-qa`・`task-team`)。

## 捨てた案

1. 今のまま、重さを付けずに、出た指摘の全部の直しを頼む(ADR 0067-3 の捨てた案2 の形): 細かい指摘も直しと直しの確かめを生み、直しの確かめで残れば利用者に聞くことになる(ADR 0085-7)。変更が目的を果たしていても、完璧でないことで止まる。
2. Nit を書かず、直さないと通せない指摘だけを書く: code-review が出す細かい改善を、作業をした役割が知る手が無くなる。Google の手引きも、直さなくてよい指摘を、印を付けて書く。
3. 重さを3段(止める・止めない・Nit)にする(d977475 の形): 止めないと Nit は、どちらも直しを頼まない。通すかを分ける境目は1つで足りる。
4. Nit を直すかを QA が決める: 直すかを決めるのは、作業をして終わらせる役割(RACI チャートの R)。Google の手引きでも、Nit は書いた人が無視してよい。

## 理由

1. 利用者の「なぜ」: 無限のレビューにしない。完璧かどうかでなく、変更が目的を果たすかで通す。
2. Google の手引き(https://google.github.io/eng-practices/review/reviewer/standard.html 。2026-11-14 に読んだ): 全体を確かに良くする変更は、完璧でなくても通す。直さなくてよい指摘には「Nit: 」を付け、書いた人はそれを無視してよい。
3. ADR 0067-3 の捨てた案2 が重さを捨てた理由(完璧を目指した往復が起きた)は、利用者が 2026-11-14 に撤回した。当時の往復は、直しを何度でも見直す形から起きた。今は直しの確かめが1回だけ(ADR 0085-7)なので、往復の回数は重さに依らず限られる。重さが無いと、細かい指摘も直しの確かめに入り、残れば利用者に戻る。
4. 境目を要件・受け入れ条件・設計・規則にするのは、QA が照らす相手がこれらだから(ADR 0067-3・0069-2・0085-5)。QA が自分で境目を作る余地が残らない。
