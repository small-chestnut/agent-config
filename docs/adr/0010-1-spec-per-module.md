# 0010-1 モジュールごとの仕様を1つ残し、動きを変える変更のたびに直す

状態: 提案
日付: 2026-10-31
対象: 全体

## 決めたこと

モジュールごとの仕様を `docs/specs/<モジュール>.md` に1つ置き、そのモジュールの外から見える動きを変える変更の中で直す(task-team では SE が設計のコミットで直す)。

## 捨てた案

1. 今のまま、仕様はタスクの記録にだけ書き、タスクが終わったら直さない(spec-first まで)。
2. OpenSpec のように、記録に仕様の差分(ADDED / MODIFIED / REMOVED)を書き、マージのときに仕様へ合わせ込む。
3. 仕様を、モジュールのフォルダ(`modules/<モジュール>/`)に置く。
4. 仕様を、モジュールの CLAUDE.md に書く。

## 理由

1. 利用者は「spec駆動開発の考えは、このリポジトリに取り入れられている？」と聞き、agent-config の目的(新しいシステムを開発するとき、そのリポジトリの CLAUDE.md を作りこまなくても、agent-config の設定を読めば、すぐに AI 駆動開発に最適な環境ができること。利用者の言葉を整えた文)の話のあとで「だから、spec駆動開発が要るんじゃない？って思った」と言った。
2. 案1では、機能の今の動きを知るのに、その機能に触れた記録を全部読むことになり、読む量がタスクの数に比例して増える。仕様をタスクのあとも残して直すのが spec-anchored(https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)。
3. 案2: 作業ブランチの差分が、そのまま仕様の差分になる。合わせ込む手順を足すと、忘れたときに仕様が古いまま残る。
4. 案3: 定石はどれも、仕様をコードの外の1つのフォルダに置く(Kiro は `.kiro/specs/<機能>/`、Spec Kit は `specs/<番号>-<機能>/`、OpenSpec は `openspec/specs/<領域>/spec.md`)。まだモジュールのフォルダになっていない既にあるリポジトリでも、同じ置き場が使える。
5. 案4: CLAUDE.md は決まりの文書で、そのフォルダで作業するたびに読み込まれる。動きの説明を足すと、決まりの文書が長くなる。
6. 仕様に書くのは外から見える動きだけにし、クラス名・ライブラリ・手順は書かない。OpenSpec の定石に沿う(https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)。
