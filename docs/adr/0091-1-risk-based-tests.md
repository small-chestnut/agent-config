# 0091-1 置くテストを、間違いに気づかず使い続けるか元に戻せない業務の規則のものに限る

状態: 提案
日付: 2026-11-24
対象: task-team-test-list
置き換える: 0005-1 の1

## 決めたこと

小と中のテストを、業務の規則の計算か判断のうち、間違っていても利用者が気づかずに使い続けるか、間違うと元に戻せないものに限り、置くテストは、同じ処理を通る値の1組に1つとし、組の境目の値で確かめる(詳しい文は skill `task-team-test-list`)。

## 捨てた案

1. 今のまま、受け入れ条件・分かれ目・境目の数からテストの数を決める: 下限だけがあり、規則どおりのテストは何件でも通る。壊れたときの害を問わない。
2. 件数・割合・カバレッジの目標か上限を置く: どの規則を確かめたかを問わない(ADR 0005-1 の理由2)。
3. 「表の値はテストしない」など、作らないものを1つずつ並べる: gemini で増えたテストの大半は、値の書き写しでなく、新しい機能の断る場合ごとのテスト。並べても、書き漏らしたものは止まらない(ADR 0027-1)。
4. テスト1件ごとに、壊れたときの害を書かせる: どのテストにも何かの害は書ける。
5. 「見ても気づけない」で決める: 画面に出ているものはみな「見れば気づける」と読まれ、LogiFee の税区分が戻るテスト(壊れると消費税を請求し漏らす)が落ちた。
6. 作るものを「業務の規則」だけで決める: 断る場合も業務の規則と読めるので、断る場合ごとのテストが残る。

## 理由

1. 利用者の理由: テストが作業のたびに増え続けると困る。過剰なテストはパフォーマンスを落とす。基準は、あるべき形から決める。
2. 今の基準が入った 2026-10-31 から 2026-11-24 までに、gemini(`退避/` を除く Python)は、テスト以外の行が 27,916 から 27,817 で変わらず、テストの行が 982 から 11,406 になった。
3. 定石: テストは一番大事な所(業務の規則)に集め、価値が維持の手間を大きく上回るものだけを残す(Khorikov『Unit Testing Principles, Practices, and Patterns』1章、https://enterprisecraftsmanship.com/files/Unit-Testing-Chapter-1-Excerpt.pdf)。範囲と量は、リスク(起きる見込み × 起きたときの害)で決める(ISTQB CTFL v4.0.1 5.2、https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)。どちらも 2026-11-24 に読んだ。
4. 手間は、維持の手間(コードを変えるたびに直す・毎回実行する・誤った失敗に対応する・読む)だけでなく、書く・レビューする時間も含む。作った後にすぐ消すテストも、書いてレビューした分は手間になる。
5. 計算か判断は見込みに、気づかずに使い続けるか元に戻せないは害に当たる。定石の「価値が手間を上回る」を、AI が見分けられる条件にしたもので、条件そのものは定石に書かれていない。
6. 同じ処理を通る値は、1つの組で代表させられる(同値分割。ISTQB CTFL v4.0.1 4.2.1)。代表の値を境目の値にすれば、1組に1つのまま、隣の組の値とあわせて境目の両側を確かめられる(境界値分析)。境目の前後を確かめる 0005-1 の1の決定は、この形で引き継ぐ。
