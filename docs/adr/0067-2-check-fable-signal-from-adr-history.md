# 0067-2 Fable にする途中の印は、SE がコミットのたびに、QA が設計レビューの前に、ADR の git の履歴で確かめる

状態: 提案
日付: 2026-11-12
対象: task-team-se・task-team-qa・task-team-lead

## 決めたこと

ADR 0065-1 の途中の印(同じタスクで入れた決定を消す・同じ決まりを3回変える)は、このタスクの ADR の `git log -p` で、SE がコミットのたびに、QA が設計レビューの前に確かめ、当たれば PL に知らせて、PL が SE を Fable 5.2 の high に替える(詳しい文は skill `task-team-se`・`task-team-qa`・`task-team-lead`)。

## 捨てた案

1. 今のまま、SE が気づいたときに PL に知らせる: R-0718 では、SE は ADR-2871-4 を取り下げて印に当たっていたのに、利用者に「モデルの思考量あげたほうがいいの？」と聞かれるまで PL に知らせなかった。気づくかに頼ると、浅い判断のときほど知らせが出ない。
2. 確かめるのをフックにする: フックを変えるのは、安全の原則で利用者に頼まれたときだけ。今回は頼まれていない。
3. PL が確かめる: PL はタスクの中身を読まない(ADR 0056-1)。どの ADR がこのタスクのもので、どれが同じ決まりかは、中身を読まないと分からない。
4. 利用者が SE の誤りを止めた回数を印に足す: どの発言が誤りを止めたものかを分ける判断が、また SE 本人に任される。止められて決定を取り下げれば、今の印に当たる。
5. チケットの固まった要件や設計の行を消したことも印にする: 壁打ちと設計の間は、要件と設計の行を書き直していくのがふつうで、印が出すぎる。ADR 0065-1 の理由4 の印(ADR-2842-2 → 2842-5・立替金の分け方を4回変えた)も、ADR に出ていた。

## 理由

1. 確かめる時を決まった操作(SE のコミット・QA の設計レビュー)に結びつけると、本人が気づくかによらず確かめが走る。
2. ADR の状態の変化と、決めたことの書き換えは、git の履歴に事実として残る。気づきでなく、履歴を読んだ事実で決まる。
3. QA は SE と別のセッションで、SE の判断の浅さを引き継がない。R-0718 では、ADR-2871-4 を取り下げたあとも、QA は ADR-2871-6 と 2871-9 の設計レビューをしていた(LogiFee の SE の記録)。その前に履歴を見ていれば、利用者に聞かれる前に印が PL に届いた。
4. 印が出るのは ADR を出すタスクだけで、ADR を出すタスクは大きな変更として設計レビューを通る(skill `task-team-qa`)。設計レビューの無いタスクに、確かめ漏れは出ない。
