# 0045-2 仕様を、機能ごとのファイル `docs/specs/<モジュール>/<機能>.md` に置き、動きを変える変更のたびに直す

状態: 採用
日付: 2026-11-09
対象: 全体
置き換える: 0010-1

## 決めたこと

仕様を、モジュールの1ファイルではなく、機能ごとのファイル `docs/specs/<モジュール>/<機能>.md` に置き、その機能の外から見える動きを変える変更の中で直す(task-team では SE が設計のコミットで直す)。「ADR」の節は機能ごとの仕様が持ち、2つ以上の機能に効く ADR の番号は、効く機能の仕様のどれにも並べる。

## 捨てた案

1. 今のまま、モジュールごとに1ファイルで、機能はその中の見出しにする(ADR 0010-1)。
2. 機能が増えたモジュールだけ、機能ごとのファイルに分ける。
3. タスクごとに仕様のファイルを分ける。

## 理由

1. 案1では、機能の多いモジュールほど、1つのタスクでそのタスクが触らない機能の仕様まで読む。機能ごとのファイルなら、読む仕様はタスクが触る機能の分だけになり、フォルダの一覧で機能の名前が見える。要る情報を要る時にだけ読ませるのは、コンテキストエンジニアリングのやり方(https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。
2. 案2では、分ける境目の大きさが決まらず、境目を越えたときにファイルを移す作業が要る。
3. 案3: タスクの形は毎回変わり(計算と画面にまたがるタスクもある)、タスクごとの文書はチケットで、終われば消す。仕様までタスクごとにすると、今の動きを知るのに全部のファイルを読むことになる(ADR 0010-1 の捨てた案1と同じ)。
4. 1つのファイルに機能を1つだけ置くのは、Gherkin の定石に沿う(「1つの `.feature` ファイルに置ける Feature は1つだけ」https://cucumber.io/docs/gherkin/reference/)。
5. 仕様をコードの外の1つのフォルダに置き、変更のたびに直す点は ADR 0010-1 のまま。
6. 2つ以上の機能に効く番号を、どれか1つの仕様にだけ並べると、ほかの機能を変えるタスクの SE がその番号にたどり着けない(ADR 0010-2 の理由1と同じ)。
