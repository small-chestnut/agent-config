# 0067-3 QA の設計レビューは、code-review より先に、ゴールに合うか・既にあるものと重ならないか・もっと単純な手が無いかを、同じ1回で見る

状態: 採用
日付: 2026-11-12
対象: task-team-qa

## 決めたこと

QA の設計レビューでは、code-review より先に、設計がゴールを果たしてゴールの外のことをしていないか、新しく作るものと同じ機能か反する決まりが既に無いか(チケットに出る語で仕様・コード・ADR・CLAUDE.md を grep する)、根本原因を取り除き同じゴールをもっと単純に果たす手が無いかを見て、どれも同じ1回のレビューの指摘にする(詳しい文は skill `task-team-qa`)。

## 捨てた案

1. code-review の段を low から上げる: code-review が探すのは、渡した文の中の正しさの誤りで、段を上げても同じ種類の指摘が増えるだけ。R-0718 で通ったのは、設計がゴールに合うかと、リポジトリに既にあるものとの重なりで、設計の文の外に照らさないと見えない。
2. c8fa8b4 の前の、自作のレビューの項目と重さ(止める・止めない・Nit)に戻す: 完璧を目指した往復が起き、利用者はそれを止めるために消した。見る所は、R-0718 で通った本質的におかしな設計の型の3つに絞り、重さは付けない。
3. SE が指摘を直したあと、設計レビューをもう一度する: SE と QA の往復が増える。利用者は、何往復もするレビューは本末転倒と言った。指摘を直した設計は、今のとおり見直さずに PG に渡す。
4. 設計レビューを Fable 5.2 にする: 欠陥を探す課題で、Fable 5.2 の high は Opus 5.5 の high より 5.9 ポイント上だが、費用は 2.4 倍(https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence.md 。2026-11-12 に読んだ)。見る所が code-review の正しさだけのままなら、モデルを上げても、ゴールと既にあるものに照らす所は増えない。ADR 0065-1 の捨てた案5 のとおり、Opus の QA は設計の食い違いを拾えている。
5. SE が設計する前に既にある機能と決まりを探す手順だけを足し、QA は今のままにする: R-0718 では SE と QA の両方が通した。SE 1つに頼ると、SE が見落としたとき止める役がいない。利用者は、利用者に依らずに止めることを第一に求めた。SE の手順は、PL に別に知らせた。
6. 設計が言い切った件数などの事実を、QA が数え直す: 数えるデータは、本番の DB やリポジトリの外のファイルにあることが多い。QA が読むのはチケットとリポジトリだけで、本番環境に触る作業は PL に知らせて止める決まり(skill `task-team-messaging`)。

## 理由

1. 利用者が求めるのは、必要十分なレビューで、SE が作った本質的におかしな設計を、利用者に依らずに止めることが第一。SE と QA が何往復もするのは本末転倒(利用者の答え)。
2. R-0718 では、QA の設計レビュー(code-review)は、ADR の文の食い違いやテストの抜けはよく拾ったが、データ投入の段階に訂正の仕訳を持ち込む設計(ADR-2871-6)と、既にある入出金の組(`create_pair`)を作り直す設計(ADR-2871-9 の前の版)を通した。どちらも利用者が止めるか、Fable に替えた SE が見つけた(LogiFee の SE の記録)。
3. 3つの見る所は、R-0718 で利用者が止めた本質的な誤りの型に当たる。ゴールの外のこと(2 の訂正の仕訳)、既にある機能と決まり(4 の `create_pair`、3 の ADR-2842-3)、もっと単純な手(5 の元のデータを直す)。
4. 既にある機能は、利用者の語から探せる。R-0718 で利用者は「組にしていく」と言い、Fable の SE は仕様とコードを grep して `create_pair` を見つけた。
5. 見る所を足しても、レビューは設計と実装に1回ずつのまま。指摘は SE が直して PG に渡し、もう一度は見ない(skill `task-team-se`・`task-team-qa`)。
