# 0084-1 説明に、起こるかもしれない別の場合を足させる規則を置かない

状態: 採用
日付: 2026-11-14
対象: 全体

## 決めたこと

全体の CLAUDE.md と skill に、説明に起こるかもしれない別の場合(失敗する条件・例外・リスク)を足させる規則を置かず、今ある4か所を消す(全体の CLAUDE.md の「手順の説明には、そのとおりにやっても失敗する条件まで入っている」・「例外は、知らないと操作を誤るときだけ、答えの後に例外として添えている」・「伝えるリスクは、…」と、skill `task-team-se` の「失敗する条件」)。

## 捨てた案

1. 「失敗する条件」の見出しの下に、対象を確かめた条件だけに絞る行を足す: 絞っても、足させる向きは残る。足すものが無いときも探させ、ほとんど起こらない小さな可能性からひねり出させる。
2. 「例外は、知らないと操作を誤るときだけ」を残し、歯止めにする: 「知らないと操作を誤る」はどの例外にも言えるので、何も絞らない。LogiFee の例では、この行があっても例外を添えた。
3. 「伝えるリスクは、…」を残し、後から直せない壊れ方を伝える受け持ちにする: 押す規則が消えれば、歯止めの役目がほぼ無くなる。後から直せない操作は、安全の原則(消す前に対象と理由を伝える)と、skill `task-team-se` の「元に戻せない操作には、そう書いている」が受け持つ。

## 理由

1. 利用者の理由: 異常系は、1つの正常系に対して数え切れないほどあり、説明に持ち出すと、どれも同じ重さに見えて話が進まない。説明で大事なのは分かりやすさで、いつも但し書きで失敗する場合を書くのは、いつも屁理屈を混ぜるのと変わらない。
2. 文章の量は既に制約されている(結論から・補足は 400 字まで・収まらなければ数ターンに分ける)。足させる規則は、量の制約と押し合い、足すものが無いときにひねり出させる。LogiFee の会話で、Claude は「4〜9月の消込を進められる」の答えの後に、確かめていない、後から直せる場合を添え、利用者は答えにたどり着くまで4回聞き直した。添えた例外は、補足の 400 字に収まっていた。
3. 「失敗する条件」の見出しは、2026-10-21 の書き直し(5a23833)で、対象を「利用者がこの後に操作する所で、そのとおりにやっても壊れるもの」に絞る文と例を落とし、下に規則の行の無い見出しだけになっていた。
