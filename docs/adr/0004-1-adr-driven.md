# 0004-1 設計の決定を ADR に提案し、利用者が採用してから実装する

状態: 採用
日付: 2026-10-31
対象: 全体

## 決めたこと

1. 設計の決定のうち Nygard の5つ(構造・非機能の特性・依存・インターフェース・作り方の技法)に効くものは、SE が ADR に「提案」で書き、利用者が「採用」にしてから PG が実装する。task-team を通さない会話では ADR を書かず、タスクにして PL に回す。
2. ADR は対象のリポジトリの `docs/adr/` にまとめて置き、番号は `<タスクの番号>-<そのタスクの中の連番>`。タスクの番号は PL が振る4桁の連番。リポジトリに ADR の決まりか既にある ADR があれば、番号・置き場・形はそちらに従う。
3. agent-config の規則(グローバルの CLAUDE.md・skill・AGENTS.md)が、作業するリポジトリの決まり(コミットされた文書に書かれた決まりと、既にあるファイルの並び)とぶつかったら、必ずリポジトリの方に従い、そのことを利用者に1行で伝える。

## 捨てた案

1. ADR の番号を、リポジトリの中の通し番号にする(Nygard の定石)。
2. ADR を、モジュールごとのフォルダに置く。
3. task-team を通さない会話でも、`0000-<連番>` の番号で ADR を書く。

## 理由

1. 番号: タスクから、対応する ADR をすぐ引けるようにするため。定石(通し番号)からは外れる。
2. 置き場: 人が一覧で見渡せ、AI にとっての差は小さいため。
3. リポジトリの決まりを優先: agent-config は利用者が AI 駆動開発のために使う私的な規則で、これによって複数の人間が触るリポジトリの規則を逸脱するわけにはいかないため。
4. 書く対象と状態は、Nygard の定石に沿う(https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)。
