# 0085-2 話題をいくつのタスクに分けるかは SE が設計の最初に決め、分けた残りは PL が未着手のチケットにして順にチームを作る

状態: 置き換え済み(0085-8)
日付: 2026-11-14
対象: task-team-se・task-team-lead
置き換える: 0065-1 の決めたことのうち「1つの会話に収まらないと見込める仕事」

## 決めたこと

SE は、設計の最初に仕様とコードを読み、1つのタスクが SE・PG・QA のどれも1つの会話で終えられる大きさに収まらなければ、利用者が確かめる単位で話題を2つ以上のタスクに分け、SE が分けたタスクごとに書いた要件と「なぜ」を、PL がそのチケットのゴールの節に写して未着手のチケットにし、1つ前のタスクを終えてから順にチームを作り、壁打ちをせずに設計を始めるよう SE に添える。Fable にするのは、分けても1つの会話に収まらないと見込める仕事だけにする(詳しい文は skill `task-team-se`・`task-team-lead`)。

## 捨てた案

1. PL が、話題を受け付けたときに分ける: PL は話題の1文しか持たず、壁打ちをせずにタスクにする(ADR 0056-1・0056-2)。大きさを見積もる材料の仕様とコードを読まない。
2. 大きすぎる仕事は、今のまま Fable にするだけにする: 1つのタスクで出来上がるものが大きいままで、利用者が一度に確かめる量が減らない(README の「なぜ」)。
3. 分けたタスクのチームを、すぐに全部作る: 前のタスクが変えるファイルに次のタスクが重なり、次のタスクの SE が前のタスクの決定を読まずに設計する。
4. SE が、分けたタスクのチケットを自分で作る: タスクの番号は PL が振り(ADR 0004-1)、まだ始めていないタスクのチケットは PL が作る(ADR 0047-3)。

## 理由

1. LogiFee では、タスクが適切な大きさに分けられず、1つのタスクで終わらないことがしばしばあった(利用者の答え)。根本原因は、タスクの大きさを決める役割と基準が、規則に無かったこと。
2. SE は、設計で仕様とコードを読むので、タスクの大きさを見積もれる。
3. 作業の単位(ユーザーストーリー)は、計画できないほど大きくせず、大きすぎるものは分けるのが定石(INVEST の Small。https://en.wikipedia.org/wiki/INVEST_(mnemonic) 。2026-11-14 に読んだ)。
4. 利用者は、分ける判断を SE、分けたタスクのチームを作るのを PL と決めた。
5. 分けるのは、利用者が設計に進めると言った後の設計の最初なので、分けたタスクは、利用者が進めると言った話題の一部。壁打ちをもう一度する理由が無い。
