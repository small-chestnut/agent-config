# 0085-8 話題をいくつのタスクに分けるかは SE が設計の最初に決めて要件の節に書き、QA が設計レビューで見て、PL がタスクを終えるときに未着手のチケットにする

状態: 採用
日付: 2026-11-14
対象: task-team-se・task-team-qa・task-team-lead
置き換える: 0085-2

## 決めたこと

SE は、設計の最初に仕様とコードを読み、1つのタスクが SE・PG・QA のどれも1つの会話で終えられる大きさに収まらなければ、利用者が確かめる単位で話題を2つ以上のタスクに分けて、分けたタスクの要件を番号と「なぜ」を付けて「要件」の節に書き、QA が設計レビューで分け方を見て、PL が、タスクを終えるときにその要件を写した未着手のチケットを作り、1つ前のタスクを終えてから順に、壁打ちをせずに設計を始めるチームを作る。Fable にするのは、分けても1つの会話に収まらないと見込める仕事だけにする(詳しい文は skill `task-team-se`・`task-team-qa`・`task-team-lead`)。

## 捨てた案

1. PL が、話題を受け付けたときに分ける: PL は話題の1文しか持たず、壁打ちをせずにタスクにする(ADR 0056-1・0056-2)。大きさを見積もる材料の仕様とコードを読まない。
2. 大きすぎる仕事は、今のまま Fable にするだけにする: 1つのタスクで出来上がるものが大きいままで、利用者が一度に確かめる量が減らない(README の「なぜ」)。
3. 分けたタスクのチームを、すぐに全部作る: 前のタスクが変えるファイルに次のタスクが重なり、次のタスクの SE が前のタスクの決定を読まずに設計する。
4. SE が、分けたタスクのチケットを自分で作る: タスクの番号は PL が振り(ADR 0004-1)、まだ始めていないタスクのチケットは PL が作る(ADR 0047-3)。
5. 分けたタスクの要件を、ゴールの節に書いて PL がゴールの節に写す(0085-2 の形): 利用者と合意した内容を「要件」の節にだけ書く決まり(ADR 0085-5)と食い違い、分けたタスクの要件が、番号も「なぜ」も無いまま渡る(設計レビューの指摘)。
6. SE が分けたらすぐ PL に知らせ、PL がそのときチケットを作る(0085-2 の実装の形): QA が設計レビューで分け方を見る前に、既定のブランチにチケットができる。タスクを終えるときなら、分け方は承認済みで、作るのは1回で済む。
7. 分け方を承認する役割を PL にする: PL はタスクの中身を読まないので、読まずに通すだけになる(ADR 0007-1 の捨てた案1 と同じ)。

## 理由

1. LogiFee では、タスクが適切な大きさに分けられず、1つのタスクで終わらないことがしばしばあった(利用者の答え)。根本原因は、タスクの大きさを決める役割と基準が、規則に無かったこと。
2. SE は、設計で仕様とコードを読むので、タスクの大きさを見積もれる。
3. 作業の単位(ユーザーストーリー)は、計画できないほど大きくせず、大きすぎるものは分けるのが定石(INVEST の Small。https://en.wikipedia.org/wiki/INVEST_(mnemonic) 。2026-11-14 に読んだ)。
4. 利用者は、分ける判断を SE、分けたタスクのチームを作るのを PL と決めた。
5. 分けるのは、利用者が設計に進めると言った後の設計の最初なので、分けたタスクは、利用者が進めると言った話題の一部。壁打ちをもう一度する理由が無い。
6. RACI チャートで、分ける作業の A は QA(ADR 0085-3)。QA は、話題を分けた変更の設計レビューで、分け方を見る。
