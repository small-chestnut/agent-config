# 0069-2 QA の実装レビューは、code-review より先に、作ったものを、利用者が合意した時点の設計の節と受け入れ条件に照らす

状態: 採用
日付: 2026-11-12
対象: task-team-qa・task-team-se

## 決めたこと

QA の実装レビューでは、code-review より先に、作ったものを設計の節と受け入れ条件に照らす。照らす設計の節は、実装のサブタスクの依存先がみな `[x]` になったコミットのものに、「設計への問い」に SE が答えて直した所を足したもの。ほかに変わった設計の節の行と、設計と違う作りを指摘にし、設計の節が二通りに読める所は、設計の指摘として SE に返す。実装レビューの設計の指摘は、SE が設計の節を直し、PG が作り直して PL に知らせ、QA はもう一度は見ない(詳しい文は skill `task-team-qa`)。

## 捨てた案

1. 今のまま、code-review と仕様の行で見る: code-review は、渡した差分の中の正しさの誤りを探し、設計とのずれは探さない(ADR 0067-3 の捨てた案1)。プロンプトが中身のリポジトリでは、仕様は PG が書いた文書そのもので、照らす相手にならない。
2. 照らす相手を、レビューのときの設計の節にする: 設計の節が合意の後に書き換わっていれば、ずれた中身どうしを照らすことになる。ADR 0069-1 で PG は書き換えないが、書き換えたときに止める所が要る。
3. 合意した時点を、ステータスが「実装中」になったコミットにする: 大きな変更では、「実装中」にするのは PG で、そのコミットに PG の書き換えが入りうる。
4. 合意した時点を、SE が実装を頼むコミットに付けたタグか、決まったコミットメッセージで示す: 新しい決まりが要る。済んだサブタスクに `[x]` を付けてから知らせる決まりは、既にある(skill `task-team-messaging`)。
5. 二通りに読める所を、実装の指摘として PG に返す: どちらの読み方が合意した中身かを知るのは SE で、PG が直すと、また PG が選ぶことになる。
6. 実装レビューの設計の指摘を SE と PG が直したあと、QA が実装レビューをもう一度する: SE・PG・QA の往復が増える。利用者は、何往復もするレビューは本末転倒と言い、レビューは設計と実装に1回ずつにした(ADR 0067-3 の捨てた案3)。直しは、QA が指摘の文で決めた所に限られ、PG が判断する余地が残らない。

## 理由

1. 利用者の怖れ(PG の解釈のずれによる誤った実装が通る)は、ずれが起きる所と、ずれを見つける所の両方をふさがないと残る。ADR 0069-1 がふさぐのは、PG が判断していると気づいている所だけで、気づいていない読み違いは、照らす所でしか見つからない。
2. 今の skill `task-team-qa` の実装レビューは、code-review・テスト一覧・ADR の番号・仕様の行の4つで、作ったものを設計の節と受け入れ条件に照らす行が無い。
3. 利用者が見る「やり方を決める」の結果は、実装のサブタスクが始まる前の設計の節。サブタスクは、設計・設計レビュー・利用者が確かめるサブタスク・実装レビューの順に並ぶ(skill `task-team-se`)。
4. 照らし合わせは、同じ1回の実装レビューの中でするので、レビューの往復は増えない(ADR 0067-3 の理由5)。
