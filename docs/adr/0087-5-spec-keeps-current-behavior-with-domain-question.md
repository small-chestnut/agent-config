# 0087-5 コードから仕様を作るときは、今の動きを仕様に書き、業務の状態を分野の定義と照らして、違いを決まっていない問いにする

状態: 採用
日付: 2026-11-15
対象: task-team-se
置き換える: 0087-3

## 決めたこと

skill `task-team-se` で、仕様の無い機能の仕様をコードから作るときは、仕様にはコードの今の動きを書き、コードが分けている業務の状態を、その業務の分野の定義と照らし、違いをチケットの「決まっていない問い」にする。行は、入れる前と入れた後の試し聞きで、入れた後の方が違いを問いにした答えが多いときだけ入れる。

## 捨てた案

1. ADR 0087-3 のまま、違いを仕様に写さない: 仕様は機能の今の動きを書く文書(ADR 0045-2)で、今の動きを書かない仕様は、利用者が答えるまで、コードの今の動きをどこにも残さない。試し聞き(K4)では、行を入れた後の3回とも、今の動きを仕様に書いたうえで、違いを決まっていない問いにした。
2. 違いのある状態を、仕様に書いたうえで「要確認」などの印を付ける: 印の付いた行と決まっていない問いの2か所に同じことを書くことになる。利用者が問いに答えれば、仕様の直しはそのタスクでする。
3. 全体の CLAUDE.md に、業務の語と状態を分野の定義から決める一般の文を置く(LogiFee から届いた G1・G2・G4): LogiFee の試しで、一般の文は答えを変えなかった(0/3・0/3・1/5)。利用者も入れないと決めた。
4. 今の行のまま、コードの今の動きを写すだけにする: コードの取り違えが仕様に入り、仕様と照らすレビューでも見つからない(LogiFee R-0822)。
5. 違いを見つけたら、SE が分野の定義の方に合わせて仕様に書く: コードと定義のどちらが利用者の業務に合うかは業務の事実で、利用者に聞くこと(ADR 0063-1)。SE が決めると、コードと仕様の食い違いを利用者が知らないまま残る。
6. 試し聞きをせずに入れる: 同じ作りの文が LogiFee で答えを変えなかったので、効くと示せない。skill `prompt-structure` は、足しても振る舞いが変わらなかった規則を消すと決めている。

## 理由

1. Claude は、その作業で目の前にある仕様の名前と定義に沿う(LogiFee の試し)。仕様を作る時点で照らさないと、コードの誤った分かれ方が仕様に入り、後の作業がそれに沿い続ける。
2. 取り違えが仕様に残って見つからないのを防ぐのは、違いを利用者に問うことで、仕様から今の動きを外すことではない。違いを決まっていない問いにすれば、どちらが正しいかを、業務の事実を知る利用者が答える。
3. 仕様に今の動きを書いておけば、利用者がコードを直すと答えたときも、名前や定義を直すと答えたときも、直す元の動きが仕様にある。
4. 試し聞き(K4・2026-11-15)で、違いを問いにした答えは、行を入れる前が3回のうち1回、入れた後が3回のうち3回だった。
5. LogiFee の一般の文が届かなかったのは、目の前の仕様に負けたから。この行は、目の前にまだ仕様が無く、SE が仕様を書くその手順の中で働く。
