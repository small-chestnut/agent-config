# 0085-5 チケットを、要件・設計・作業の一覧を持つ1つのテンプレートに固定し、要件を番号と「なぜ」つきで書いて設計とテストから番号で指す

状態: 採用
日付: 2026-11-14
対象: task-team-se・task-team-pg・task-team-qa

## 決めたこと

チケットの形を、skill `task-team-se` に置く1つのテンプレートに固定し、利用者と合意した内容は、要件ごとに番号・「なぜ」・受け入れ条件を持つ「要件」の節にだけ書いて、設計の行とテストから番号で指し、PG と QA は「要件」の節を読む(テンプレートは skill `task-team-se`)。

## 捨てた案

1. 今のまま、チケットの形を規則の文で決める: 利用者と合意した内容と「なぜ」は「壁打ち」の節にあり、PG が読む節(ゴール・受け入れ条件・設計)に入っていない。SE が別の節へ写し直した分しか届かない。設計の節の中の見出しも決まっていない。
2. SE がテンプレートの構成を自分で組み立てる: 利用者は、定石の構成を使うと決めた。
3. 利用者が見せた、ほかの AI の7節の設計書の形を使う: 5節(スコープ・データ・画面・例外・受け入れ条件)は今の規則にある。「技術スタック」はリポジトリの CLAUDE.md にあり、タスクごとに書くと同じ事実が2か所になる。
4. 要件・設計・作業の一覧を、定石のとおり3つのファイルに分ける: かんばんとフック(チケットのコミットの push)が、チケットを1つのファイルとして読んでいる。1つのファイルの3つの節にすれば、どちらも変えずに済む。
5. テンプレートを、SKILL.md と別のファイルに置く: インストールのスクリプトは、skill のフォルダから SKILL.md だけを配る。
6. PG に「壁打ち」の節も読ませるだけにする: 合意した内容が、決まっていない問いや経緯と混ざったまま届き、設計のどの行がどの合意のためかは分からないまま残る。
7. 管理の欄(ステータス・PC・利用者待ち・難しさ)を消す: 「PC: 」と利用者待ちの行は、かんばんと PL が読んでいる。難しさは、モデルを替える根拠の記録。設計の中身ではないので、テンプレートの上にまとめ、PG と QA が読む節(ゴール・要件・設計)と分ける。

## 理由

1. 利用者の「なぜ」: チームは、コンテキストを節約し、役割ごとに専門の仕事をさせるために、セッションを分けている。そのため、意図が伝わるかは受け渡す文書の書かれ方で決まる。SE が利用者と壁打ちして、理由も含めて合意した設計の意図が、後のセッションで漏れるのは受け入れられない。意図を欠いた実装になり、QA の指摘も的を外す。
2. スペック駆動開発は、文書を要件・設計・作業の一覧に分け、決まったテンプレートで AI に渡す。GitHub の Spec Kit の仕様のテンプレートは、利用者の話ごとに理由と受け入れの筋書きを持たせ、要件に番号を振る(https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md )。Kiro は、requirements.md・design.md・tasks.md の3つを作る(https://kiro.dev/docs/specs/feature-specs/requirements-first/ 。どちらも 2026-11-14 に読んだ)。
3. Anthropic は、エージェントに渡す文に目的・出力の形・範囲が欠けると、受け取った側が読み違えると書いている(https://www.anthropic.com/engineering/multi-agent-research-system 。2026-11-14 に検索で読んだ)。
4. 要件に番号を振り、設計の行とテストから指すと、QA は、どの要件も設計と作ったものに入ったかを番号で確かめられる(トレーサビリティ)。
5. 今のチケットの節は、定石の3つに当たる(ゴール・受け入れ条件が要件、設計が設計、進捗が作業の一覧)。足りないのは、形を固定したテンプレートと、要件ごとの「なぜ」と番号。
