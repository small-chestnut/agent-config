# 0087-3 コードから仕様を作るときは、業務の状態を分野の定義と照らし、違いを決まっていない問いにする

状態: 提案
日付: 2026-11-15
対象: task-team-se

## 決めたこと

skill `task-team-se` で、仕様の無い機能の仕様をコードから作るときは、コードが分けている業務の状態を、その業務の分野の定義と照らし、違いを仕様に写さずにチケットの「決まっていない問い」にする。行は、入れる前と入れた後の試し聞きで、入れた後の方が違いを問いにした答えが多いときだけ入れる。

## 捨てた案

1. 全体の CLAUDE.md に、業務の語と状態を分野の定義から決める一般の文を置く(LogiFee から届いた G1・G2・G4): LogiFee の試しで、一般の文は答えを変えなかった(0/3・0/3・1/5)。利用者も入れないと決めた。
2. 今の行のまま、コードの今の動きを写す: コードの取り違えが仕様に入り、仕様と照らすレビューでも見つからない(LogiFee R-0822)。
3. 違いを見つけたら、SE が分野の定義の方に合わせて仕様に書く: コードと定義のどちらが利用者の業務に合うかは業務の事実で、利用者に聞くこと(ADR 0063-1)。SE が決めると、コードと仕様の食い違いを利用者が知らないまま残る。
4. 試し聞きをせずに入れる: 同じ作りの文が LogiFee で答えを変えなかったので、効くと示せない。skill `prompt-structure` は、足しても振る舞いが変わらなかった規則を消すと決めている。

## 理由

1. Claude は、その作業で目の前にある仕様の名前と定義に沿う(LogiFee の試し)。仕様を作る時点で照らさないと、コードの誤った分かれ方が仕様に入り、後の作業がそれに沿い続ける。
2. 違いを決まっていない問いにすれば、どちらが正しいかを、業務の事実を知る利用者が答える。
3. 一般の文が届かなかったのは、目の前の仕様に負けたから。この行は、目の前にまだ仕様が無く、SE が仕様を書くその手順の中で働くので、一般の文とは置き場所が違う。ただし効くかは試し聞きで確かめる。
