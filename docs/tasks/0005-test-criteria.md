# ゴール

task-team で、どのテストを作り、どのテストを作らないかと、テストの大きさ(小・中・大)の決め方を、SE・PG・QA の skill と README に入れる。SE が設計の節に受け入れ条件ごとのテストの大きさを書き、PG はそのとおりに作り、QA はレビューで多すぎるテストと足りないテストを指摘する。

範囲外: 既にあるテストを、この基準に合わせて足す・消すことと、基準をフックやテストで検査すること。

# 受け入れ条件

1. `task-team-se` に、目指す状態「作るテストは、設計のテスト一覧に、数と大きさまで決まっている」と、その下の9行がある。
2. `task-team-se` に、目指す状態「テスト一覧に、要らないテストが無い」と、その下の5行がある。
3. `task-team-pg` の「テスト名は、受け入れ条件の文。」が、テスト一覧のとおりに作る行と、一覧に無いテストを設計への問いにする行に替わっている。
4. `task-team-qa` に、目指す状態「多すぎるテストと足りないテストが、指摘に入っている」と、その下の3行がある。
5. README の「セッションの役割分割」の節に、テストの基準の意図と理由がある。
6. `docs/用語集.md` に、テスト一覧・テストの大きさ・テストの基準がある。
7. どの SKILL.md の箇条書きの行も 60 字以内(`python -m unittest discover -s tests` が通る)。

# 設計

決定は [ADR 0005-1](../adr/0005-1-test-criteria.md)(採用)。用語は [docs/用語集.md](../用語集.md)(この設計と同じコミットで SE が足した)。する人は、どの手順も PG。

出典: テストの大きさの定義と、カバレッジを目標にする弊害は、Software Engineering at Google 11章(https://abseil.io/resources/swe-book/html/ch11.html)。公開の入口から振る舞いを確かめることは、同じ本の12章「Test via Public APIs」「Test State, Not Interactions」(https://abseil.io/resources/swe-book/html/ch12.html)。

## 手順: 規則の文書を直す

下の行を、そのとおりの文で入れる。「→」は置き換え、「足す」は新しい行。フック(`ask_removable_words.py`)が問い返してきても、文は変えない。SKILL.md の行の字数は `rule_length` で数え済み(すべて 60 字以内)。

### `claude/skills/task-team-se/SKILL.md`

「### 目指す状態: 受け入れ条件は、テスト名で言える」とその1行の後(「### 目指す状態: 設計は、短く、…」の前)に、次の2つを足す。

```
### 目指す状態: 作るテストは、設計のテスト一覧に、数と大きさまで決まっている

- 設計の節に「テスト一覧」の表を置き、テスト名・大きさ・受け入れ条件を並べている。
- 受け入れ条件1つに、テスト1つ以上。
- 業務の規則の分かれ目(分岐・計算)ごとに、小さいテストを1つ。
- 分かれ目の値の境目は、前後の値も確かめている(境界値分析)。
- バグは、再現するテストを1つ。
- 大きさは、確かめられる中で一番小さいもの。
- 中は、外部(DB・ネットワーク)とのつなぎ目を確かめるときだけ。
- 大は、利用者の主な使い方1本につき1つまで。
- 大きさごとの割合と、カバレッジの目標値は置かない。

### 目指す状態: テスト一覧に、要らないテストが無い

- 内部の作り(外から呼べない関数・呼ばれた回数など)は確かめない。
- 言語・フレームワーク・外部ライブラリそのものの動きは確かめない。
- 分岐の無いコード(値の受け渡しだけ・設定の値)は確かめない。
- 同じ規則を、別の大きさでもう一度確かめない。
- 文書だけ・設定だけの変更は、テストを作らず、確かめ方を一覧に書く。
```

### `claude/skills/task-team-pg/SKILL.md`

「### 目指す状態: 受け入れ条件ごとに、先に失敗するテストがある」の「- テスト名は、受け入れ条件の文。」→ 次の2行。

```
- テストは、設計のテスト一覧の名前・大きさ・数のとおりに作っている。
- 一覧に無いテストが要ると思ったら、作らずに「設計への問い」にしている。
```

### `claude/skills/task-team-qa/SKILL.md`

「### 目指す状態: レビューは、公式の code-review を1回かけたもの」の箇条書きの後(「### 目指す状態: ターンが終わるとき、…」の前)に、次を足す。

```
### 目指す状態: 多すぎるテストと足りないテストが、指摘に入っている

- 設計のレビューでは、テスト一覧を skill `task-team-se` のテストの基準と比べている。
- 実装のレビューでは、作ったテストを、テスト一覧とテストの基準と比べている。
- 多すぎるテストと足りないテストを、指摘に足している。
```

### `README.md`

「## セッションの役割分割(PL / SE / PG / QA)の意図」の「- **テストを流す時と量は、…**」の項目の後(「- **後から変えにくい設計の決定は、…**」の前)に、次の項目を足す。

```
- **作るテストと作らないテストは、SE が設計のテスト一覧で決め、PG はそのとおりに作り、QA が多すぎと足りなさを指摘する**(ADR 0005-1)。
  基準は `task-team-se` に置き、QA はそれを読む。作るのは、受け入れ条件ごとのテスト・業務の規則の分かれ目ごとの小さいテスト(境界値分析)・
  バグを再現するテスト。内部の作りを確かめるテストは、振る舞いを変えずに作りを直しただけで壊れるので作らない。
  大きさは、確かめられる中で一番小さいもの(小さいほど速く、落ちた原因を絞りやすい)。大きさごとの割合とカバレッジの目標値は、
  どの規則を確かめたかを問わない数字で、多すぎるテストを止められないので置かない
```
