## ゴール

実際の小さいタスク1つを、プロジェクトのクラウドのスレッドで最後まで進め、task-team の手順と規則がどれだけ減らせるかを確かめる。

範囲外: この PC が要る仕事。複数のスレッドは、割り振った結果スレッドが2本以上になったときだけ見る。

## 要件

### R1 小さいタスク1つを、スレッドで最後まで試す

- 要件: 実際の小さいタスク1つを、スレッドで最後まで試す(利用者が「続ける」と答えた)。agent-config の決まりは、環境のセットアップスクリプトで届ける(ADR 0100-1)。環境 `agent-config-trial` が残っていれば、それを使う。
- なぜ: task-team に書いてある手順と規則を、「プロジェクト」機能にカバーさせて減らすため。1回目の試験は、リポジトリの無いプロジェクトで、決まりが届くことだけを確かめた。
- 受け入れ条件 R1-1: `result.md` に、チケットの作成からマージまでのどの工程も、「した」「利用者の手でした」「止まった」「しなかった」のどれかで書かれ、根拠(コミット・PR・スレッドの出力)が付いている
- 受け入れ条件 R1-2: スレッドが main にマージしたか、止まった所と止めた文が `result.md` に書かれている
- 受け入れ条件 R1-3: `result.md` に、covered-groups.md の A〜K のどれも、「肩代わりされた」「されなかった」「見ていない」のどれかで書かれ、根拠と、「肩代わりされた」行の数の計が付いている
- 受け入れ条件 R1-4: 試すために作ったプロジェクトが、アーカイブされている。環境は、元に戻せないことを伝えたうえで利用者が許可したらアーカイブされ、許可しなければ残り、残したことが「実装」の節に書かれている

### R2 1回目に確かめなかったものを、同じタスクで見る

- 要件: 1回目の試験で確かめなかったもの(リポジトリを付けたプロジェクト・QA の独立・マージの担当)と、確かめきれなかったもの(利用者を待つことが、Overview とプロジェクトの会話のどちらに出るか)を、同じタスクで見る。
- なぜ: 肩代わりする見込みの 72 行のうち、利用者待ちとかんばんの待ちの行は、肩代わりされるかが決まっていない(ADR 0100-1 の理由4)。公式文書に無い3つは、SE・PG・QA のやりとりの規則が消えるか書き換えになるかを決める(理由5)。
- 受け入れ条件 R2-1: `result.md` に、スレッドに読み込まれた指示のファイルのパス(全体の CLAUDE.md とリポジトリの CLAUDE.md)と、スレッドが始まったブランチとコミットが書かれている
- 受け入れ条件 R2-2: `result.md` に、QA に渡した文の全部・QA が合言葉を知っていたか・QA が「レビュー」の節を自分で書いたか・利用者が QA の会話を開けたかが書かれている
- 受け入れ条件 R2-3: `result.md` に、PR を作った人とマージした人と、その方法が書かれている
- 受け入れ条件 R2-4: 質問 1(質問用のツール)と質問 2(文)のそれぞれが、利用者の画面の Overview とプロジェクトの会話のどちらに、どの見出しで出たかが、`result.md` に書かれている

### R3 役割の割り振りを、始める前に利用者に聞く

- 要件: SE・PG・QA の仕事を、スレッドとサブエージェントのどれに割り振るかは、始める前に利用者に聞く。利用者は、この試しの間だけ、SE と PG の仕事を同じスレッド1本で、QA の仕事をそのスレッドのサブエージェントでする形でよいと答えた(「試しの間だけよい」)。ADR は書き換えない。
- なぜ: この形は、ADR 0057-2 の捨てた案3の理由(利用者が開いて止めたり口を挟んだりできなくなる)・ADR 0007-1 の理由1(SE の会話を知らない別のセッションが読むことが、利用者の代わりの同意になる)・ADR 0059-1 の理由1(モデルは役割の仕事ごとに割り当てる)と逆向き。3つを利用者に見せて、この試しの間だけ外すかを聞いた。

### R4 試すタスクとクラウドの操作を、利用者に聞く

- 要件: 試すタスクを選ぶことと、クラウドの操作をすることは、利用者に聞く。試すタスクは「agent-config に lint のコマンドを足す」(利用者が、候補2つを見て選んだ)。

公式文書で確かめた事実(2026-11-25 に web-fetch のサブエージェントが https://code.claude.com/docs/en/claude-projects を読んだ。初めの約 40,000 字が原文、残りは要約):

### 手順

外部の操作をする前に、PG は下の「許可を受ける操作」の全部を PL に知らせ、利用者の許可が届いてから始める。操作は Claude in Chrome でする。画面が手順と違うときと、手順に無い操作が要るときは、操作せずに「設計への問い」にする。サインイン・GitHub App の導入・同意・許可の問い・スレッドへの答えは、利用者がする。(R4-1)

許可を受ける操作(スレッドが使った利用枠は戻らない。公開リポジトリに push したコミットと PR は、消しても人に見られた後かもしれない):

1. 利用者の Chrome で claude.ai/code を開いて見る
2. プロジェクト `agent-config-lint-trial` を作り、リポジトリ `small-chestnut/agent-config` と環境 `agent-config-trial` を選び、スレッドの effort を「高」にする
3. プロジェクトの会話に thread-message.md の文を1回送る(スレッド1本。クラウドの中でサブエージェントも動く)
4. スレッドが、公開リポジトリ agent-config に作業ブランチを push し、PR を1つ作る
5. 利用者が質問 2 に「よい」と答えたら、スレッドが PR を main にマージする(戻すときは revert のコミットを足す)
6. プロジェクトを作った直後に Claude が自分でスレッドを始めたら、止める
7. 終わった後、プロジェクトをアーカイブし(戻せる)、マージの後に残った作業ブランチを GitHub から消す(PR の画面から戻せる)。環境のアーカイブは元に戻せないので、するか残すかを別に聞く

手順:

1. 利用者の Chrome で claude.ai/code を開き、プロジェクトを作る画面でリポジトリ `small-chestnut/agent-config` が選べるかを見る。選べなければ、「利用者がする操作」の操作 C を頼む。(R2-1)
2. プロジェクトを作り、上の「置くファイルと名前・データ」の設定にする。リポジトリ・環境・effort が選ばれていることを、画面で確かめる。Claude が自分でスレッドを始めたら、止めて `result.md` に書く。(R1・R2-1)
3. thread-message.md の文を送る。送る前の入力欄の文がファイルと同じことを確かめる。許可の問いでスレッドが止まったら、PG は答えず、止めた文を `result.md` に書き、操作 D を頼む。(R1・R2)
4. 質問 1 が出たら、Overview とプロジェクトの会話のスクリーンショットを撮り、操作 A を頼む。(R2-4)
5. 質問 2 が出たら、Overview とプロジェクトの会話のスクリーンショットを撮り、QA のサブエージェントの会話がスレッドの画面から開けるかと、入力欄か停止のボタンがあるかを見て(押さない)、操作 B を頼む。(R2-2・R2-4)
6. スレッドが終わったら、スレッドの出力と、GitHub の PR・コミット・main を見て(`gh` で読むだけ)、`result.md` を書く。判定は covered-groups.md の見え方と次の表でする。どちらとも言い切れないものは「見ていない」とし、理由を1行書く。B は、かんばんの代わりになるかの利用者の答えを待つので、見えたものだけを書く。(R1-1・R1-2・R1-3・R2-1・R2-2・R2-3・R2-4)

| 見るもの | 見え方 |
|---|---|
| QA が SE の会話を引き継いでいない(R2-2) | QA の答え (1) が「分からない」で、(2) が QA に渡した文の最初の1行。渡した文に、thread-message.md の 2 にあるもののほかが無い |
| QA が自分で書いた(R2-2) | 「レビュー」の節を書いたコミットが作業ブランチにあり、QA の最後の返答に、そのコミットをしたとある |
| リポジトリが付いた(R2-1) | 読み込まれた指示に、全体の CLAUDE.md とリポジトリの CLAUDE.md の両方がある。始まったコミットが、送った時点の main の先頭 |
| マージの担当(R2-3) | PR の作成者とマージした人(GitHub の表示)と、スレッドの出力にある方法 |

   - 確かめ方: `result.md` の根拠の文が、スレッドの出力か GitHub の表示の中にそのままあることを、1つずつ照らして確かめる。利用者の名前・メールアドレス・アカウントの URL・トークンが無いことを、検索して確かめる。
7. コミットし、SE に「実装」の節を読むよう `SendMessage` で知らせてターンを終える。マージされていれば、PL に、main に `claude/` の変更があるか(あればインストールが要ること)を知らせる。(R1)
8. SE が `result.md` の表を利用者に見せ、B がかんばんの代わりになるかと、次にすることを聞く。答えを `result.md` の B の判定と計、ADR に書き、続けるなら「分けたタスク」に書く。QA に設計レビューを頼む。(R1-3)
9. QA から実装を頼まれたら、PG がプロジェクトをアーカイブし、一覧に「アーカイブ済み」と出ることを見る。残った作業ブランチを消し、GitHub のブランチの一覧に無いことを見る。環境は、利用者の答えのとおりにして、環境の選択の一覧で確かめる。新規セッションの環境の選択が「自動」のままであることも見る。結果を「実装」の節に書き、QA に実装レビューを頼む。(R1-4)

### 利用者がする操作

操作 A・C・D は元に戻せる。操作 B の「よい」で main にマージされる(戻すときは revert のコミットを足す)。

操作 A(手順 4):

- 何を: 自分の画面(デスクトップアプリ)で、プロジェクトの Overview と会話を見て、質問 1 がどこに出ているかを確かめてから、スレッドを開いて答える。
- ゴールにどうつながるか: かんばんと「利用者待ち」の規則を、プロジェクトの画面が肩代わりできるかが分かる。
- なぜ利用者の手でか: 肩代わりされるのは利用者への見え方で、フックのコードを直してよいかは利用者が決めることだから。
- 手順: PG が出すプロジェクトへのリンクを開く → Overview を見る → プロジェクトの会話を見る → スレッドを開いて質問 1 に答える。
- 終わったら返すこと: 質問 1 が、Overview のどの見出しに出たか(出なければ「出ない」)と、会話に出たか。

操作 B(手順 5):

- 何を: 操作 A と同じことを質問 2 で見てから、スレッドの中の QA のサブエージェントの会話を開いてみて、質問 2 に答える。
- ゴールにどうつながるか: QA をサブエージェントにしたときに、利用者が QA の会話を見られるか(ADR 0057-2 の捨てた案3 の理由)と、誰がマージするかが分かる。
- なぜ利用者の手でか: 利用者への見え方と、main にマージしてよいかは、利用者が決めることだから。
- 手順: PG が出すリンクを開く → Overview と会話を見る → スレッドを開き、QA のサブエージェントの行を押す → 質問 2 に「よい」か「よくない」と答える。
- 終わったら返すこと: 質問 2 が出た所と、QA の会話を開けたか(話しかける欄か止めるボタンがあったか)。

操作 C(リポジトリが選べないときだけ):

- 何を: GitHub で、Claude GitHub App を `agent-config` に入れる(ほかのリポジトリは選ばない)。
- ゴールにどうつながるか: リポジトリを付けたプロジェクトを試せる。
- なぜ利用者の手でか: アカウントへの権限の付与は、AI が代わりにできないため。
- 手順: PG が出す GitHub App の画面を開く → Only select repositories で agent-config を選ぶ → Save。戻すときは同じ画面で外す。
- 終わったら返すこと: 「済んだ」か「やめる」。

操作 D(求められたときだけ):

- 何を: サインイン・利用規約やベータ版の同意・スレッドの中の許可の問いに答える。
- ゴールにどうつながるか: 試しを続けられる。
- なぜ利用者の手でか: サインイン・同意・許可の承認は、AI が代わりにできないため。
- 手順: PG が出す画面のリンクを開き、答える。許可の問いは、agent-config の作業ブランチと PR の中の操作なら許してよい。main への push・force push・設定の変更は断る。質問 2 に「よい」と答えた後の、PR のマージは許してよい。
- 終わったら返すこと: 「済んだ」か「断った」。
