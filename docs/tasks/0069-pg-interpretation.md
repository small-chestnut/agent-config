## 壁打ち

### 固まった要件

- 利用者が SE のやり方に合意したあとで、PG が解釈のずれから誤った実装をし、それが見つからずに通ることを防ぐ。(利用者の言葉「SEのやり方に納得した後、実はPGが解釈揺れを起こして誤った実装をしていた、というのが怖い」)
- SE が全手順を決めきっているなら、PG は今の割り当てでよい。PG に判断する余地があるなら、SE と同じくらいの思考量が要る。(利用者の答え。PL のタスクの文)
- 次の3つを1つのタスクにする。(利用者が同意した)
  1. 設計が決めていない所で、利用者に見える動きを左右する判断は、PG がせずに SE に聞く。
  2. QA の実装レビューは、利用者が合意した時点の設計と実装を照らす。
  3. それでも PG に残る判断の余地には、SE と同じ思考量(Opus 5.5 の high)を当てる。
- 「合意した時点の設計」は、SE が PG に実装を頼んだときの設計の節。利用者が見る「やり方を決める」の結果がこれに当たる。

### 分かっていること

- skill `task-team-pg` の28行目「設計が決めていない所を判断して、利用者に見える動きが変わったら、設計の節を同じコミットで直している」は、PG が聞かずに判断し、設計の節を書き換えることを認めている。21行目の見出し「設計を変える判断は、PG がしていない」とぶつかる。
- skill `task-team-qa` の実装レビューは、差分に code-review を low で1回かけること、テストとテスト一覧を比べること、ADR の番号、仕様の行と動きを比べること、の4つ。実装が設計の節と受け入れ条件のとおりかを照らす行が無い。
- code-review が探すのは、渡した差分の中の正しさの誤り(ADR 0067-3 の捨てた案1)。設計に照らしたずれは探さない。
- SKILL.md のようにプロンプトが中身のリポジトリでは、その文書が仕様(skill `task-team-se`)。仕様の行と動きを比べても、PG が書いたものどうしを比べることになり、照らす相手は設計の節しか無い。
- 28行目のとおり PG が設計の節を書き換えると、QA が照らす設計は、合意した中身でなく PG が書き換えた後のものになる。
- 1は、PG が自分で判断していると気づいている所だけをふさぐ。PG が読み違えに気づいていない所は、2で QA が設計の節と照らして見つける。
- 今の割り当ては、低が Sonnet 5.5 の medium、中が Opus 5.5 の medium、高が Opus 5.5 の high(ADR 0059-1)。SE はいつも高(ADR 0067-1)。
- Anthropic の測定で、Opus 5.5 の medium から high では、コードの課題1件の費用が $0.21 から $0.29(約1.4倍)、解けない割合が 7.2% から 4.7%(ADR 0059-1・0067-1 の理由)。
- 2026-11-12 に `get_usage` で引いて、全部のモデルの週の枠は 36%(週の約 38% が過ぎたところ)、5時間の枠は 86%。
- タスク 0068-search-existing は、skill `task-team-se` の「設計で読む ADR」の見出しの前に見出しを1つ足し、その見出しを書き換え、全体の CLAUDE.md の1行を3行にする(ブランチ `claude/0068-search-existing-de7fd1` の設計の節)。このタスクで触る見込みの所(skill `task-team-pg`・`task-team-qa`、skill `task-team-se` の費用対効果の目的)とは、同じ行に当たらない。

### 効くか逆効果か

- 1は効く。PG が聞かずに判断して設計を書き換える入口(`task-team-pg` の28行目)をふさぐ。
- 2は効き、3つの中でいちばん大きい。今は、実装が設計のとおりかを照らす所が QA に無く、ずれが見つからずに通る原因になっている。
- 3は効くが、1と2より小さい。1のあと PG に残る判断は、利用者に見えない所と、設計の読み取りだけになる。増える費用は、中の仕事で約1.4倍。今の週の枠の使い方なら収まる見込み。
- 3の「判断の余地には SE と同じ思考量」という理由は、役割によらない。QA の中の仕事にも同じく効く。
- 逆効果になる所は見つからなかった。PG から SE への問いは増えるが、利用者の合意から外れた実装を利用者が自分で見張る手間(README の「なぜ」の認知負荷)が減る。
