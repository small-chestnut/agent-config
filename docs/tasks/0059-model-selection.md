## ゴール

チームの各役割(PL・SE・PG・QA)のモデルと effort を、役割に要る力で決める規則を作る。

タスクの文(利用者の言葉のまま): PLセッションが、単純なチーム管理の役割になった結果、必ずしもPLのモデル > SE/QA/PGのモデルという図式が成り立たなくなったように思う よって、モデル選定のルールを決めたい

範囲外: task-team の外(ふだんのセッション・サブエージェント一般)のモデル選びは決めない。

## 壁打ち

### 固まったこと

1. Fable は、起こすときの割り当てに入れない。なぜ: 測った数字では、Fable 5.2 が費用に見合ったのは、長いコードの作業と大きな資料の作業だけ。調べものに近い作業では、Opus 5.5 の medium が同じか上だった。このチームの仕事は、1つの会話に収まる短い仕事。
2. PL のモデルは Opus 5.5。
3. 子を PL より強いモデルにするときは、PL が起こした直後に `set_session_model` で上げる。
4. モデルと effort は、役割ごとに固定にせず、タスクで変える。なぜ: 性能は大事だが、利用者の財布(使用量の費用)も気にしたい。
5. 設計する SE 自身のモデルも、設計の難しさで変える。
6. 基準は、どの種類のタスクに、どのモデルのどの effort を割り当てるかの形で書く。基準の中身は SE が決める。なぜ: どのモデルがどの仕事に合うかは、利用者が決めても推測にしかならない。
7. モデルと effort は、仕事の難しさで決める。なぜ: 本質は、難しさに合わせてモデルと effort を変えること。ADR の有無・誰が頼んだか・レビューの種類は、難しさをざっくり切り分けた目安にしかならない。
8. 難しさは、タスクごとでなく、役割の仕事ごとに見る(決めるのは難しいが作るのは易しいタスクも、その逆もある)。
9. 難しさは、やることが、既にあるもの(仕様・設計・規則)でどこまで決まっているかで、3段に分ける。割り当ては、下の「割り当て」のとおり(SE が決めた)。
10. 難しさを決めるのは、その仕事の中身を知っている SE。SE の仕事は最初のターンで、PG と QA の仕事は設計を書き終えたときに決め、理由と一緒にチケットに書く。
11. 規則の目的は、仕事の難しさに足りる性能を出す形を選び、それを越える性能を選ばないこと。なぜ: 難しさに足りない性能では仕事が仕上がらず、余る性能は費用を損なう。難しさの3段と割り当ては、この目的の今の手段。

12. 利用者は、費用と性能の釣り合いの判断を SE に任せた(モデルと effort の仕様を正確に把握した上で SE がよいと思うなら、よい)。

### 調べた事実

1. 今の規則は、`claude/skills/task-team-lead/SKILL.md` の「モデルと effort は、SE と QA が `claude-opus-5-5` の high、PG が `claude-sonnet-5-5` の medium。」と、`claude/skills/task-team-lead/CLAUDE.md` 原則3 の「PL は進捗管理だけで、Opus 級のモデルで足りる。」「子は起こした側のモデル以下しか選べず、PL のモデルが上限になる。」「Fable が要る設計は、利用者が SE のモデルを手で上げる。」。
2. 今の PL のセッションは `claude-fable-5-2` の high、この SE は `claude-opus-5-5` の high(2026-11-10 に `get_session` で引いた)。
3. 「起こした側のモデル以下」は、起こすときだけ正しい。`start_session` の `model` は「起こした側と同じ系統か安いもの。高いものは無視」。
4. 起こした後は、`set_session_model` と `set_session_effort` で、起こした側より高いモデル・effort に上げられる。高い方へ上げるときは、アプリが利用者に聞く。権限のモードが bypassPermissions なら聞かない(どちらも道具の説明による。まだ試していない)。
5. タスク 0056 で、タスクの中身の話は PL でなく SE の会話でする形になった(ADR 0056-1)。利用者が読む文の多くは、SE が書く。
6. 100万トークンあたりの値段(入力 / 出力)は、Fable 5.2 が $8 / $40、Opus 5.5 が $4 / $20、Sonnet 5.5 が $2 / $10、Haiku 5.5 が $0.10 / $0.50。Fable は Opus の2倍、Sonnet の4倍。
7. Anthropic の手引きでは、Fable 5.2 は「いちばん難しい推論と長い作業」向けで、effort は high から始める。high より上の伸びはまばらで、xhigh は測って伸びが出た所だけ。
8. 同じ手引きで、Opus 5.5 は medium で Opus 5 の high を越え(コードと知的作業)、effort は medium から始める。Sonnet 5.5 は、エージェントのコーディングで medium から始める。
9. 同じ手引きで、費用はトークン単価でなく、作業1つを終えるまでの合計で比べる。
10. モデルを替えると、その会話のキャッシュは使えず、次のターンで会話の全部を読み直す(キャッシュはモデルごと)。
11. 役割ごとの使用量は、道具では引けない(`get_usage` が返すのは、プランの上限の残りと、会話の埋まり具合だけ)。
12. この会話で、Opus 5.5 の SE は、SE が決めるべき基準を利用者に2回聞き返し、利用者に「あなたが考えるべきこと」と直された(2026-11-10)。

13. 利用者のプランは Max。使用量の枠は、5時間・週(全モデル)・週(Fable)の3つで、Fable だけ別の週の枠がある。追加の課金は切ってある(2026-11-10 に `get_usage` で引いた)。
14. その時点で、週の枠はリセットまで6日2時間(始まって1日弱)で、全モデルが 32%、Fable が 43% 使われていた。PL は Fable 5.2 の high で動いていた。
15. コードの課題(SWE-bench Pro)を1件解く費用と、解けた割合: Sonnet 5.5 の high が $0.11 で 87.6%(medium は費用が約6割で、約7ポイント下)。Opus 5.5 は low が $0.11 で 87.4%、medium が $0.21 で 92.8%、high が $0.29 で 95.3%、xhigh が $0.74 で 96.7%。Fable 5.2 は low が $0.39 で 94.6%、high が $1.39 で 96.3%。
16. 長いコードの作業(Anthropic の社内の課題)では、Sonnet 5.5 が medium 62.7%($0.16)・high 77.8%($0.33)。Opus 5.5 が medium 86.6%($0.84)・high 88.4%($1.38)。Fable 5.2 が low 88.9%($1.05)・high 93.5%($5.39)。
17. 調べものの課題(DeepResearch Bench II)では、Fable 5.2 の high は、Opus 5.5 の medium より 1.9 ポイント下で、費用は 2.9 倍。
18. 同じページの勧め: たいていのエージェントの作業は、Opus 5.5 の medium から始める。決まりきった作業は low から。high より上は、失敗が高くつき、伸びが測れた所だけ。
19. 同じページ: 失敗が分かる仕組み(テストなど)があるなら、全部を低い設定で走らせ、失敗だけを高い設定でやり直すと、全部を高い設定で走らせるのと同じ割合が、約4割安く出た。
20. 同じページ: いちばん小さいモデル(Haiku 5.5)が合うのは、結果を確かめられる大量の作業で、長いエージェントの作業ではない。
21. Claude Code では、Fable 5.2・Opus 5.5・Sonnet 5.5 の effort の既定は medium。medium は「範囲のはっきりした日々の開発」、high は「確かめが大事か、端の場合がありそうな作業」向け。
22. モデルは、会話の途中でなく、会話と会話の間で替える。途中で替えると、キャッシュが効かず、替えた先が前のモデルの考えた跡を読めないことがある。

### 割り当て

| 難しさ | どういう仕事 | モデルと effort |
|---|---|---|
| 低 | 書いてあるとおりにやれば済む(やることが、設計や仕様で1つに決まっている) | Sonnet 5.5 の medium |
| 中 | 決まった枠の中で、自分で選ぶ所がある | Opus 5.5 の medium |
| 高 | 枠そのものを決める(今の仕様・規則・設計に、答えが無い) | Opus 5.5 の high |

- PL の仕事は、中で固定(PL のモデルは利用者が選ぶ。セッションは自分のモデルを替えられない)。
- SE の仕事は、中か高(設計は、少なくとも枠の中で選ぶ仕事)。モデルは Opus のままで、替わるのは effort だけ。
- PG の仕事が高になるのは、設計が足りていないとき。SE が設計を足して、中か低にする。
- Fable が要ると利用者が見た仕事は、利用者が手で上げる。
