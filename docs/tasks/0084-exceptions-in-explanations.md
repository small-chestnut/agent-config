## 難しさ

- SE: 高(ADR 0067-1)

## ゴール

機能や仕組みの説明を求められたときに、Claude が聞かれていない異常系を持ち出さないように、全体の規則を直す。

なぜ: 異常系は、1つの正常系に対して数え切れないほどあり、説明に持ち出すと、どれも同じ重さに見えて話が進まない。利用者は、聞いた正常系の答えにたどり着くまでに、何度も聞き直すことになる。説明で大事なのは分かりやすさで、いつも但し書きで失敗する場合を書くのは、いつも屁理屈を混ぜるのと変わらず、分かりやすい説明にならない。

範囲外: LogiFee など、ほかのリポジトリの CLAUDE.md の規則。理解を確かめる問いに「半分は合っています」と返す癖(利用者が決めた)。

## 壁打ち

### 固まったこと

- 直すのは、全体の規則(`claude/CLAUDE.md` と skill)。
- 範囲は、説明に足させる規則を洗い出してから決める(利用者が選んだ)。
- 消す規則(利用者が決めた): 「手順の説明には、そのとおりにやっても失敗する条件まで入っている」の見出し・「例外は、知らないと操作を誤るときだけ…」・skill `task-team-se` の「失敗する条件」・「伝えるリスクは…」・「規則や設計の理由を聞かれた答えは…」の目指す状態(ADR 0046-2)・「規則・仕様・コードは…AI が保っている」の目指す状態(ADR 0046-3)のうち、AI が規則を目的に照らして直す・消す行。
- 「自分の文の誤りに気づいたら、誤りと認めてから、正しい言い方に言い直している」(ADR 0074-1 の3行のうちの1行)も消す(利用者が決めた)。なぜ: 大事なのは誤りに気づけるかで、誤りと自覚すれば訂正は必ずする。気づくための2行(意味を問われたら誤りを疑う・一般の語を辞書と違う意味で説明しかけたら誤用を疑う)は残す。
- なぜ(ADR 0046-2・0046-3 を消す): AI が規則を自分で目的に照らして直す(自浄する)ことを期待しない。聞かれる前に判断する規則は実際には全く働いておらず、聞かれてから働く規則は、利用者が先に疑いを持った後にしか効かない。

### 見立て(SE が調べたこと)

- 起きた例: LogiFee の会話で、「2026年4〜9月の入出金の消込を完了させられるか」と聞かれ、答え(進められる)の後に、「管理部の答えが『3月の受領請求書は3月31日の買掛金に入れていない』だった場合は別」と、決算書かデータが誤っていた場合の話を添えた。付け直しは後からでもできる、と同じ答えに書いていた。
- 押した規則: `claude/CLAUDE.md` の見出し「手順の説明には、そのとおりにやっても失敗する条件まで入っている」は、下に規則の行が1つも無い。2026-10-21 の書き直し(5a23833)の前は、対象を「利用者がこの後に操作する所(手順・設定・コマンド)があるとき、そのとおりにやっても壊れるもの」に絞る文と例があった。書き直しで絞りが落ち、「失敗する条件」が、どの異常系にも当てはまる読みを許している。
- 入れる向きの規則は、答えに失敗する条件や悪い知らせが無いときにも、Claude にそれを探させる。見つからなければ、ほとんど起こらない小さな可能性からひねり出して入れる(利用者が確かめた理解)。
- 同じことを別の語で言う規則が2つある: 「例外は、知らないと操作を誤るときだけ、答えの後に例外として添えている」は絞る向き、上の見出しは入れる向き。語が「例外」と「失敗する条件」で違うので、別の規則として読める。
- 止めるはずの規則も守られていない: 「伝えるリスクは、自分で確かめた事実があり、最悪の場合に後から直せないかデータが消えるものだけ」。上の例は、確かめていない場合の話で、後から直せるものだった。
- 失敗する条件の規則が初めに入った理由(612ca3b・5a23833): 必要な説明だけに絞ると、そのとおりにやっても壊れる条件まで省かれ、利用者は正しい手順を踏んだまま失敗する。このうち後から直せない壊れ方は、残る規則「伝えるリスクは、…後から直せないかデータが消えるものだけ」と、skill `task-team-se` の「元に戻せない操作には、そう書いている」が受け持つ。
- 「失敗する条件」の語がある規則は2か所: `claude/CLAUDE.md` の上の見出しと、skill `task-team-se` の「同じ操作に、手順・失敗する条件・終わったら利用者が返すことを書いている」。
- 「例外は、知らないと操作を誤るときだけ、答えの後に例外として添えている」も、絞る規則として働いていない。「知らないと操作を誤る」はどの例外にも言えるので、何も絞らない(利用者の指摘)。この行が入ったときに止めたかったこと(理解の確かめに例外で先回りする)は、「合っているかを言い切り、違う所だけを正しく言い直している」が受け持つ。要る警告は、「伝えるリスク」の行が、確かめられる条件(確かめた事実・後から直せないかデータが消える)で受け持つ。
- 利用者の感覚: 文章の量は既に制約されている(結論から・補足は 400 字まで・収まらなければ数ターンに分ける)。その上で、説明の中身に制約をかける規則の必要性を疑っている。
- SE の見立て: 中身の規則には2種類ある。説明に何かを足させる規則(失敗する条件・例外を添える)は、量の制約と同じ所を押し合い、足す物が無いときにひねり出させる。正しさを守る規則(確かめた事実だけを事実として書く・自分の文の誤りを認める)は、量では代わりが利かない。LogiFee の例では、ひねり出した例外は補足の 400 字に収まっていた。

### 説明に足させる規則の洗い出し(利用者が頼んだ)

`claude/CLAUDE.md` の「人間側の最適化」と、上の skill `task-team-se` の1行を見た。足させるものの種類で分けた。

| 規則 | 足させるもの | SE の見立て |
|---|---|---|
| 手順の説明には、そのとおりにやっても失敗する条件まで入っている | 起こるかもしれない別の場合 | 消す。上の見立てのとおり |
| 例外は、知らないと操作を誤るときだけ、答えの後に例外として添えている | 起こるかもしれない別の場合 | 消す。上の見立てのとおり |
| (`task-team-se`)同じ操作に、手順・失敗する条件・終わったら利用者が返すことを書いている | 起こるかもしれない別の場合 | 「失敗する条件」だけ消す。後から直せない操作は、すぐ下の「元に戻せない操作には、そう書いている」が受け持つ |
| 伝えるリスクは、自分で確かめた事実があり、最悪の場合に後から直せないかデータが消えるものだけ | 確かめた事実のリスク | 残す。足させる向きでなく、リスクを確かめた事実で後から直せないものに絞る向き |
| 数式で表せる概念は、数式より先に、値を入れた図で見せている | 同じ答えを図にしたもの | 残す。別の場合を足さず、同じ中身を分かりやすい形で見せる |
| 画面と印刷物に出るものが変わる提案には、補足の文より先に、実装後の図がある | 同じ答えを図にしたもの | 残す。同上 |
| 理解できていない所を確かめる問いは、1行で答えられるものを3〜5個にしている | 利用者への問い | 残す。説明し直すときだけで、別の場合を足さない |
| 根本原因を取り除かない回避策は、暫定対応と言い、恒久対応と並べて出している | もう1つの案 | 残す。回避策を出すときだけで、回避策を直したと取り違えないための案 |
| 規則や設計の理由を聞かれたら、先に利用者のやりたいことを1文で言葉にしている | やりたいことの1文 | 残す。理由を聞かれた問いの答えそのもの |
| 自分の文の誤りに気づいたら、誤りと認めてから、正しい言い方に言い直している | 誤りを認める文 | 残す。正しさを守る規則 |

- 洗い出した結果: 起こるかもしれない別の場合を足させるのは、初めの3か所だけ。ほかは、同じ答えを別の形で見せるか、決まった場面でだけ問い・案・事実を足すもので、屁理屈を混ぜる形にならない。
- 「原則3: AI 側の最適化」にも、報告に足させる規則(テストと lint の結果・画面のスクリーンショット・従わなかった規則)がある。どれもしたことの事実で、起こるかもしれない場合ではないので、見ていない。

### 残すとした3つの規則(利用者が消したいと言った)

- 利用者は、「伝えるリスクは…」「規則や設計の理由を聞かれたら…」「自分の文の誤りに気づいたら…」も、規則として曖昧で理解しがたいので消したいと考えている。
- SE の見立て: 「伝えるリスクは…」は消してよい。この行は、上の3か所が押す向きへの歯止めで、押す規則が消えれば役目がほぼ無くなる。後から直せない操作は、安全の原則(消す前に対象と理由を伝える)と、skill `task-team-se` の「元に戻せない操作には、そう書いている」が受け持つ。
- SE の見立て: 「規則や設計の理由を聞かれたら…」(ADR 0046-2)と「自分の文の誤りに気づいたら…」(ADR 0074-1)は、消すより、利用者に分かる言葉に直す方がよい。どちらも、規則が無かったときに Claude が実際にした、利用者が嫌った振る舞い(規則を理屈で守る答え・誤った説明に説明を重ねる)から入った。
- 利用者の「なぜ」: 大事なのは、理由を聞かれてから規則が要らないと答えることでなく、聞かれる前から、規則が利用者のやりたいことにそぐわないと判断して消せること。
- 利用者の指摘: 聞かれる前に判断する規則(`claude/CLAUDE.md` の ADR 0046-3 の目指す状態)は、実際には全く働いていない。このタスクでも、SE は3つの規則を「残す」と見立て、利用者に指摘されるまで曖昧さを判断できなかった。
- SE の見立て(0046-2): 「規則や設計の理由を聞かれたら…」の2行は消してよい。聞かれてから働く規則で、利用者が先に疑いを持った後にしか効かない。利用者が負いたくない矛盾探しの役を、減らさない。
- SE の見立て(0046-3): 働いていないのは確かだが、消しても、聞かれる前に判断する振る舞いは生まれない。働かない原因の見立ては、照らす相手が「設計や判断の根拠にした規則」に限られ、説明の形を決める規則は根拠に挙がらないので照らされないこと。もう1つは、照らすときに目的の言葉と規則の言葉が合うかで見て、規則が実際に何を起こすかで見ないこと(例: 「失敗する条件」の見出しは、目的「判断と操作を誤らない」の下にあり、言葉の上では合って見える)。説明の例外の話から離れるので、別のタスクにするのがよい。
