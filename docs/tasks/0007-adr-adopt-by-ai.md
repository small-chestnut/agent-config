# ゴール

agent-config の目的(新しいシステムを開発するとき、そのリポジトリの CLAUDE.md を作りこまなくても、agent-config の設定を読めば、すぐに AI 駆動開発に最適な環境ができること)と、今の設定のずれが見つかったら、PL は、やるかどうかを利用者に聞かずにタスクにして回す。ADR の採用も利用者に聞かず、QA の設計レビューで採用にする(ADR 0007-1)。利用者は、終わったタスクの報告で、採用した ADR を知る。

利用者の理由:「乖離があれば、タスクを立てればいいよね？」「で、そのときに、私にやるべきかどうかなんて聞かなくていいよね？」「AI駆動開発　"AI"ですよ？人間じゃなくて」「なら、俺に聞かなくていいよね」。ADR の採用も聞かなくてよいかには「採用も含む」。

範囲外: 原則1(削除・本番環境・permissions とフックの変更)の決まりと、本番環境に触る作業を PL に戻す決まりを変えること。

# 受け入れ条件

1. このリポジトリの CLAUDE.md に、README の目的とのずれが見つかったら、PL がやるかを利用者に聞かずにタスクにして回す行がある。
2. `task-team-lead` に、リポジトリの決まりで利用者に聞かずに回すタスクは、聞かずに番号を振り、次に利用者が書いたターンでチームを起こす行と、起こすまでのタスクを報告に並べる行がある。
3. `task-team-lead` に、利用者に ADR を採用するかを聞く行と、「利用者の判断待ち」の行が無く、終わったタスクの報告に、そのタスクで採用した ADR のパスと「決めたこと」の1行を入れる行がある。
4. `task-team-se` に、ADR を書いたらステータスを「利用者の判断待ち」にしてターンを終える行と、PL の返事で状態を変える行が無く、設計レビューで ADR に指摘が来たら、直して状態を「採用」か「却下」にする行がある。
5. `task-team-se` に、採用中の ADR とぶつかるなら、決定を変えるかを利用者に聞く行が無く、置き換える ADR を提案する行がある。
6. `task-team-qa` に、設計のレビューで指摘が無い ADR の状態を「採用」にする行がある。
7. グローバルの CLAUDE.md(`claude/CLAUDE.md`)原則3 の ADR の行が、task-team の SE が提案し QA が採用してから実装する、になっている。
8. 採用する人を決めた行(上の 3・4・6・7 と README)に `(ADR 0007-1)` が付き、ADR 0004-1 の書く対象と task-team を通さない会話の行は `(ADR 0004-1)` のまま。`docs/adr/0004-1-adr-driven.md` は変わっていない。
9. README の「セッションの役割分割」の節に、ADR を QA の設計レビューが採用にする意図と、目的とのずれを聞かずにタスクにする意図と、利用者の理由がある。
10. `docs/用語集.md` に「利用者の判断待ち」の行が無い。
11. 原則1(グローバルの CLAUDE.md の原則1・`task-team-lead` の本番環境と原則1 に触れる指摘を利用者に聞く行・`task-team-pg` の外部のシステムの設定を直前に確かめる行)は変わっていない。
12. どの SKILL.md の箇条書きの行も 60 字以内(`python -m unittest discover -s tests` が通る)。

# 設計

決定は [ADR 0007-1](../adr/0007-1-adr-adopt-by-qa.md)(採用。PL が利用者に代わって返した)。置き換えるのは [ADR 0004-1](../adr/0004-1-adr-driven.md) の1 のうち、誰が採用にするかだけ。0004-1 の状態は変えない(ADR 0006-2)。する人は、どの手順も PG。用語は [docs/用語集.md](../用語集.md)(この設計と同じコミットで SE が「次に回すタスク」を足し、「利用者の判断待ち」を消した)。

出典: 関係者が同意したら「採用」にするのは、Michael Nygard「Documenting Architecture Decisions」(https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)。
