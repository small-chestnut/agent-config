# ゴール

skill `task-team-lead` に、利用者の依頼のうち決まった動きに戻すもの(エラーや、仕様・規則と違う動きを直す)だけをすぐにタスクにし、ほかは「タスクにして」と言われるまで壁打ちにする規則と、壁打ちで PL がアイデアが命題に効くか逆効果かを根拠つきで言い切る規則と、壁打ちの後に SE へ渡すタスクの文を PL がまとめる規則があり、その理由として利用者が言ったことが README に残っている。

範囲外: skill `task-team-se`・`task-team-qa`・`task-team-pg` と `claude/CLAUDE.md`(SE・QA は今までどおり要件の是非を問わない)、task-team を通さない1つだけのセッションでの壁打ち、命題が書かれていないリポジトリに命題を書き足すこと、PL が見つけた README の目的とのずれを聞かずにタスクにする今の規則。

# 受け入れ条件

1. skill `task-team-lead` の「# 原則1: 統括」のすぐ下、「## 目的: タスクが SE → PG → QA の順で進み、PL は設計も実装もしない」より前に、「## 目的: 命題に逆効果な変更を、利用者の理解が曖昧なまま、チームが作り始めない」がある。
2. その目的の下に「### 目指す状態: チームは、決まった動きに戻す依頼と、「タスクにして」の後にだけ起きている」があり、その下に次の5行がある。
   - エラーや、仕様・規則と違う動きを直す依頼は、すぐにタスクにしている。
   - ほかの依頼は、命令の形でも、「タスクにして」と言われるまで壁打ちにしている。
   - 「タスクにして」と言われたら、壁打ちの途中でもすぐにタスクにしている。
   - 逆効果だと思うタスクには、利用者への返答に懸念を1行だけ添えている。
   - 壁打ちの間は、チームを起こさない。
3. 同じ目的の下に「### 目指す状態: 壁打ちで、利用者は、アイデアが命題に効くか逆効果かを、根拠つきで知っている」があり、その下に次の4行がある。
   - 命題は、`docs/概要.md` の冒頭か、CLAUDE.md が書くか指す目的。
   - 命題が見つからなければ、壁打ちの前に利用者に聞いている。
   - 効くか逆効果かは、調べた根拠をつけて言い切っている。
   - やるかを決めるのは利用者。
4. 「### 目指す状態: 受け渡しの記録が、タスクごとに1つのファイルにある」の節の、「- PL の答えは、タスクの文が受けている PL の返答。無ければ渡さない。」の次に、次の4行がある。
   - 壁打ちの後のタスクの文は、利用者が決めたことを PL がまとめた文。
   - まとめには、利用者が訂正・撤回した認識を入れない。
   - まとめの中の利用者の「なぜ」は、利用者の言葉のまま引く。
   - 壁打ちの後の PL の答えは、まとめに残した事柄に答えた返答だけ。
5. README の「## セッションの役割分割(PL / SE / PG / QA)の意図」の節に、壁打ちとタスクにする分け目の項目があり、利用者の理由が言葉のままあり、そのほかの理由は無い。
6. 用語集に「壁打ち」「命題」「タスクの文」の行があり、「PL の答え」の行の意味に壁打ちの後のものが入っている。
7. skill `task-team-lead` の箇条書きの行は、どれも60字以内(既にあるテスト `test_どのSKILL_mdの箇条書きの行も60字以内` が通る)。
8. 上に挙げた行のほかの行は、skill `task-team-lead`・README・用語集で変わっていない。

# 設計

書き換える所(skill `task-team-lead` の原則1 と、その「受け渡しの記録が、タスクごとに1つのファイルにある」の節、README の役割分割の意図の節)と、その見出しに ADR の番号は付いていない。壁打ちの規則は skill の数行で決まり、後から書き換えで変えられるので ADR は書かない。設計レビューは無く、PG に回す。

skill `task-team-lead` は決まりの文書なので、それ自体が仕様で、別の仕様は直さない。足す目的と目指す状態の文は、skill `prompt-structure` の「原則・目的・目指す状態は、利用者が合意したものだけ」のとおり、SE が利用者に確かめて決めた。新しい名前「壁打ち」「命題」と、意味を決めた「タスクの文」を用語集に足す。

利用者が SE の問いに答えた理由(README に入れる): 壁打ちの後に渡す発言を言葉のままにするかと聞いたときの答えが「「言葉のまま」というのが、ちょっと曖昧で不安　壁打ちの過程で訂正した、私の誤った認識まで入る必要はないように思うのだが」。そのあと、渡すのは PL がまとめ直した文にする、外した認識に答えた PL の返答も外す、まとめは利用者に見せずにチームを起こす、と答えた。

## 手順1: skill `task-team-lead` に壁打ちの目的を足す(する人: PG)

`claude/skills/task-team-lead/SKILL.md` の「# 原則1: 統括」の行と、その次の空行のあとに、次の行をそのとおりの文で足す。足した後ろに空行を1つ置き、「## 目的: タスクが SE → PG → QA の順で進み、PL は設計も実装もしない」が続くようにする。

```
## 目的: 命題に逆効果な変更を、利用者の理解が曖昧なまま、チームが作り始めない

### 目指す状態: チームは、決まった動きに戻す依頼と、「タスクにして」の後にだけ起きている

- エラーや、仕様・規則と違う動きを直す依頼は、すぐにタスクにしている。
- ほかの依頼は、命令の形でも、「タスクにして」と言われるまで壁打ちにしている。
- 「タスクにして」と言われたら、壁打ちの途中でもすぐにタスクにしている。
- 逆効果だと思うタスクには、利用者への返答に懸念を1行だけ添えている。
- 壁打ちの間は、チームを起こさない。

### 目指す状態: 壁打ちで、利用者は、アイデアが命題に効くか逆効果かを、根拠つきで知っている

- 命題は、`docs/概要.md` の冒頭か、CLAUDE.md が書くか指す目的。
- 命題が見つからなければ、壁打ちの前に利用者に聞いている。
- 効くか逆効果かは、調べた根拠をつけて言い切っている。
- やるかを決めるのは利用者。
```

失敗する条件: main に入った他のタスクの変更で「# 原則1: 統括」の下が変わっていたら、main を取り込み、原則1 の最初の目的の前に同じ行を入れる。原則1 が無ければ PL に知らせて止める。

## 手順3: README に理由を足す(する人: PG)

`README.md` の「## セッションの役割分割(PL / SE / PG / QA)の意図」の節で、「- **PL は、利用者のタスクの文に加えて、タスクの文が受けている PL の答えを、言葉のまま SE に渡す**。」の項目(最後の行は「…用語集自体を廃止するようなタスクを作っていたと思うんだけど」)の次に、次の項目をそのとおりの文で足す。

```
- **利用者の依頼は、決まった動きに戻すもの(エラーや、仕様・規則と違う動きを直す)だけをすぐにタスクにし、ほかは「タスクにして」と言われるまで壁打ちにする**。
  壁打ちでは、PL はアイデアが命題(`docs/概要.md` の冒頭か、CLAUDE.md が書くか指す目的。agent-config では冒頭の「目的: 」の行)に
  効くか逆効果かを、調べた根拠をつけて言い切る。壁打ちの間はチームを起こさず、やるかは利用者が決める。
  「タスクにして」と言われたら、壁打ちの途中でもすぐにタスクにし、逆効果だと思えば懸念を1行だけ添える。
  壁打ちの後のタスクの文は、利用者が決めたことを PL がまとめた文にし、利用者が訂正・撤回した認識と、それに答えた PL の返答は SE に渡さない。
  まとめの中の利用者の「なぜ」は、言葉のまま引く。
  利用者の理由は「一旦そこで壁打ちを挟まないと、私自身の理解が曖昧なままタスクにして、なおかつ、それがAI駆動開発に逆効果であるにもかかわらずタスクとして走り始めてしまうのが嫌なんだ」。
  「タスクにして」と言うまでは全部アイデアとして扱う案について「2. にしたほうが、あなたが導線を混乱せずに済むように思えるが、どうだろうか」
  「要件のように命令形で私が言った場合であっても、あなたが「いや、この要件は、リポジトリの命題に沿っていない」という私見を述べることができるよね」。
  すぐにタスクにする道について「明示的に即タスクにする導線も欲しいんだよな」「もう壁打ちはいらない、いいからあなたの裁量でやりなさい、みたいなケース」
  「もしこれが業務システムであるなら、「この画面で出たエラーを直して」というのは、もはやあなたの裁量でやってほしい確定タスクになるわけだよね」。
  まとめにする理由は「「言葉のまま」というのが、ちょっと曖昧で不安　壁打ちの過程で訂正した、私の誤った認識まで入る必要はないように思うのだが」
```

失敗する条件: その項目が動いたか消えていたら、main を取り込み、同じ節の「**ターンの受け渡しは、PL を通さず子セッションどうしが SendMessage でする**」の項目の次に入れる。節が無ければ PL に知らせて止める。

## 手順4: 用語集に足す・直す(する人: PG)

`docs/用語集.md` の表で、「| PL の答え |」の行を、次の4行に、そのとおりの文で置き換える。

```
| 命題 | — | — | リポジトリの目的(システムを作る理由)。`docs/概要.md` の冒頭か、CLAUDE.md が書くか指す目的。agent-config では README の「目的: 」の行 |
| 壁打ち | — | — | 利用者の依頼のうち、決まった動きに戻すもののほかを、「タスクにして」と言われるまで PL と話すこと。PL はアイデアが命題に効くか逆効果かを根拠つきで言い切り、チームは起こさない |
| タスクの文 | — | — | PL が SE に渡す利用者の依頼。壁打ちが無ければ利用者の言葉のまま、壁打ちの後は利用者が決めたことを PL がまとめた文 |
| PL の答え | — | — | 利用者のタスクの文が受けている PL の返答(壁打ちの後は、まとめに残した事柄に答えた返答)。PL が言葉のまま、決定ではなく材料だと添えて SE に渡す |
```
