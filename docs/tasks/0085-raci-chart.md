## ゴール

task-team の作業ごとの役割の表を、利用者の列を足した RACI チャートにし、話題をいくつのタスクに分けるかを決める役割を足す話。

範囲外: 今ある作業の、受け持つ役割を変えること。

## 壁打ち

### 固まったこと

- 利用者の発端の文: 「私とPL/SE/PG/QAセッションの関係　これをRACIチャートにするといいのでは？と思ったのだけど」
- 利用者は、ほかの AI に作らせた RACI チャート(利用者を全工程の A に置く表)を例として見せた。その表が今のやりたいこととずれていることは、利用者も分かっている。
- 表には、利用者の列がある(発端の文が「私と」の関係を言う)。
- なぜ: AI のセッションが受け持ちを取り違えないように、各セッションが自分の役割を分かっているようにするため。
- 事実(利用者): LogiFee では、タスクが適切な大きさに分けられず、1つのタスクで終わらないことがしばしばあった。
- 根本原因: タスクの大きさを決める役割と基準が、今の規則に無い。大きすぎる仕事への今の規則は、分けることでなく、SE を Fable にすること。
- 話題をいくつのタスクに分けるかは、SE が仕様とコードを読んだ後に判断し、分けたタスクのチームは PL が作る(PL は話題の1文しか持たず、大きさを見積もる材料が無いため)。
- 役割の skill から、RACI チャートが既に言っている受け持ちと重なる記述を消す(利用者の依頼)。
- 誰が何を受け持つかは、RACI チャートで言い切れる。役割の skill に残るのは、受け持った作業のやり方・基準・知らせる時と、セッションの立て方と知らせ方。
- 利用者は、設計に進めると言った。
- 利用者は、SE の skill に足す目指す状態「1つのタスクは、SE・PG・QA のどれも1つの会話で終えられる大きさ」の文に合意した。
- 利用者だけがする作業は、どの skill にも RACI チャートにも書かない(利用者。skill を読むのは AI のセッションなので、AI が関わらない作業は書いても振る舞いを変えない)。

## 受け入れ条件

1. skill `task-team` の役割の表は、利用者・PL・SE・PG・QA の列に R・A・C・I・「-」を置く RACI チャートである。
2. RACI チャートのどの行にも、A がちょうど1つある。
3. RACI チャートの「話題をいくつのタスクに分けるかを決める」行で、SE が A/R である。
4. 役割の skill に、RACI チャートと重なる受け持ちの行(設計の「消す行」)が無い。
5. SE は、設計の最初に、タスクが SE・PG・QA のどれも1つの会話で終えられる大きさかを見積もり、収まらなければ話題を2つ以上のタスクに分ける。
6. PL は、SE が分けたタスクを、SE が書いた要件と「なぜ」をゴールの節に写した未着手のチケットにし、1つ前のタスクを終えてから、聞かずに進めるタスクとしてチームを作る。
7. Fable にする大きさの条件は、タスクに分けても1つの会話に収まらないと見込める仕事である。
8. どの SKILL.md の箇条書きの行も60字以内である。
9. RACI チャートに、AI のセッション(PL・SE・PG・QA)がどれも「-」の行が無い。

## レビュー

### 設計レビュー(1回目)

- 設計: 分けたタスクのチケットはゴールの1行だけで、壁打ちで固まったそのタスクの要件が、今のチケットを消すと失われる。次の SE は壁打ちをしないので、その要件を知らずに設計する(SE に足す7行・PL に足す3行・ADR 0085-2)。
- 設計: 表の「ADR の状態の行を書き換える」で A が SE だが、ADR 0007-1 は、指摘が無ければ QA の設計レビューが採用にすると決めている。表のとおりだと SE が自分で採用を決められる。
- 設計: 表の「子セッションのモデルと effort を、割り当ての範囲で替える」で QA が「-」だが、QA は SE を Fable にするよう PL に知らせる(ADR 0067-2・skill `task-team-qa`)。QA が知らせたときに A が SE なのも、ADR 0067-2 の流れと合わない。
- 設計: 表の「目的と「なぜ」を決める」の利用者 A・SE R は、R の定義(作業をする役割)では SE が決めて利用者が承認するとも読め、二通りに読める。ADR 0063-1 では決めるのは利用者だけ。
- 設計: 表の「要件と設計を決める」の PG C は、C の定義(作業の前に意見を聞かれる)に当たる規則が無い。PG の「設計への問い」は設計の後に PG から出すもの。
- ADR の番号: 「PL が振る」を消して表の行「話題をタスクにし(番号を振る)」だけに残すのに、その行に、PL が番号を振ると決めた ADR 0004-1 が付いていない。
- ADR 0085-1・0085-2 は、上の指摘があるので状態を「提案」のまま返す。

### 設計レビュー(1回目)への直し

- 分けたタスクの要件: SE は分けたタスクごとに見出しを立て、ゴールの1文と、壁打ちで固まった要件と「なぜ」を書き、PL はそれをそのチケットのゴールの節に写す(SE の4・5行目、PL に1行足して4行)。ADR 0085-2 の決めたことにも足した。
- ADR の状態の行: QA を A/R、SE を R にした。
- モデルと effort: 「PG と QA のモデルと effort を替える」(SE が A/R)と「SE を Fable に替える」(PL が A/R、SE と QA が C)の2行に分けた。C の定義を「作業の前に意見を出す役割」にした。
- 目的と「なぜ」: 決めるのは利用者だけで AI のセッションが関わらないので、表に載せない(利用者の依頼)。SE が聞く所は「目的・「なぜ」・業務の事実を利用者に聞く」(SE が A/R、利用者が C)の1行にした。
- 要件と設計の PG: 「-」にした。PG の「設計への問い」は、PG の skill の行に残る。
- ADR 0004-1: 「話題をタスクにし(番号を振る)」の行に足した。
- ほかに、利用者の依頼で「割り当てより上のモデルにする」の行を表に載せないことにした(D5 は消したまま)。表は18行。
