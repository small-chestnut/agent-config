## 壁打ち

### 固まったこと

- 利用者の発端の文: 「私とPL/SE/PG/QAセッションの関係　これをRACIチャートにするといいのでは？と思ったのだけど」
- 利用者は、ほかの AI に作らせた RACI チャート(利用者を全工程の A に置く表)を例として見せた。その表が今のやりたいこととずれていることは、利用者も分かっている。
- 表には、利用者の列がある(発端の文が「私と」の関係を言う)。
- なぜ: AI のセッションが受け持ちを取り違えないように、各セッションが自分の役割を分かっているようにするため。
- 事実(利用者): LogiFee では、タスクが適切な大きさに分けられず、1つのタスクで終わらないことがしばしばあった。
- 根本原因: タスクの大きさを決める役割と基準が、今の規則に無い。大きすぎる仕事への今の規則は、分けることでなく、SE を Fable にすること。
- 話題をいくつのタスクに分けるかは、SE が仕様とコードを読んだ後に判断し、分けたタスクのチームは PL が作る(PL は話題の1文しか持たず、大きさを見積もる材料が無いため)。
- 役割の skill から、RACI チャートが既に言っている受け持ちと重なる記述を消す(利用者の依頼)。
- 誰が何を受け持つかは、RACI チャートで言い切れる。役割の skill に残るのは、受け持った作業のやり方・基準・知らせる時と、セッションの立て方と知らせ方。
- 利用者は、設計に進めると言った。
- 利用者は、SE の skill に足す目指す状態「1つのタスクは、SE・PG・QA のどれも1つの会話で終えられる大きさ」の文に合意した。
- A は、成果物とタスクが正しく終わることに最後まで責任を負い、前提がそろっているかを確かめて R に任せ、R の作業を承認する役割(利用者が示した Wikipedia の定義)。SE が前に書いた凡例「A は作業の結果を最後に決める役割」は、この定義と違っていた。
- 1つの行で、1つの役割に付ける文字は1つだけにする(A/R のような兼務を置かない)。なぜ: 兼務は役割の分担を曖昧にし、AI の逃げ道になる(利用者)。
- RACI チャートの行は、タスクの中で各役割が何をするかで立てる。利用者の許可が要るかどうかと、知らせ方は、行にしない(利用者)。
- 行の名前は、IT の用語にする(要件定義・設計・実装)。
- 作業が終わったときに誰に知らせるかは、表の I で表し、役割の skill の同じことを言う行は消す。残すのは、知らせ方と、作業の途中の知らせ(利用者を待つとき)。
- 進み具合を見せるのは、タスクの外の作業で、PL の役割。SE は、そのタスクの作業に集中する(利用者)。サブタスクの図を SE が描く決まり(ADR 0056-4 のその部分)は撤回する。
- モデルと effort を替える行(PG と QA のモデル・SE を Fable に)は、表に置かない。いつ・何を基準に替えるかの規則が skill に残り、誰が替えるかもその規則が言っているため(利用者の問い)。
- かんばんのカードのサブタスクの数は、外さない(外しても PL の負荷が変わらないため。利用者)。
- RACI チャートの行は、2つ以上の役割が関わる、タスクの中の作業だけにする。1つの役割だけがして利用者は結果を見るだけの作業(かんばん・マージ・チームを作る・閉じる)は、行にしない(利用者)。
- タスクの分け方の A は QA(PL は中身を読まないので、読まずに通すだけになる。ADR 0007-1 の捨てた案1 と同じ理由)。QA は設計レビューで分け方も見る。
- 設計レビューの指摘を直した後の ADR の採用は、SE でなく QA がする(このタスクで、SE が自分で採用にした直しの誤りが、実装の後の実装レビューで見つかった)。

| 作業 | 利用者 | PL | SE | PG | QA |
|---|---|---|---|---|---|
| 話題をいくつのタスクに分けるかを決める | I | I | R | - | A |

### 設計書のテンプレート(0085 の中でする)

SE が書いて PG と QA に渡す設計書(チケット)の形を、1つのテンプレートに固定する話。

- なぜ(利用者): チームは、コンテキストを節約し、役割ごとに専門の仕事をさせるために、セッションを分けている。そのため、意図が伝わるかは設計書の質で決まる。SE が利用者と壁打ちして、理由も含めて合意した設計の意図が、後のセッション(PG・QA)で漏れるのは受け入れられない。
- 要件: SE が利用者と壁打ちして決めた内容と「なぜ」が、PG と QA に届く。
- 要件: テンプレートの構成は、SE が組み立てず、定石(スペック駆動開発の、要件・設計・作業の一覧)の構成を使う。定石にもっと良い構成があれば、それを採用する(利用者)。
- 分かっている事実: 今の PG が読む節は「ゴール」「受け入れ条件」「設計」で、「壁打ち」の節は入っていない。
- 終わったタスクのチケットは、今のまま消してよい(利用者は、後で見返さない)。
- 分かっている事実: 今は、チケットの形を SE の skill の規則の文(節の並び16行・進捗の形19行)で決め、設計の節の中の見出しは決まっていない。
- 分けずに 0085 の中でする(利用者: 文脈を持っている今やる)。SE が分けたタスクにして PL に頼んだ分は、取り消す。
- 利用者が、設計書に要るかが分からないと挙げた欄: PC・利用者待ち・難しさ・develop へのマージ。
- 調べた事実: 「PC: 」と利用者待ちの行を読むのは、かんばんと PL。難しさを読むのは、SE 自身と、Fable に替えるときの PL。PG と QA の skill は、どれも読むと書いていない。develop へのマージの欄は、全体の skill に無い。

- SE の skill に足す目指す状態の文は、利用者が決めた「要件と意図が、正確に届いている」。
- 利用者は、前に決めた「レビューは設計と実装に1回ずつ。何往復もするのは本末転倒」(ADR 0067-3・0069-2)を撤回し、指摘の直しを QA が見る形を選んだ。設計レビューの指摘の直しにも、実装レビューの指摘の直しにも当てる。

- 無限のレビューにしない(利用者)。直しの確かめでは、新しい指摘を足さず、前の指摘が直ったかだけを見て、回数は1回だけ。残った指摘は、SE が利用者に聞く。

1. QA の指摘を「直さないと通せないもの」と「直さなくてよいもの」に分ける決まりを足すか(利用者に聞いた。答えはまだ)。

## 受け入れ条件

1. skill `task-team` の RACI チャートは、利用者・PL・SE・PG・QA の列を持ち、どのマスも R・A・C・I・「-」のどれか1文字である。
2. RACI チャートのどの行にも、A がちょうど1つ、R が1つ以上ある。
3. RACI チャートの行は、話題をタスクに分ける・要件定義・設計・実装の4つである。
4. A は、R の作業を承認したら、その行の I のセッションに知らせる。
5. SE は、チケットを、skill `task-team-se` のテンプレートの形で作る。
6. SE は、利用者と合意した要件を、1つずつ番号と「なぜ」と受け入れ条件を付けて、「要件」の節にだけ書く。
7. 設計の節の、置くファイルと手順の行と、テスト一覧のテストは、元の要件か受け入れ条件の番号を持つ。
8. PG は、チケットの「ゴール」「要件」「設計」の節を読み、設計の行が要件や「なぜ」と食い違う所で手を止める。
9. QA は、設計レビューで、どの要件にも番号で指す設計の行かテストがあるかを見て、実装レビューで、作ったものを設計の節と要件の節に照らす。
10. SE は、分けたタスクを要件の節に番号と「なぜ」を付けて書いて QA の設計レビューに出し、PL は、タスクを終えるときに、その要件を写した未着手のチケットを作る。
11. SE は、サブタスクの進み具合を図に描かない。
12. レビューの指摘を SE か PG が直したら、QA が、前の指摘が直ったかだけを1回確かめてから、ADR を採用にするか実装を通し、残った指摘は SE が利用者に聞く。
14. チームの開始と終了、main へのマージとインストールは、PL だけがする。
13. どの SKILL.md の箇条書きの行も60字以内である。
