# ゴール

task-team の skill(`task-team-lead`・`task-team-se`・`task-team-pg`・`task-team-qa`)を、コードの無いタスク(情シス的な作業、特定のリポジトリに紐づかないタスク)でも同じ仕組みで回せるようにする。

# 要件

## ゴール

README と skill 3つ(lead・se・pg)に、コードの無いタスクの受け皿・読み替え・外部のシステムの設定を変える操作の扱いが書いてあり、`python -m unittest discover -s tests` が通る。

## 範囲外

- `task-team-qa` の skill(利用者の決定: 足さない)。
- 記録だけを置くリポジトリ(例: `tasks`)そのものを作ること。
- main へのマージ・push・`install.ps1 -Yes`(PL がする)。
- フックとテストのコードを変えること。

## 受け入れ条件

1. README の「セッションの役割分割」の節に、リポジトリに紐づかないタスクの受け皿が書いてある。
2. `task-team-se` と `task-team-pg` に、目指す状態「コードの無いタスクも、同じ節と順で回っている」と読み替えの3行がある。
3. `task-team-se` の同じ目指す状態の下に、手順を設計に書く1行がある。
4. `task-team-pg` に、目指す状態「外部のシステムの設定は、利用者が直前に認めた操作でだけ変わっている」と2行がある。
5. `task-team-lead` に、記録だけのリポジトリでの子の起こし方と、main への直接コミットの2行がある。
6. どの SKILL.md の箇条書きの行も 60 字以内(`python -m unittest discover -s tests` が通る)。
7. `task-team-qa` の SKILL.md は変わっていない。
8. コミットメッセージの本文に、利用者の理由の文がそのままある。

# 設計

## 決めたこと(利用者の決定)

- 記録だけのリポジトリでは、記録を main に直接コミットする。子が同じフォルダで動くため。
- PG の規則の対象は、外部のシステムの設定を変える操作すべて(元に戻せるかを PG に判断させない)。
- QA の skill には足さない。
- 読み替えは、SE と PG の原則1に新しい目指す状態を足し、その下に置く。文は下のとおり(利用者が合意した文)。
- SE に、設計の節に手順を操作ごとに書く1行を足す(QA が手順をレビューできるように)。

## 変えるファイル

すべて既にあるファイル。新しいファイルは作らない。用語集・ADR・`docs/概要.md` はこのリポジトリに無く、作らない(README の「〜の意図」の節が決定の置き場)。

### `claude/skills/task-team-se/SKILL.md`

「### 目指す状態: 記録は、決まった形で1ファイルにある」の箇条書きの後(「### 目指す状態: 要件は、…」の前)に、次の節を挟む:

```
### 目指す状態: コードの無いタスクも、同じ節と順で回っている

- コードの無いタスクでは、実装を手順の実行と読み替えている。
- テストを確認手順と読み替え、手順を実行する前に書いている。
- 受け入れ条件を、確認して言い切れる文と読み替えている。
- 設計の節には、実行する手順を操作ごとに書いている。
```

### `claude/skills/task-team-pg/SKILL.md`

1. 「### 目指す状態: 読むものは、設計が指すものだけ」の箇条書きの後に、次の節を挟む:

```
### 目指す状態: コードの無いタスクも、同じ節と順で回っている

- コードの無いタスクでは、実装を手順の実行と読み替えている。
- テストを確認手順と読み替え、手順を実行する前に書いている。
- 受け入れ条件を、確認して言い切れる文と読み替えている。
```

2. 「### 目指す状態: 設計を変える判断は、PG がしていない」の箇条書きの後に、次の節を挟む:

```
### 目指す状態: 外部のシステムの設定は、利用者が直前に認めた操作でだけ変わっている

- 外部のシステムの設定を変えるのは、設計レビューを通った手順にある操作だけ。
- その操作は、実行の直前に利用者に1回確かめてからしている。
```

### `claude/skills/task-team-lead/SKILL.md`

1. 「- SE は `use_worktree: true`、`branch_name` にタスク名。」の次の行に足す:

```
- 記録だけのリポジトリでは、SE も `use_worktree: false` で、PL のフォルダを `cwd` にする。
```

2. 「- QA が実装を通したら、CLAUDE.md 原則1 のとおりマージして push、できないリポジトリでは PR。」の次の行に足す:

```
- 記録だけのリポジトリでは、記録を main に直接コミットしている。
```

### `README.md`(「## セッションの役割分割(PL / SE / PG / QA)の意図」の節)

1. 冒頭の段落の1文目を次に替える(2文目「利用者(PM)がタスクを PL に渡し、…」はそのまま):

```
skill `task-team-lead`・`task-team-se`・`task-team-pg`・`task-team-qa` は、1つのリポジトリへのタスクを、
役割ごとに分けたセッションで回す手順。コードを書くタスクも、コードの無いタスク(情シス的な作業など)も同じ仕組みで回す。
```

2. 「- **1リポジトリに PL が1つ**。…」の箇条の後に、次の3つの箇条を足す:

```
- **受け皿は、タスクが触るリポジトリ**。特定のリポジトリに紐づかないタスクは、記録だけを置く専用の
  git リポジトリ(例: `tasks`)を1つ作り、そこに PL セッションを開く。コードを書かないので worktree は要らず、
  子3つは `use_worktree: false` で PL と同じフォルダに起こす。子が同じフォルダで動くので、記録は main に
  直接コミットする。子はこの決まりを読まないので、そのリポジトリの CLAUDE.md にも書いておく
- **コードの無いタスクは、言葉を読み替えて同じ節と順で回す**。実装 = 手順の実行、テスト = 確認手順
  (手順を実行する前に書く)、受け入れ条件 = 確認して言い切れる文。SE は実行する手順を操作ごとに設計に書き、
  QA がそれを設計レビューで見る
- **外部のシステムの設定を変える操作は、PG が実行の直前に利用者に確かめる**。アカウント・DNS・課金などの
  設定は git の外にあり、元に戻せないことがある(CLAUDE.md 原則1 の延長)。PG がするのは、QA の設計レビューを
  通った手順にある操作だけ
```

## コミット

1コミットにする: 上の4ファイルと、この記録の「実装」の節。

- 件名: `task-team の skill を、コードの無いタスクでも回せるようにする`
- 本文の1段落目に、利用者の理由をそのまま書く:「この仕組み自体は応用が利く。情シス的な作業や、特定のリポジトリに紐づかないタスクも管理できると良い」
- 本文の2段落目に、上の「決めたこと(利用者の決定)」を短く書く。

フック(`ask_removable_words.py`)が足した行に語を消すよう問い返してくるが、skill の文は利用者が合意した文なので変えない。
