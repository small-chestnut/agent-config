## ゴール

Claude が、1つの事実(移行の範囲の日付など)を表す値を、機能を足すたびに別々のファイルへ直に書き、事実が変わると全部を探して直すことになる。これを、全体の CLAUDE.md(`claude/CLAUDE.md`)か skill の規則で起きないようにする。

タスクの文(利用者の言葉のまま): 「なんでさ、こう　あなたは「汎用化」ってのが下手くそなんだろうね？ハードコードなんて、プログラム覚えさせられるときに、まずモジュールの汎用性を落とすからやるなって言われるのにな」

起きたこと(PL が利用者の画面から書いた): logifee の七海の取り込みスクリプトで、Claude が、移行の範囲の日付(帳簿の開始日 2026-04-01・消込を終える日 2026-09-30・移行日 2026-10-01 など)を、機能を足すたびに別々のファイルへ直に書いていた。17ファイル・66行にあり、同じ日付が3つのファイルに別々にあるものや、引数で渡せる所と定数の所が混ざったものもある。範囲が1か月ずれるだけで、全部を探して直すことになる。全体の CLAUDE.md(`claude/CLAUDE.md`)には、値を直に書かず1か所で決める規則が無い(PL が grep で確かめた)。

範囲外(案。壁打ちで確かめる): LogiFee の取り込みスクリプトの日付を1か所にまとめること(LogiFee のタスクにする)。

## 壁打ち

### 根本原因(SE が LogiFee のコードと git の履歴で確かめた・2026-11-13)

1. 同じ値の重なりが、1つのセッションの中でなく、セッションをまたいで生まれている。`scripts/lib/nnm_import2551/` の日付を持つ8ファイルは、7つの管理番号(2551・2756・2759・2777・2864・2868・2871)で、2026-10-30〜11-12 に別々のセッションが足した。どのセッションも、自分の作るファイルの中では値に名前を付けている(`END = '2026-09-30'`・`LEDGER_START = '2026-04-01'`・`CUTOVER = '2026-10-01'` など)。1ファイルだけを見れば「マジックナンバーを避けて名前付き定数にする」という定石を守っていて、重なりは、ファイルをまたいで見たときにだけ見える。
2. 新しいファイルを書くセッションが、同じ値が既にどこにあるかを探す規則が無い。全体の CLAUDE.md は、読むものをモジュールと import でたどったファイルに絞り、全体の検索を「変更の影響」「モジュールの外の原因や呼び出し元」と「新しい仕組みを作る前」(ADR 0068-1)に絞っている。ADR 0068-1 の「新しい仕組み」は機能・データ・処理の種類で、値は入っていない。だから、`clearing_csv.py` に `END` があっても、後から `offbook_clearings.py` を書くセッションは探さず、同じ `END = '2026-09-30'` をもう一度書いた。
3. 値の元が、コードでなく文書(skill の `.claude/skills/nnm-import/七海国際物流のデータ.md` の「期首 2026-04-01・移行日 2026-10-01」と、チケットの文)にある。`precheck_csv.py` は `CUTOVER = '2026-10-01'   # 七海の移行日(.claude/skills/nnm-import/七海国際物流のデータ.md)` と、元の文書を指したうえで値を写している。各セッションは、文書とチケットに書かれた日付を、そのままコードへ写した。
4. 同じ事実に、名前が5つある。帳簿の開始日は `LEDGER_START`・`FISCAL_START`(`datetime.date(2026, 4, 1)`)・`MARKS_FROM`・引数の既定値 `ledger_start='2026-04-01'`・`start='2026-04-01'`、消込を終える日は `END`・`DUE_END`。名前が違うので、grep で1つを見つけても、ほかに当たらない。
5. 1か所で決める仕組み(設定のモジュール・コマンドの引数)が、途中まであって広がっていない。`main.py` には `--cutover-date`(既定値 `2026-10-01`)の引数があるが、後から足したファイルは引数を受けず、自分の定数を持った。

(推測。確かめていない)モデルの癖として、頼まれた機能を、いまのファイルの中で小さな差分で動かすことを優先する。汎用化の得は「次に値が変わるとき」に出るが、そのときは別のセッションで、いまのセッションには見えない。

### アイデアがリポジトリの目的に効くか

効く。README の目的は「新しいシステムを開発するとき、そのリポジトリの CLAUDE.md を作りこまなくても、agent-config の設定を読めば、すぐに AI 駆動開発に最適な環境ができること」。上の根本原因1・2は LogiFee だけのものでなく、セッションを分けて機能を足すどのリポジトリでも起きる。全体の CLAUDE.md に規則が無いので、各リポジトリが自分で書かないかぎり防げず、目的とずれている。

懸念(1行): 規則を「値はみな設定に出す」と書くと、1か所でしか使わない値まで設定に出し、読むファイルが増えて、AI 側の最適化(読むものを絞る)に逆効果になる。
