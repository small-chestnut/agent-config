## 壁打ち

### 固まった要件

- Fable にすべき場合のパターンを用意する。(利用者のタスクの文)
- パターンは、Opus 5.5 の high では仕上がらない仕事を見分けるためのもの。Fable の週の枠を使い切るためのものではない。(利用者の答え)

### なぜ

- Opus 5.5 の high では仕上がらない仕事がある。利用者は、仕上がらないと見込んだ仕事を、始める前から Fable にした(LogiFee の管理番号2856 の SE)。(利用者の答え)
- 見込んだ根拠は、前の同じ種類の仕事で、Opus がその場かぎりの対応を繰り返して作業が破綻し、利用者が AI の出力をつかみきれなくなったこと。仕上がらない仕事は、性能の問題だけでなく、利用者の認知負荷を壊す。(利用者の答え。README の「なぜ」の、利用者が AI の出力をつかむ認知負荷に当たる)

### 分かっていること

- セッションは、自分のモデルと effort を替えられない。`set_session_model` と `set_session_effort` は、自分のセッションを対象にすると断る(道具の説明)。SE の難しさが高なら PL が SE の effort を high にし、PG と QA は SE が替える(task-team-se・task-team-lead の SKILL.md)。
- SE は、PG と QA を Fable にも替えられる。今より高いモデルに替えるときは、アプリが利用者に確かめる(bypass permissions のときは確かめない)(道具の説明)。
- Anthropic のページで Fable 5.2 を勧めるのは、難しい推論と長いエージェントの作業、1つのコンテキストに収まらない大きな作業、Opus 5.5 の高い effort でも足りないとき(https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence.md 。2026-11-11 に読んだ)。
- 同じページで、コードの課題(SWE-bench Pro)は、Fable 5.2 の high が解けた1件あたり $1.39 で 96.3%、Opus 5.5 の xhigh が $0.75 で 96.5%。調べもの(DeepResearch Bench II)では、Fable 5.2 は Opus 5.5 より費用 2.9 倍で 1.9 ポイント下。
- 利用者のプラン(Max)には、全部のモデルの週の枠とは別に、Fable の週の枠がある。2026-11-11 に `get_usage` で引いた値は、全部のモデル 40%、Fable 12%。Fable を使った分が全部のモデルの枠にも数えられるかは、引いた値からは分からない。
- モデルを会話の途中で替えるとキャッシュが効かない(ADR 0059-1 の理由6)。SE を Fable にすると、会話の途中で替えることになる。

- LogiFee の管理番号2856 は、よその会社の会計データを移す計画を作る SE の仕事。SE の最初のコミットから Fable 5.2 で、ADR を7件出し、設計レビューを5回受けた(LogiFee のコミットの記録)。
- 2856 の前の移行(七海の移行、R-0571)は、範囲の終わりと合格の判定が無く、セッションごとにその場かぎりの処理が増えた(2856 の最初のコミットメッセージ)。
- 2856 より前の LogiFee の記録には、七海の移行で決定を直したコミット(管理番号2845 の「ADR-2845-5 の決定を直す」など)と、Co-Authored-By の行のモデル名が残っている。破綻したことと、利用者が出力をつかめなくなったことは、どこにも書かれていない。SE が記録から分かるのは、直しが重なったことまでで、案1 に当たるかは言い切れない。
- 前の移行(2026-11-02〜11-06、七海の会計データを LogiFee に入れる作業)では、会計の知識が、リポジトリにも利用者にも足りなかった。Claude が「入らない理由」を次々と出し、セッションを並べて進めた。期限の 11-06 までに終わらず、利用者は何をしているか分からなくなった。範囲の終わり(9月末まで両方の側で合う)は、途中で口頭で決まった(gemini リポジトリの記録「東京出張と七海国際物流へのLogiFee導入」)。
- 利用者が 11-09 に振り返って挙げた破綻の元は、会計の知識を入れながら導入作業を進めたことと、それを多くのセッションを並べて進めたことの2つ。そのときどのモデルが動いていたかは、記録に無い(Gemini PL の答え)。モデルは Opus だった(利用者の答え)。
- 七海の移行(R-0571)で、破綻の前に記録に出ていた印は、1つの管理番号に ADR の枝番が積み上がった(2729 が -16 まで)、同じ日に入れた決定を消した(ADR-2842-2 → 2842-5)、同じ決まりを4回変えた(立替金の分け方)、先行チケットが1週間で29本増えた、手順の無い使い捨てのスクリプトで本番に書いた、の5つ。(2856-migration-plan-se (fork) の答え)。
- 2856 で、Fable が Opus より効いたと言える比べた事実は無い。読み違いは Opus のときにも Fable のときにも起きた。Fable の設計にも整合の誤りがあり、Opus 5.5 の medium の QA が5回のレビューで15件拾った(同じ答え)。
- 2856 の仕事の特徴は、SE の難しさが高、読む元が多い(skill 約50KB・チケット30本・ADR 約20件)、要件が約20ターンかけて少しずつ出た、利用者が会計の中身を確かめられない、決定どうしがつながっていて1つ変えるとほかが合わなくなる、の5つ(同じ答え)。

### 決まっていない問い

- なし(SE が出した次の案で、設計に進めると利用者が答えた)。
  - 案1(始める前): SE の難しさが高で、利用者が中身を確かめられない分野の知識が要り、決定どうしがつながっている仕事は、SE を始めから Fable にする。
  - 案2(途中): Opus で進めている仕事で、ADR の枝番の積み上がり・同じ日の決定の撤回・同じ決まりの繰り返しの変更が出たら、Fable の新しいセッションに移す。
  - 案3: 仕事が1つの会話に収まらない大きさになると見込めるなら、Fable にする(Anthropic のページの勧め)。
  - どれでも、レビューは今の割り当てのまま QA がする。当たると決めるのは SE。PG と QA は SE が替え、SE 自身は PL が替える。

### 設計レビュー(1回目)

- 手順1の「入れた決定を後の ADR で消す」に、同じタスクの中という範囲が無い。前のタスクの ADR を置き換える(ADR 0006-2)ふつうの設計でも当たり、Opus で足りる仕事が Fable になる。

- 手順1の「次の見出しと11行を足す」が、ブロックの箇条書き10行と合わない。
- テスト一覧・ADR の番号の付け方・SKILL.md の箇条書きの字数(新しい行は `check_rule_length.py` で全部60字以内)は、指摘なし。
