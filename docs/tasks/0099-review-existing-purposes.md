## レビュー

### 設計レビュー

code-review(low)の指摘は無い。`rebuild.py` を別のフォルダで実行し、出力の目的の文・原則と、足した規則が headings.md と同じこと、R1-2・R1-3、テスト 118 本の成功を確かめた。Fable に替える条件には当たらない。ADR 0099-1 には直さないと通せない指摘が無いので「採用」にした。

- D1: `task-team-se` に足す規則「コードの無いタスクは、手順を実行して結果を確かめる。」は、skill `task-team` の RACI(設計の手順を実行するのは PG)とぶつかる。前は状態を言う見出しで、規則にすると SE への指示になる(SE の skill の規則なので)。置き直す目的「出来上がりが合っているかを、QA が要件を読むだけで言い切れる」のための手段でもない。
- D2: `task-team-qa` に足す規則「指摘の根拠にするのは、チケットとコードだけ。」は、同じ文書の規則とぶつかる(直さないと通せない指摘は「規則に合わない所」、テスト一覧を全体の CLAUDE.md の決まりと比べる、ADR の番号と状態を見る)。read1.txt の3つの答えも、3つともチケットの記載とコードの内容に限る決まり(2つは、ほかの資料は根拠にしない、とも書く)と読んでいる。設計の「どれも意図どおりに読んだ」は、意図がこの読みなら上の規則とぶつかり、違うなら成り立たない。
- Nit: `task-team-lead` に足す規則「利用者に聞かずに進めるタスクは、始めてよいかを利用者に確かめずに始める。」は、read1.txt の3つとも、前半の言い換えとも読める所として挙げている。見出し(R1 で合意済み)だけで足りるかもしれない。
- Nit: 利用者が headings.md を見て「設計に進める」と答えた後に、この規則の文を「聞かずに始める」から替えている。合意した文と違うことが、要件にもチケットにも書いていない(「サブタスクの前提」に、採点の後に替えたことだけがある)。
- Nit: ADR 0099-1 の理由3は、変えるのを規則の 13 行と2行だけとするが、`rebuild.py` は `task-team-pg`・`task-team-qa`・`team-kanban` に「原則がぶつかったときは、…」の行も足す。
- Nit: `task-team-pg` の「利用者に操作を頼むとき、ステータスを「利用者の操作待ち…」にする。」は、新しい目的では「自分が待たれていることを、…分かる」の方に合う。`task-team-pg` の「始めるとき、ステータスを「実装中」にする。」だけが利用者の目的に移り、`task-team-se`・`task-team-qa` の同じ種類の行は「次の役割が、…」に残っていて、そろっていない。
- Nit: 受け入れ条件 R1-1 は `rebuild.py` の出力と比べるだけで、plan.txt が、利用者の合意した headings.md と同じことを確かめる受け入れ条件と手順が無い(QA が照らした今の plan.txt は同じ)。

直しの確かめ: D1・D2 とも直った。残った指摘は無い。
