# ゴール

モジュラーモノリスを採る理由と、それが定石に沿うかが、リポジトリに残っている。理由は ADR 0012-1 に書き、今の規則の行に番号を付ける。今の決まり(グローバルの CLAUDE.md 原則3、skill `module-layout`・`restructure-modules`)を定石と照らし、ずれていた「ほかのモジュールからは公開の入口だけを使う」を ADR 0012-2 にして規則に足す。

発端: 利用者は「モジュラーモノリスも、AI駆動開発に効くんだっけ」と聞き、PL の答えのあとで「モジュラーモノリスの記述も含めて　それぞれタスク作って」と頼んだ。

利用者の理由:「AI駆動開発で大事なのは、コードのスケールと同時に、あなたが見るコンテキストまでスケールしないように、極力抑えることが命題で、そのためにモジュラーモノリスや、ADRの配置があると思っているのだけど、違う？」。

範囲外: モジュールの境目を lint やアーキテクチャのテストで止める規則と、モジュールどうしの依存を輪にしない規則。

## 手順: 規則の文書を直す

下の行を、そのとおりの文で入れる。「→」は置き換え、「足す」は新しい行。フック(`ask_removable_words.py`)が問い返してきても、文は変えない。SKILL.md と CLAUDE.md の箇条書きは、`rule_length` で数えて、すべて 60 字以内。main に入った他のタスクの変更とぶつかったら、main を取り込んで、下の文が下の位置に入る形に直す。

### `claude/CLAUDE.md`(原則3「1つの作業で読むものが、その作業に要るものに絞られている」の下)

- 「- 新しく作るファイルは、業務のまとまり(モジュール)ごとのフォルダに置いている(モジュラーモノリス)。」→ 次の行。

```
- 新しく作るファイルは、業務のまとまり(モジュール)のフォルダに置いている(モジュラーモノリス)。(ADR 0012-1)
```

- 「- モジュールの外は、import や型の参照をたどって行き着いたファイルだけを読んでいる。…」の次に、次の行を足す。

```
- ほかのモジュールは、そのモジュールの公開の入口だけを使っている。(ADR 0012-2)
```

### `claude/skills/module-layout/SKILL.md`

- frontmatter の description → 次の文。

```
description: ファイルの置き場所を決めるとき・新しいフォルダやモジュールを作るとき・ほかのモジュールのものを使うとき・新しいプロジェクトを始めるときの規則。ソースを業務のまとまり(モジュール)ごとのフォルダに置き、ほかのモジュールからは公開の入口だけを使う。
```

- 「## 目的: 1つの作業で開くファイルが、1つのモジュールのフォルダに集まっている」→ 末尾に `(ADR 0012-1)`。
- 「### 目指す状態: `shared/` には、どの業務のものでもないものだけがある」の箇条書きの後(「### 目指す状態: モジュールの中で、…」の前)に、次を足す。

```
### 目指す状態: ほかのモジュールからは、公開の入口だけが使われている(ADR 0012-2)

- ほかのモジュールが使うものは、そのモジュールの公開の入口から出している。
- 公開の入口は、モジュール直下の1つのファイル。
- 入口のファイルの名前は、言語の慣例(`index.ts`・`__init__.py`)があればそれ。
- 慣例の無い言語では、`<モジュール>Api` の名前にしている。
- 入口の外(内部のクラス・関数・テーブル)は、ほかのモジュールから直接使っていない。
```

### `README.md`(「プロンプト層(CLAUDE.md / AGENTS.md)の意図」の節)

- 「- **CLAUDE.md の原則3「開発」は、…**」の項目の後に、次の項目を足す。

```
- **ソースは業務のまとまり(モジュール)ごとのフォルダに置き、ほかのモジュールからは公開の入口だけを使う(モジュラーモノリス)**(ADR 0012-1・0012-2)。
  利用者の理由は「AI駆動開発で大事なのは、コードのスケールと同時に、あなたが見るコンテキストまでスケールしないように、極力抑えることが命題で、そのためにモジュラーモノリスや、ADRの配置があると思っているのだけど、違う？」。
  モジュールのフォルダなら、1つの作業で読む量はそのモジュールの大きさで決まり、ほかのモジュールを使うときも入口のファイルで止まるので、
  コード全体が増えても読む量は増えない。技術の層ごとのフォルダでは1つの機能が層の数だけ散らばり、マイクロサービスではリポジトリとネットワークをまたぐ。
  機能ごとにまとめる形と、モジュールに公開の入口を置いて中を隠す形は、人の開発の定石(vertical slice・Spring Modulith・Shopify)に沿う。
  AI が読む量が減るという理由は、実践者のブログで言われているだけで比べた調査は無く、agent-config が組み立てたもの
```

## 定石との照合

| 今の決まり | 定石 | 判定 |
|---|---|---|
| 原則3・`module-layout`: 業務のまとまりごとのフォルダに、画面・処理・データの出し入れを置く | vertical slice(要求ごとに前から後ろまでまとめる)、Shopify(商取引のサブドメインごとの component) | 沿う |
| 原則3: モジュールは画面のナビの行き先ごと、画面が無ければデータのまとまりごと | Shopify・DDD はサブドメイン(業務の領域)ごと | 沿う(業務の画面のナビの行き先は業務の領域に当たる) |
| `module-layout`: どの業務のものでもないものだけを `shared/` に置く | vertical slice の、slice をまたいで共有するコードを小さくする | 沿う |
| `module-layout`: ほかのモジュールが使うものも、その業務のモジュールに置いたまま。どこから使うかの決まりは無い | Simon Brown・Spring Modulith・Shopify: モジュールは公開の API を出し、中はほかのモジュールから使わせない | ずれ → ADR 0012-2 |
| `restructure-modules`: 中身を変えずに `git mv` で動かし、前後の動きを比べる | Shopify: ファイルをまず component のフォルダへ動かし、境目はあとから整える | 沿う(直さない) |

出典:
- vertical slice: https://www.jimmybogard.com/vertical-slice-architecture/
- Shopify: https://shopify.engineering/shopify-monolith
- Spring Modulith: https://docs.spring.io/spring-modulith/reference/verification.html
- Simon Brown「Modular Monoliths」(GOTO Berlin 2018): https://files.gotocon.com/uploads/slides/conference_12/515/original/gotoberlin2018-modular-monoliths.pdf
