## 難しさ

- SE: 高(prompt-structure に、目的の下の目指す状態の数を決める規則が無く、段の型そのものを決める仕事のため)

## ゴール

目的と目指す状態は 1:N であるべきなのに、目的がその下の目指す状態1つの言い換えになっている所がある。skill prompt-structure がこの形をどう扱うかと、リポジトリの規則の文書にそういう段が無いかを点検したい。(0060 の壁打ちで利用者が出した話題)

範囲外: `.claude/rules/settings.md` の段(0060 の中で直している)。

## 壁打ち

### 固まった要件

- 問題は、目的と目指す状態のスコープが分かれていないこと。目指す状態が1つしかないこと自体は問題でない。
- スコープが分かれていない段を直す。目指す状態の数によらず、全部の目的を点検する。
- Claude が今後、目的と目指す状態をスコープを分けて書けるようにする。
- なぜ: スコープが同じだと、目的がその下の状態がなぜあるかを説明せず、親の段を読んでも理由が分からない。今ある段は AI がタスクで書いたもので、直しても書き方が変わらなければ同じ段がまた増える。

### 点検で分かったこと

- prompt-structure には、目的の下に目指す状態をいくつ置くかの規則が無い。目的についての規則は「下の状態がそろえば達成したと言える文にする」だけ。
- そのため、目指す状態が1つだと、「その状態がそろえば達成」となる目的を書けば規則を満たし、言い換えでも型の上では通る。
- `claude/` と `.claude/` の下の規則の文書(SKILL.md・CLAUDE.md・rules)と直下の CLAUDE.md にある目的は 52 個。そのうち目指す状態が1つのものは 15 個(settings.md の2個を含む)。
- 15 個のうち、目的が目指す状態の言い換えに近いもの:
  - task-team-se の CLAUDE.md「利用者の使用量が、仕事の難しさに足りる分だけで済む」/「モデルと effort は、仕事の難しさで決まっている」
  - task-team-se の CLAUDE.md「利用者が、サブタスクが済むたびに、何を確かめればよいかが分かる」/「サブタスクは、利用者が把握できる単位と順で進んでいる」
  - task-team-messaging「子セッションが、チケットを根拠に動く」/「子セッションどうしの知らせは、チケットだけを指している」
  - task-team-lead「利用者の話題が、混ざらずに、当たるタスクの SE に届いている」/「PL が持つのは、話題がどのタスクに当たるかまで」
  - notion-learning-log「学習記録が、Notion の運用ルールのとおりになっている」/「書く・直す前に、運用ルールのページを読んでいる」
- task-team-se の SKILL.md の原則2 の目的「各役割の仕事が、難しさに足りる性能で進み、それを越える性能を使わない」も、目指す状態「モデルと effort は難しさで決まる」と同じスコープ。ADR 0059-1 の理由1 は「足りないと仕事が仕上がらず、余ると使用量を損なう」で、今の目的と CLAUDE.md の目的は、その片側しか持っていない。
- 1つだが言い換えではないもの: task-team-qa(目的が広く、状態はその一部)、task-team-pg の CLAUDE.md の2個、global-claude-md.md の2個。
- prompt-structure の CLAUDE.md の3個は、「なぜ」の文書で、状態が「〜の行が skill に残っている」の形。1つの規則の理由を書く置き場なので、1つになるのが自然な形。

### 決まっていない問い

- 目的と目指す状態のスコープを分ける基準。案: 目的は、利用者かリポジトリにとっての結果で、下の目指す状態が「なぜ要るか」の答えになる文。目指す状態は、その結果のために AI の振る舞いかプロンプトに保つ条件。

- 「なぜ」の文書(skill の CLAUDE.md・`.claude/rules/`)も、同じ型で点検するか。
