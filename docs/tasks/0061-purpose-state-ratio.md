## ゴール

目的と目指す状態は 1:N であるべきなのに、目的がその下の目指す状態1つの言い換えになっている所がある。skill prompt-structure がこの形をどう扱うかと、リポジトリの規則の文書にそういう段が無いかを点検したい。(0060 の壁打ちで利用者が出した話題)

範囲外: `.claude/rules/settings.md` の段(0060 の中で直している)。

## 壁打ち

### 固まった要件

- 問題は、目的と目指す状態のスコープが分かれていないこと。目指す状態が1つしかないこと自体は問題でない。
- スコープが分かれていない段を直す。目指す状態の数によらず、全部の目的を点検する。「なぜ」の文書(skill の CLAUDE.md・`.claude/rules/`)も含む。
- Claude が今後、目的と目指す状態をスコープを分けて書けるようにする。目的には、目指す状態を一段抽象化した文を書く(例: 目指す状態「モデルと effort は、仕事の難しさで決まっている」に対し、目的「AI の費用対効果を最適化する」)。
- Claude は、確かめる手順が無いと、一段抽象化した目的を書けない。この会話でも、最初に出した目的の案は、難しさや仕上がりという目指す状態の言葉を残していた。
- リポジトリを一言で説明するものを「命題」と呼び、段のいちばん上に置く。段の2段目の「目的」とは呼び分ける。
- agent-config の命題は「AI 駆動開発の最適化」。AI 側の最適化と、人間側の最適化の2つの面がある。
- 全体の CLAUDE.md の原則1「安全」は、命題の2つの面でなく、最適化の制約条件(最適化は、安全を守る範囲の中でする)。
- なぜ: 置かないと、破壊的な操作を通すリスクがある。制約条件はどれだけ良くなる案でも破れないので、原則1 として最も先にする。
- 原則は、命題のどの面か、制約条件かが分かる言葉にする(例: AI 側の最適化・人間側の最適化・安全)。体言1語(例: 開発)からは、受け持つ面が読めず、目的を導けない。
- 段の文面は、命題・規則・ADR・知識から SE が導いて作る。利用者に1語ずつ聞かない。
- 目的がよいかは、利用者がその時に一番よいと思うかでなく、親の段に従っているかで決まる。原則は命題から導き、目的は原則から、目指す状態は目的から導く。
- なぜ: 段を「原則 → 目的 → 目指す状態」の入れ子にしているのは、下の段を上の段から導くため。
- なぜ: スコープが同じだと、目的がその下の状態がなぜあるかを説明せず、親の段を読んでも理由が分からない。今ある段は AI がタスクで書いたもので、直しても書き方が変わらなければ同じ段がまた増える。

### 点検で分かったこと

- prompt-structure には、目的の下に目指す状態をいくつ置くかの規則が無い。目的についての規則は「下の状態がそろえば達成したと言える文にする」だけ。
- そのため、目指す状態が1つだと、「その状態がそろえば達成」となる目的を書けば規則を満たし、言い換えでも型の上では通る。
- `claude/` と `.claude/` の下の規則の文書(SKILL.md・CLAUDE.md・rules)と直下の CLAUDE.md にある目的は 52 個。そのうち目指す状態が1つのものは 15 個(settings.md の2個を含む)。
- 15 個のうち、目的が目指す状態の言い換えに近いもの:
  - task-team-se の CLAUDE.md「利用者の使用量が、仕事の難しさに足りる分だけで済む」/「モデルと effort は、仕事の難しさで決まっている」
  - task-team-se の CLAUDE.md「利用者が、サブタスクが済むたびに、何を確かめればよいかが分かる」/「サブタスクは、利用者が把握できる単位と順で進んでいる」
  - task-team-messaging「子セッションが、チケットを根拠に動く」/「子セッションどうしの知らせは、チケットだけを指している」
  - task-team-lead「利用者の話題が、混ざらずに、当たるタスクの SE に届いている」/「PL が持つのは、話題がどのタスクに当たるかまで」
  - notion-learning-log「学習記録が、Notion の運用ルールのとおりになっている」/「書く・直す前に、運用ルールのページを読んでいる」
- task-team-se の SKILL.md の原則2 の目的「各役割の仕事が、難しさに足りる性能で進み、それを越える性能を使わない」も、目指す状態「モデルと effort は難しさで決まる」と同じスコープ。ADR 0059-1 の理由1 は「足りないと仕事が仕上がらず、余ると使用量を損なう」で、今の目的と CLAUDE.md の目的は、その片側しか持っていない。
- 釣り合いの目的が言うべきことは、費用対効果(仕事が仕上がることと、使用量の枠を無駄にしないことの両方)。
- 1つだが言い換えではないもの: task-team-qa(目的が広く、状態はその一部)、task-team-pg の CLAUDE.md の2個、global-claude-md.md の2個。
- prompt-structure の CLAUDE.md の3個は、「なぜ」の文書で、状態が「〜の行が skill に残っている」の形。1つの規則の理由を書く置き場なので、1つになるのが自然な形。

- 今ある原則の名前も、命題のどの面か、制約条件かが分かる言葉に直す。目的の書き直しより先にする。
- なぜ: 目的は原則から導くので、原則が「開発」のような1語のままだと、書き直した目的が上から導けているかを確かめる拠り所が無い。つながった作業を細かいタスクに分けると、利用者が追うタスクとそのつながりが増え、命題の人間側の面(認知負荷を下げる)に反する。
- 今あるものを直すだけでなく、後から目的・目指す状態・規則を足すときも、Opus のままスコープを分けて書けるようにする。
- なぜ: 段は今後も足していく。今回直せても、足すたびに壊れるなら、直した意味が無い。

### 決まっていない問い

- 書いた時に問い返すフックを足すか。案: 「## 目的」「### 目指す状態」の行を書いた保存で、`ask_about_written_lines.py` と同じ形で「この目的は原則から導いたか。下の目指す状態の手段の言葉が入っていないか」を問い返す。フックを変えるので、利用者に頼まれてから入れる。

- prompt-structure の段の決め方を、親から導く向きにどう書き直すか。今は「原則は、下に置く目的すべてと適合するものにする」「目的は、下の状態がそろえば達成したと言える文にする」と、どちらも子の段から決める向きで、目指す状態を見て目的を書くと言い換えになる。

## 受け入れ条件

1. prompt-structure の段は、命題・原則・目的・目指す状態・規則の入れ子で書く。
2. prompt-structure では、下の段をすぐ上の段から導いて書く。
3. prompt-structure の原則は、命題のどの面か、命題を追う中で守る制約条件かが分かる言葉にする。
4. prompt-structure の目的は、原則をその文書の範囲で果たした姿を、下の目指す状態の手段の言葉を使わずに書く。
5. README の冒頭に、agent-config の命題「AI 駆動開発の最適化」がある。
6. 用語集に、命題がある。
7. プロンプトに原則・目的・目指す状態の見出しを足した保存では、すぐ上の段から導いたかを問い返す。
8. 段の見出しを足していない保存では、段の問いを出さない。
9. シェルでプロンプトに段の見出しを足したときも、すぐ上の段から導いたかを問い返す。
10. 段の問いの文は、`ask_about_written_lines.py` の1か所にだけある。
11. 書き直し一覧の目的 15 個が、新しい文になっている。
12. prompt-structure では、制約条件の原則を先に置き、命題の面の原則は命題が決めた順に並べる。
13. 並べ直し一覧の 23 ファイルの原則は、安全・人間側の最適化・AI 側の最適化のどれかで、この順に並んでいる。
14. prompt-structure では、ほかの行から原則を指すときは、番号でなく原則の名前で指す。設計 7. の6行も、原則を名前で指している。

### 5. 原則の並べ直し(PG)

原則の見出しを、安全・人間側の最適化・AI 側の最適化の3つの名前に替え、目的(その下の目指す状態と規則ごと)を下の表の原則の下へ移す。原則の番号は、表の順に1から振る。目的どうしの順は、今の順のまま。原則が2つ以上になったファイルには「原則がぶつかったときは、番号の小さい方を先にする。」の行を置き、1つになったファイルからは消す。目的は「目的: 」の後の頭の数語で示す(書き直し一覧の目的は、新しい文で置く)。

## レビュー

### 設計レビュー

- 設計 4 は知らせの1行目の「2つ」を替えるが、`ask_about_written_lines.py` と `check_rule_documents_changed_by_shell.py` の1行目の docstring の「2つ(…)を問う」「2つの問い」を替えていない。
- 点検した目的の数が、壁打ちでは 52 個、設計の点検の基準では 15+35=50 個、ADR 0061-1 の理由2 では 50 個と食い違う。
- 受け入れ条件 11 の確かめ方は「`## 目的: <新しい目的>` の行が1つずつある」だが、「AI の費用対効果を最適化する」は3つのファイルに入るので、grep では3件当たる。ファイルごとに確かめる書き方にする。
- テスト一覧は、テストを作る決まりに合っている(受け入れ条件 7〜10 に1つ以上、文書だけの条件は確かめ方)。
- ADR 0061-1 は指摘があるので「提案」のまま。

### 設計レビュー(2回目)

- 前の指摘3件は直っている。
- 原則を安全・人間側の最適化・AI 側の最適化の順に並べる決定(設計 5.・受け入れ条件 12・13)が、ADR 0061-1 に無い。規則の文書すべての構造に効くので ADR に書き、設計 1. で足す行と README の命題の行に、その番号を付ける。
- ADR 0061-1 の状態を、SE が「採用」にしている。採用にするのは QA で、上の指摘があるので「提案」に戻した。
- 書き直し一覧(設計 6.)は「原則4」「原則1 の1つ目」など今の原則の番号で目的を指すが、設計 5. の並べ直しが先に入るので、番号が変わって指す先が分からなくなる(例: `.claude/rules/global-claude-md.md` の「原則4」は並べ直し後にはない)。今の目的の文で指す。
- 並べ直しで、ファイルの中で原則を番号で指す行が指す先を失う。`claude/skills/task-team-lead/SKILL.md` の「原則2 の、かんばんの書き直しの見出し」は、今の原則2「軽さ」が AI 側の最適化(並べ直し後の原則3)に移る。番号で指す行の直し方を設計に入れる。
- テスト一覧は、足した受け入れ条件 12・13 が文書だけの条件で確かめ方があり、テストを作る決まりに合っている。

### 設計レビュー(3回目)

- 2回目の指摘4件は直っている(ADR 0061-2、目的を文で指す、設計 7.)。
- 受け入れ条件 14 は「ほかの行から原則を指すときは、番号でなく原則の名前で指す」と、後から足す行にも当たる決まりの形だが、設計は今ある6行を替える(設計 7.)だけで、その決まりを置く所が無い。後から番号で指す行を足しても止まらない。prompt-structure に規則の行を足すか、受け入れ条件 14 を「設計 7. の6行が、原則を名前で指している」に狭める。
- ADR 0061-1・0061-2 は、上の指摘が受け入れ条件 14 にかかるので「提案」のまま。

### 設計レビュー(4回目)

- 指摘なし(3回目の指摘は、設計 1. の足す行と受け入れ条件 14 で直っている)。ADR 0061-1・0061-2 を「採用」にした。
