# ゴール

機能(モジュール)ごとの仕様を1つ残し、そのモジュールの動きを変えるタスクのたびに直す(spec-anchored)。SE が機能の今の動きを知るのに読むのは、その機能の仕様1つで、タスクの数に比例して増えない。仕様には、そのモジュールを縛る ADR の番号を並べ、コードを書き換える SE がその ADR にたどり着ける。

利用者の理由: 利用者は「spec駆動開発の考えは、このリポジトリに取り入れられている？」と聞き、agent-config の目的(新しいシステムを開発するとき、そのリポジトリの CLAUDE.md を作りこまなくても、agent-config の設定を読めば、すぐに AI 駆動開発に最適な環境ができること。利用者の言葉を整えた文)の話のあとで「だから、spec駆動開発が要るんじゃない？って思った」と言った。

範囲外: 既にあるモジュール(agent-config の hooks も)の仕様をまとめて作ることと、仕様の直し忘れをフックやテストで検査すること。

# 受け入れ条件

1. `task-team-se` に、仕様の置き場(`docs/specs/<モジュール>.md`、モジュール1つに1ファイル)・機能の今の動きを知るのに前のタスクの記録を読まない・動きを変えるときは設計のコミットで仕様を直す・仕様の無いモジュールはそのタスクで作る、の行がある。
2. `task-team-se` に、仕様の形(冒頭は `# <モジュール>`・節は `## ADR` と機能ごとの `## <機能の名前>`・外から見える動きだけ・機能の節の行は業務の規則の1文・無くなった動きは行を消す)と、決まりの文書が中身のモジュールはその文書が仕様で、番号は行と見出しに付けて「ADR」の節は作らない、の行がある。
3. `task-team-se` に、仕様で足した行・変えた行を同じ文で受け入れ条件に入れる行があり、設計で読むものの行にモジュールの仕様がある。
4. `task-team-se` の ADR の読み方に、コードを書き換えるときは仕様の「ADR」の節の番号を集める行・仕様が無いときだけ「ADR」で検索して作る仕様に並べる行・コードか CLAUDE.md に番号を付けたら仕様の「ADR」の節にも並べる行がある。
5. `task-team-qa` に、仕様の直し忘れと仕様と違う動きを指摘する行と、コードに付いた番号が仕様の「ADR」の節にもあるかを見る行がある。
6. `task-team-pg` に、利用者に見える動きを自分の判断で変えたら、仕様も同じコミットで直す行がある。
7. グローバルの CLAUDE.md(`claude/CLAUDE.md`)原則3 に、モジュールの今の動きは仕様にある・動きを変える変更で直す・仕様の形は `task-team-se` に従う、の行があり、読む順は `docs/概要.md`・モジュールの仕様・モジュールのフォルダの1行にまとまっている(「作業の最初に」で始まる別の読む順の行が無い)。
8. README の「セッションの役割分割」の節に、仕様を残して直す理由と利用者の言葉がある。
9. `docs/用語集.md` に、仕様・仕様の「ADR」の節・機能の節の行がある。
10. この変更で足した行のうち、ADR 0010-1・0010-2 で決めた行に、設計のとおり ADR の参照が付いている。
11. どの SKILL.md の箇条書きの行も 60 字以内(`python -m unittest discover -s tests` が通る)。

# 設計

決定は [ADR 0010-1](../adr/0010-1-spec-per-module.md)・[ADR 0010-2](../adr/0010-2-adr-list-in-spec.md)(どちらも採用)。用語は [docs/用語集.md](../用語集.md)(この設計と同じコミットで SE が足した)。する人は、どの手順も PG。

読んだ ADR: 書き換える行に付いた 0005-1・0006-1・0006-2、それと 0010-1・0010-2。

出典: spec-anchored の定義は https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html 。仕様をコードの外の1つのフォルダに置くのは Kiro(https://kiro.dev/docs/specs/best-practices/)・Spec Kit(https://github.com/github/spec-kit/blob/main/spec-driven.md)・OpenSpec。外から見える動きだけを書くのは OpenSpec(https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)。

## 仕様の形

PG はこのファイルを作らない(範囲外)。skill の行が指す形を、ここに示す。

```
# <モジュール>

## ADR

- <ADR の番号> <ADR の題>

## <機能の名前>

- <業務の規則を用語集の言葉で書いた1文>(ADR <番号>)
```

## 手順: 規則の文書を直す

下の行を、そのとおりの文で入れる。「→」は置き換え、「足す」は新しい行。フック(`ask_removable_words.py`)が問い返してきても、文は変えない。字数は `rule_length` で数え済み(SKILL.md と CLAUDE.md の足す行は、すべて 60 字以内)。作業ブランチに main を取り込んで衝突したら、main の文を残し、ここの文を足し直す。

### `claude/skills/task-team-se/SKILL.md`

- 「### 目指す状態: 設計は、短く、置く場所と名前まで決まっている」の下の「読むのは、対象リポジトリの CLAUDE.md・`docs/概要.md`・そのモジュール。」→「読むのは、対象リポジトリの CLAUDE.md・`docs/概要.md`・そのモジュールの仕様とフォルダ。」
- その節の箇条書きの後(「### 目指す状態: 設計で読む ADR は、…(ADR 0006-1)」の前)に、次を足す。

```
### 目指す状態: 機能の今の動きは、モジュールの仕様1つにある(ADR 0010-1)

- 仕様は `docs/specs/<モジュール>.md`。モジュール1つに1ファイル。
- 機能の今の動きを知るのに、前のタスクの記録は読まない。
- 動きを変えるときは、設計のコミットで仕様を直している。
- 仕様の無いモジュールは、そのタスクで作っている。
- 作るときは、そのタスクで読んだコードの今の動きを書いている。
- 冒頭は `# <モジュール>`。節は、`## ADR` と、機能ごとの `## <機能の名前>`。
- 「ADR」の節には、番号と ADR の題を1行ずつ並べる。(ADR 0010-2)
- 仕様には外から見える動きだけを書き、クラス名・ライブラリ・手順は書かない。
- 機能の節の行は、業務の規則を用語集の言葉で書いた1文。
- 無くなった動きは、行を消す。前の形は git にある。
- SKILL.md など決まりの文書がモジュールの中身なら、その文書が仕様。
- 決まりの文書が仕様なら、番号は行と見出しに付け、「ADR」の節は作らない。(ADR 0010-2)
- 仕様で足した行・変えた行は、同じ文で受け入れ条件に入れている。
```

- 「### 目指す状態: 設計で読む ADR は、書き換える所に付いた番号の ADR だけ(ADR 0006-1)」の下:
  - 「コードを書き換えるときは、そのモジュール・テスト・lint の設定を「ADR」で検索している。」→ 次の2行。

```
- コードを書き換えるときは、仕様の「ADR」の節の番号も集めている。(ADR 0010-2)
- 仕様が無ければ、そのモジュール・テスト・lint の設定を「ADR」で検索している。(ADR 0010-2)
```

  - 「書き換えるコードに効く所の番号も集めている。」→「書き換えるコードに効く所の番号も集め、作る仕様に並べている。(ADR 0010-2)」
  - 「どれにも当たらない決定は、そのモジュールの CLAUDE.md の行に付ける。」の後に足す:

```
- コードか CLAUDE.md に番号を付けたら、仕様の「ADR」の節にも並べる。(ADR 0010-2)
```

### `claude/skills/task-team-qa/SKILL.md`

- 「### 目指す状態: ADR で決めた所に、その ADR の番号が付いている(ADR 0006-1)」の下の「実装のレビューでは、ADR で決めた所に番号が付いているかを見ている。」の後に足す:

```
- コードに付いた番号が、仕様の「ADR」の節にもあるかを見ている。(ADR 0010-2)
```

- その節の箇条書きの後(「### 目指す状態: ターンが終わるとき、…」の前)に、次を足す。

```
### 目指す状態: 仕様が、作ったものの動きと合っている(ADR 0010-1)

- 設計のレビューでは、動きを変える設計が仕様を直しているかを見ている。
- 実装のレビューでは、作ったものの動きが仕様の行と合っているかを見ている。
- 仕様の直し忘れと、仕様と違う動きを、指摘に足している。
```

### `claude/skills/task-team-pg/SKILL.md`

- 「### 目指す状態: 記録の設計の節が、作ったものと合っている」の下の「設計が決めていない所を判断して、利用者に見える動きが変わったら、設計の節を同じコミットで直している。」の後に足す:

## テスト一覧

- テスト一覧の `git diff main -- claude README.md` は、main が先に進んでいると main 側の変更(0008 の README)も出る。`git diff main...HEAD` にする。
