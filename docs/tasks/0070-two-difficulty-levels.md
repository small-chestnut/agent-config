## 難しさ

- SE: 高(ADR 0067-1 のとおり、いつも高)
- PG: 低(足す・直す・消す行と置く所は、設計の節に文のまま書いてある。ADR 0070-2 のとおり Sonnet 5.5 の high)
- QA: 高(設計レビューで、ADR 2件の決定が、利用者の「なぜ」と README の目的と既にある ADR に合うかを見る。枠を決める仕事のレビュー。Fable の3つの特徴のうち、利用者が中身を確かめられない分野の知識は要らないので、Opus)

## ゴール

役割の仕事の難しさを、低・中・高の3段から2段にまとめ、低の仕事に割り当てるモデルと effort を見直す。

範囲外: 中と高に割り当てた Opus 5.5 の high そのもの。Fable を使う条件のうち、1つの会話に収まらない仕事と、途中の印(決定を消す・同じ決まりを3回変える)。

## 壁打ち

### 固まった要件

- 難しさを、低(書いてあるとおりにやれば済む仕事)と、判断がある仕事の2段にまとめる。(PL のタスクの文)
- なぜ: 中と高は、モデルと effort の割り当てが同じになり(ADR 0069-3)、分ける意味がほとんど無い。利用者は、中と高の区別が何のためにあるのか分からなかった。(PL のタスクの文)
- 2段の名前は、「低」と「判断がある」をそのままには使わない。(利用者の答え)
- PG は、始めから Fable にしない。(利用者が同意した)
- 低の割り当て(Sonnet 5.5 の medium)の見直しも、このタスクに入れる。利用者は、測定の数字を見るかぎり、Sonnet 5.5 の high の方がよさそうだと見た。(利用者の答え)

### 分かっていること

- 中と高の割り当ては、どちらも `claude-opus-5-5` の high(skill `task-team-se` の SKILL.md 248行目、ADR 0069-3)。
- 中と高の区別を使っている所は、次の4つ。
  1. Fable を始めから使う条件の1つ目「役割の難しさが高であること」(skill `task-team-se` の SKILL.md 256行目、ADR 0065-1)。
  2. 「PG の仕事が高になるなら、設計を足して、中か低にしている」(同 242行目)。
  3. 「QA の難しさは、設計レビューと実装レビューの高い方にしている」(同 241行目)。
  4. 「PL の仕事は、決まった枠の中で選ぶ中の仕事なので、Opus 5.5 の high にしている」(skill `task-team-lead` の CLAUDE.md 63行目)。
- ADR 0069-3 は、前のタスクで、中と高を1つの段にまとめる案を見送った(捨てた案5)。見送った根拠は、2 と 3 を書き直すことになるという手間で、目的に反するからではない。
- 2 は、モデルの割り当てではなく、PG に枠を決めさせない決まり。段の名前を使わずに、PG に枠を決める所が残るなら設計を足す、と書ける。
- 3 は、2段でもそのまま効く。
- 1 は、2段にしたときに広がる。今は 2 があるので PG は高にならず、1 の条件で PG が始めから Fable になることは無い。「判断がある」をそのまま1つ目の条件にすると、判断のある PG の仕事も、残りの2つがそろえば Fable になる。
- Fable の残りの2つの条件(利用者が中身を確かめられない分野の知識が要る・決定どうしがつながり1つ変えるとほかが合わなくなる)は、どちらも枠を決める仕事で起きる(PL の答え)。
- 段の名前が出てくる所は、skill `task-team-se` の SKILL.md(233〜265行目)と CLAUDE.md(46行目「3段の割り当て」)、skill `task-team-lead` の CLAUDE.md(63行目)、用語集の「難しさ」の行(「低・中・高の3段」)、ADR 0059-1・0065-1・0067-1・0069-3。skill `task-team-lead`・`task-team-qa`・`task-team-pg` の SKILL.md には、段の名前の行は無い。
- 採用した ADR で書き換えられるのは状態の行だけなので、3段を決めた所は、新しい ADR で置き換える。
- 低の割り当ての Sonnet 5.5 の medium について、Anthropic のページ(https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence.md 。2026-11-12 に読んだ)の数字は次のとおり。
  - SWE-bench Pro では、Sonnet 5.5 の既定の high が 87.6%(解けた1件あたり $0.11)、medium は high より約7ポイント下で、1件の費用は約59%。
  - Anthropic の社内のエージェントのコードの課題では、Sonnet 5.5 の high が 77.8%(1回 $0.33)、medium が 62.7%(1回 $0.16)。Opus 5.5 は medium と high の差が約1.8ポイント。
  - 同じ課題で、Opus 5.5 の low は 74.8%(1回 $0.35)、medium は 86.6%(1回 $0.84)、high は 88.4%(1回 $1.38)。
  - SWE-bench Pro では、Opus 5.5 の low は 87.4%(解けた1件あたり $0.12)で、Sonnet 5.5 の high と、測るたびの揺れの中で同じ。
  - 安いモデルの費用は、そのモデルが失敗した仕事で決まる。失敗した仕事にもトークンがかかり、やり直しが続くから、と書いてある。
  - 単純な仕事や手順が決まった仕事での数字は無い。決まった作業に下げるなら、先に自分の作業で測る、と書いてある。
- ADR 0059-1 が低を Sonnet 5.5 の medium にした根拠は、SWE-bench Pro の数字だけで、エージェントのコードの課題の数字は引いていない。
- このリポジトリで低の PG が動いたタスク 0069 では、実装レビューの指摘が0件だった。記録は1件だけ。

### 効くか逆効果か

- 効く。中と高を分けても割り当ては変わらないので、SE が見分ける手間と見分けの誤りだけが残っている。2段にすると、チケットの「難しさ」の節と用語集を読む利用者が、使われない区別を覚えずに済む(README の「なぜ」の認知負荷)。
- 効き方は小さい。割り当ては変わらず、減るのは見分ける手間と、使われない区別だけ。
- 逆効果になりうるのは、上の1の広がりだけ。Fable の1つ目の条件を「枠を決める仕事」の意味で残せば、PG が始めから Fable になることは今と同じく無い。
- Fable の1つ目の条件に、今は高の QA の設計レビュー(枠を決める仕事のレビュー)も当たる。条件の文に設計レビューを入れれば、当たる範囲は今と同じ(SE と、枠を決める仕事の設計レビューをする QA)。

- 設計: Fable の1つ目の条件を「仕様・設計・規則に答えが無く、枠そのものを決める仕事であること」に替えると、難しさが高の QA(枠を決める仕事のレビュー。このタスクの QA がそう)が当たるかが二通りに読める。今は「役割の難しさが高」なので当たる。ADR 0070-1 の理由2 は「今と同じ範囲になる」と書いているので、QA が当たるかを条件の文で決め、範囲が狭まるならそれを ADR 0070-1 に書く(ADR 0065-1 の捨てた案5 は、Fable の仕事のレビューを Fable にしない)。
- 設計: skill `task-team-se` の SKILL.md 256行目の書き換えは ADR 0070-1(捨てた案3・4)で決めた行なので、末尾に「(ADR 0070-1)」を付ける設計にし、受け入れ条件 4 とサブタスク 3 の完了条件の「ADR 0070-1」の行数も合わせる。
