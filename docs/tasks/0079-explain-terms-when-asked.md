## ゴール

全体の CLAUDE.md(`claude/CLAUDE.md`)に、AI が勝手に作った呼び名(方言)を生みうる規則が無く、分かりやすく説明する目指す状態だけが残っている。

なぜ: 利用者が求めるのは、分かりやすく説明することの一点。そのときに AI が勝手に方言を作ると、利用者は AI の作った言葉を覚え直さなければならない。利用者はこのことを前にも言っている(ADR 0044-1)。それでも方言を生みうる規則が残っているなら、それを除きたい。

範囲外: 規則の文そのものに混ざった方言を直すこと(タスク 0078)。skill `explain-to-non-experts` が、利用者に頼まれて書く、ほかの人向けの例え話。

## 壁打ち

固まった要件:

- 根にある求めは、分かりやすく説明すること。用語を問い返されたら説明する、は手段の1つで、本質ではない(利用者の言葉「用語は問われたら説明、というのは、それそのものが本質ではない」)。
- AI が勝手に方言を作らない。方言を生みうる規則は除く(利用者の言葉「その方言を生みうる規則があるならば、それを排除したい」)。
- 方言は、IT の用語・一般の語・用語集の言葉で言える概念に、AI が付けた別の呼び名。
- IT の用語を名前に含む機能(例: メーラの IMAP 設定)を説明するときは、最初からその用語をそのまま使う(利用者の言葉「最初はその言葉をそのまま使うべき」)。画面にもその用語が出ているので、言い換えると画面と結びつかない。
- 用語の意味は、最初に出すときには添えず、利用者に問い返されたとき(例:「IMAP って何?」)に初めて説明する(利用者の言葉「『IMAPって何?』ってなったら、初めてその言葉の説明が要る」)。

なぜ:

- 方言は、利用者に、AI の作った言葉を覚え直す負担をかける。README の「なぜ」(利用者が AI の出力をつかむときの認知負荷を下げる)に逆らう。
- ADR 0044-1 は、方言を「替えず」の1行で止めたが、方言を生む側の規則は残した。

方言を生みうる規則(`claude/CLAUDE.md`):

- 36行目の目指す状態「書く文と、自分が付ける名前(見出し・呼び名)は、その分野を知らない人が一度読めば分かる」: AI が名前を付ける前提で書かれている。ADR 0044-1 の理由1は、この目指す状態を守ろうとした AI が、IT の用語を作った呼び名に置き換えていたと書いている。
- 39行目「例えと、会話の中で付けた呼び名は、その会話の中だけで使っている。」: 会話の中でなら呼び名を作ってよいと読める。この行は、利用者の「なぜ」(コミット 421ff37 の本文。会話の中では、定義した変数のように呼び名を扱ってよいが、範囲はその会話まで)で入った。その前の「名前を付けず、出てくるたびに短い説明で指す」が、同じ説明を繰り返させていたため。

- 40行目「IT の用語は、例えや作った呼び名に替えず、知らない人には初めて出すときに意味を添えている。」の条件(知らない人か・初めて出すか)は、AI に見分けられない。問い返されたときに説明する形に書き直す。

LogiFee で起きた方言(LogiFee PL セッションの答え。LogiFee の自動メモリと git の履歴と、2026-11-13 の LogiFee のチームが使った語):

- 和語に寄せた例: 木(ツリー)・窓(ウィンドウ)・入口(エンドポイント)・帯(メッセージバー)・札(バッジ)・写し(スナップショット)・道具(スクリプト)・流す(実行する) など20語余り。
- 新しく作った呼び名: 枠(本番を書く実行の順番)・指紋(plan_hash)・置き場(SharePoint の取り込みフォルダ)・書き手の順・4点・前の道。どれも、本来の言い方が既にあった。
- 会話の返答だけでなく、チケット・skill・仕様・画面の字にまで入った。LogiFee の 2012 では、使わない語77語をアプリ・API・文書から取り除いた。
- 言い換えた手がかり: 読んだ文書やコメントにある語をそのまま写す。全体の決まり「いちばんありふれた言葉で指す」を、和語に言い換える理由に読んだ(この行は bf897e7 で「広く使われている呼び名」に変わっている)。LogiFee の CLAUDE.md の「1つの作業だけの語は、チケットの本文に意味を書いて使う」の形で、枠・書き手の順・4点・前の道が作られた。
- 利用者の言葉: 「技術用語をあえて日本語にして、説明を分かりづらくする傾向」「和語の多用というのは、重複を生む可能性が高いという面で、逆効果にしかならない」。

ここから分かること:

- 範囲を決めて呼び名を作ってよい規則は、範囲を越えて広がった(会話・チケットから、skill・仕様・画面へ)。
- 作った呼び名のどれにも、本来の言い方が既にあった。「名前が無いもの」はまれで、呼び名を作ってよい規則は、本来の言い方を探す手を省かせる。
- 規則の文そのものにある和語(全体の CLAUDE.md と skill に、道具5か所・置き場24か所など)も、AI が写して広げる元になる。これはタスク 0078 の範囲を広げる話なので、PL に知らせる。

- 39行目は逆効果だった。入れたときの目的は、例えをその会話の中だけに抑えることだったが、そうならなかった(利用者の言葉「本来の目的は、喩えをセッション内のみに抑えたかっただけなのに、そうならなかった」)。39行目の呼び名の部分を消し、名前の無いものは本来の言い方(IT の用語・一般の語)を探して指す形にする。
- 抑えられなかったわけ: 写し・置き場・道具のような和語は、辞書にある普通の語に見えるので、AI は例えや作った呼び名だと気づかず、39行目が当たらなかった。チケットや skill に書かれた語は、次のセッションでは、そのリポジトリの決まった言葉として読まれ、写された。

- 154行目「言葉は、広く使われている呼び名で書いている。」も、方言を生みうる。どこで広く使われているかを言っていないので、AI は「道具」を広く使われている語と読める。前の形「いちばんありふれた言葉で指している」は、同じわけで 2026-10-30(bf897e7)にこの形になったが、その後も LogiFee のチームは 2026-11-13 に「道具」「写し」を使った(利用者の言葉「『スクリプト』を『道具』と言うこと それが『ありふれた言葉』だと思っているのかも知れない」)。
- 155行目「新しい呼び名を作る前に、同じ意味の IT の用語を調べ」も、39行目と同じわけで当たらない。AI は「道具」を選ぶとき、新しい呼び名を作っているとは思わない。規則は、名前を作るときでなく、概念ごとに「IT の用語があれば、その用語で書く」と当たる形にする。
