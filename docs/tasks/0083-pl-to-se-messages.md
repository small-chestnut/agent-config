## 壁打ち

### 固まったこと

- 話の場面: チームがもう動いているタスクについて、利用者が PL に、疑問や要望を後から話した。
- タスクの設計判断を負うのは SE。PL の役割はチームの管理。
- きっかけ: LogiFee の R-0784 のチーム(2026-11-13〜14)。SE が「PL に決めてほしい」と手段の問い(要確認ファイルの列の形、案件の依頼者を決めるときに自社宛ての請求書を数えるか、など)を送り、PL が自分の判断で答えて、SE はそれに従って方針を変えた。そのうち1つは誤りだった。PL は上海の関連会社を「自社」と読み、決まり(最初の請求書の請求先)に無い除外を足した。利用者の言葉は「私の言葉そのものではなく、あなた自身の判断で、SEの動きを訂正しているように見える」。
- 利用者の考え: PL・SE・PG・QA の役割の受け持つ範囲を、はっきり切り分けたい。
- 利用者の案: task-team とは何かを書いた、4つの役割が共通で読む skill を置き、作業ごとに各役割がしてよいか(◯✕)を表にする。
- 案への SE の見立て: 効く。今の skill は役割ごとに自分の受け持ちだけを書き、ほかの役割が何を受け持つかを書いていないので、SE は手段を PL に回し、PL はそれに答えた。1枚の表を全員が読めば、手段の決めは SE だけと、どの役割にも見える。
- 共通で読ませる仕組みは既にある。SE・PG・QA の skill を読んだ直後に、フックが skill `task-team-messaging` を渡している(`claude/hooks/add_messaging_skill_to_team_roles.py`・ADR 0071-1)。
- PL の動きは、今の決まり(skill `task-team-lead` 18行目「タスクの中身には答えていない」)に反する。
- 原因: 今の決まりは、どちらの側も一般の形にとどまり、SE が PL に決めを求める場面を書いていない。PL の側(skill `task-team-lead`)には、SE から決めを求められたときにどうするかの行が無い。SE の側(skill `task-team-se`)には、手段を PL に回さない行が無い。全体の CLAUDE.md 187・188行目は「手段は自分で決める・足りない目的と『なぜ』は利用者に聞く」だが、task-team の中で PL を利用者の代わりと読める。

### 今の決まり(skill `task-team-lead` の行番号)

PL が設計方針を決めて SE に渡すのは、今の決まりでも禁じている。PL が持つのは「話題がどのタスクに当たるかまで」で、タスクの中身には答えない(18行目・ADR 0056-1)。
