# agent-config

目的: 新しいシステムを開発するとき、そのリポジトリの CLAUDE.md を作りこまなくても、agent-config の設定を読めば、すぐに AI 駆動開発に最適な環境ができること。

そのために、Claude Code の設定として、次の3つを置く。

- 全プロジェクト共通の指示(`CLAUDE.md`)
- 作業ごとの手順(skill。呼ばれたときだけ読み込まれる)
- 意図しない破壊的操作を、設定で機械的に止める安全設定(deny ルール・hooks・サンドボックス)

## 構成

```
agent-config/
├── claude/
│   ├── user-settings.json     # → 各 Claude 設定ディレクトリの settings.json(マシン保護層)
│   ├── project-settings.json  # → 各リポジトリの .claude/settings.json にコピーしてコミット
│   ├── CLAUDE.md              # → 各 Claude 設定ディレクトリの CLAUDE.md(プロンプト層・全プロジェクト共通)
│   ├── skills/<名前>/SKILL.md  # → 各 Claude 設定ディレクトリの skills/<名前>/SKILL.md(手順。呼ばれたときだけ読み込まれる)
│   └── hooks/                 # → 各 Claude 設定ディレクトリの hooks/(settings.json の hooks が走らせるスクリプト)
├── tests/                     # hooks と skill のテスト(python -m unittest discover -s tests)
├── install.ps1                # Windows 用配置スクリプト
└── install.sh                 # WSL2 / Linux / macOS 用(Codespaces dotfiles でも自動実行される)
```

## 使い方

```
git clone <このリポジトリ> && cd agent-config
# Windows
powershell -ExecutionPolicy Bypass -File .\install.ps1
# WSL2 / Linux / macOS
./install.sh
```

- 既存ファイルと差分がある場合は diff を表示して確認してから上書きする。`-Yes`(install.sh は `--yes`)を付けると尋ねずに上書きする
- 設定は**次のエージェントセッション起動時から**有効

## 複数アカウントを使い分ける場合

Claude Code は `settings.json`・`CLAUDE.md`・`skills/` を、環境変数 `CLAUDE_CONFIG_DIR` が指す
ディレクトリから読む(未設定なら `~/.claude`)。ログイン情報もそこに保存されるため、
別ディレクトリを指定すれば別アカウントで並行して起動できる。

**そのディレクトリには安全設定が何も入っていない。** install スクリプトで配置しないと、
rm の再帰削除も force push も素通りする。

install スクリプトは `~/.claude` に加えて `~/.claude-work` にも配置する。
ただし**そのディレクトリが既に存在するときだけ**なので、他のマシンには影響しない。
別名を使うなら install.ps1 / install.sh の `.claude-work` を書き換える。

```
# 会社アカウント側を起動する例(このウィンドウの間だけ有効)
$env:CLAUDE_CONFIG_DIR = "$HOME\.claude-work"; claude
```

セッション記録と自動メモリも `CLAUDE_CONFIG_DIR` の下(`projects/`)に移る。
既存の履歴を引き継ぎたいプロジェクトは、そのプロジェクトのディレクトリだけを
ジャンクションで共有する(`mklink /J`。管理者権限は不要)。

## 運用ルール

1. **ルールの編集はこのリポジトリ側で行う**。`~/.claude/settings.json` を直接編集しない
   (マシンごとに差分が生まれ、テンプレートの意味がなくなる)
2. ただし Claude Code は許可プロンプトで「常に許可」を選ぶと `~/.claude/settings.json` に
   allow ルールを書き込むため、自然にドリフトする。install 時の diff で気づいたら、
   残したい変更はリポジトリに取り込み、不要なら上書きする
3. **秘密情報(API キー等)は絶対にコミットしない**。`env` セクションは使わない
4. 危険なコマンドがルールをすり抜けたのに気づいたら、その場でルールを追加してコミットする
5. **ゴミ箱を空にするのは人間だけ**。エージェントの削除は trash(ゴミ箱)経由なので
   間違いに気づいたら `trash-restore` で戻せる。ディスクが逼迫したら自分で
   `trash-empty` を実行する(エージェントには deny 済みで実行させない)

## 3層の守り(このリポジトリがカバーする範囲)

| 層 | 手段 | 守るもの |
|---|---|---|
| マシン保護層 | `~/.claude/settings.json` ほか(このリポジトリ) | ローカルマシン |
| ポータブル層 | 各リポジトリにコミットする `.claude/settings.json` | clone 先のあらゆる環境 |
| サーバー側 | GitHub branch protection・トークン最小権限(**このリポジトリ外**) | リモートの共有状態 |

force push などサンドボックスを捨てても取り消せない操作は、サーバー側の層でも必ず塞ぐこと。

## Claude Code テンプレートの意図

3色の信号として設計している:
**復元できる操作は allow(青)、共有状態に触れる操作は ask(黄)、復元できない操作は deny(赤)**。

- `allow`: `trash` 系(ゴミ箱への削除)。復元可能な削除は摩擦なしで通す。
  これにより「削除して」という正当な依頼はゴミ箱経由で満たされ、エージェントが
  deny を迂回して `find -delete` 等の見慣れない手段に流れる誘因もなくなる
- `deny`: rm の再帰削除(`-r` / `-R` / `-fr` / `--recursive`、フラグ後置形も含む)/
  force push(`--force` / `-f`、フラグ後置形も含む)/ `git reset --hard` / `git clean` /
  `git checkout --` / `git stash drop・clear` / `terraform destroy` /
  ゴミ箱を完全消去する `trash-empty`・`trash-rm` /
  設定ファイル自体の編集(`Edit(~/.claude/settings.json)` 等。エージェントが自分の
  ルールブックを書き換えて deny を外す経路を塞ぐ)/
  PowerShell の `Remove-Item -Recurse` 系。deny は allow やモードより常に優先され、
  ユーザーが会話で許可しても解除されない(ルール変更はこのリポジトリ経由で行う)
- `ask`: `git restore`・`git push --force-with-lease` は毎回確認。ふつうの `git push` は確認しない
  (リモートの履歴を消す push は下の PreToolUse フックが止める)。
  履歴書き換えを依頼するときは `--force-with-lease` を使い、プロンプトで承認して通す
  (素の `--force` は塞いだまま。安全版の with-lease で用が足りるため)
- パターンの仕様: ワイルドカード `*` は任意の位置に置ける。` *`(空白あり)は
  空白区切りを要求し、`*`(空白なし)は要求しない(`:*` は末尾 ` *` の別記法)
- 限界: 組み合わせ短フラグ(`rm -vrf` 等)は文字列パターンでは表現できない。push については
  `hooks/block_history_erasing_push.py`(PreToolUse)がコマンドを読み、リモートの履歴を消す push
  (`-fu`・`+main`・`:main`・`--delete`・`--mirror`・`--prune` 等)を止め、`--force-with-lease` は
  どの位置にあっても確認に回す
- 私用テンプレートのため、安全ルール以外の個人設定も user-settings.json に同居させている:
  - `extraKnownMarketplaces`: 公式プラグインカタログの登録。**マーケットプレイス登録を
    消すと、そこから入れたプラグインもアンインストールされる**仕様なので、テンプレートで
    常に維持する(削除しないこと)
  - `skipWorkflowUsageWarning`: Workflow 初回警告の抑止
  - VOICEVOX ツールの allow: `tts` MCP サーバーを設定していないマシンでは
    何にもマッチしないだけで無害

## プロンプト層(CLAUDE.md)の意図

deny ルールやサンドボックスが「実行を機械的に止める層」なのに対し、CLAUDE.md は「モデルの振る舞いを指示で誘導する層」。
規則そのものは CLAUDE.md・skill・hooks の冒頭の説明にあり、ここには、どの規則かと、その理由だけを書く。ADR を書いた決定の理由は、その ADR にある。

- **プロンプト層は「お願い」であって「強制」ではない**。文脈次第の逸脱や
  プロンプトインジェクションで破られ得るため、enforcement をここに移さないこと。
  役割は、deny に到達する前に安全な行動(ブランチ運用・削除前の説明・with-lease)を
  選ばせること
- **短く保つ**。項目が増えるほど1項目あたりの効きが薄まる。安全規律は10行前後を維持し、
  CLAUDE.md 全体は 200 行を超えない(Claude Code 公式の目安)。書き方と、規則を足す・消す条件は
  skill `prompt-structure` に従う
- **手順は skill に出す**。CLAUDE.md は毎セッション全文が読み込まれるが、
  `claude/skills/<名前>/SKILL.md` は本文が呼ばれたときだけ読み込まれる。
  CLAUDE.md からは指さず、いつ使うかを skill の description に書く(skill の一覧と description は毎回読み込まれる)
- **同じ規則は、文書をまたいでも1か所にだけ書く**。グローバルの CLAUDE.md にある規則は skill に重ねず、
  いくつもの skill が使う規則は共通の skill に置く(SE・PG・QA の知らせ方は `task-team-messaging`)。
  README のこの節と次の節も、規則を言い直さない。
  利用者の理由は「記述が重複しているものは消すべきだし（そもそも二重管理になるし）」
- **CLAUDE.md の原則3「開発」は、各リポジトリを、作業のついでに AI 駆動開発向きの形へ少しずつ寄せる規則**
- **ソースは業務のまとまり(モジュール)ごとのフォルダに置き、ほかのモジュールからは公開の入口だけを使う(モジュラーモノリス)**(ADR 0012-1・0012-2)。
  利用者の理由と、人の開発の定石との関係は、ADR にある
- **用語集(`docs/用語集.md`)に、業務の言葉とコードの名前を1対1で並べる(ユビキタス言語)**。
  利用者の理由は「用語集を作っている理由が、これもまた、ユビキタス言語を策定することによって、リポジトリ内に、例えや比喩が混入することを防ぐため」
  IT の用語を、リポジトリで形か意味を決めたものだけに絞る理由は「だからといって、用語集に、ITドメインのテクニカルターム、これらをすべて載せるわけにはいかない」
  「用語集が、ITのテクニカルタームの辞書になってしまっては困る。そんなものを読み切れるわけはないし、そもそも、テクニカルタームの最も正確な定義は、あらためて用語集に書くまでもなく把握している」。
  利用者が挙げた例は DB のスキーマで、会話で「箱」と例えても、スキーマにはスキーマという、はっきり定義された用語がある
- プロジェクト単位で効かせたい場合は、各リポジトリ直下に `CLAUDE.md` を
  コミットする(project-settings.json と同じ配布モデル)
- **作業するリポジトリの決まりは、agent-config の規則に勝つ**(ADR 0004-1)。
  deny ルールとフックは文書の規則では外れないので、リポジトリの決まりに従っても、それらが止める操作は止まったまま
- **決まりの1行の長さは、フック `hooks/check_rule_length.py` が数える**。「短く」と書くだけでは、モデルの判断で長い文が通るため
- **決まりの文書に足した行は、フック `hooks/ask_removable_words.py` が問い返す**。モデルは書いている最中には冗長さに気づけず、
  1か所を指して問われると気づけるため
- **シェルから書いた決まりの文書にも、同じ2つを、フック `hooks/check_rule_documents_changed_by_shell.py` が掛ける**。
  上の2つは Edit / Write にだけ掛かり、Bash や PowerShell で書いた行は素通りするため。
  コマンドに出てこないパスへ書くスクリプトは、cwd のリポジトリの分しか見えない
- **終わる前の確かめは、Stop フック `hooks/require_verify_before_stop.py` が守らせる**(ADR 0011-1・0011-2)。
  CLAUDE.md に「確かめてから終える」と書くだけでは、モデルの判断で確かめずに終えることがあるため(公式の手引き
  https://code.claude.com/docs/en/best-practices も、例外の無い決まりはフックに置くよう勧める)。
  動きは `docs/specs/require_verify_before_stop.py.md` にある。ツールを使わずに8回続けて止めると、Claude Code がターンを終わらせる

## セッションの役割分割(PL / SE / PG / QA)の意図

skill `task-team-lead`・`task-team-se`・`task-team-pg`・`task-team-qa` と、SE・PG・QA に共通の知らせ方の `task-team-messaging` は、
1つのリポジトリへのタスクを、役割ごとに分けたセッションで回す手順。コードを書くタスクも、コードの無いタスク(情シス的な作業など)も同じ仕組みで回す。
利用者(PM)がタスクを PL に渡し、PL がタスクごとにチームを起こし、SE(要件定義・設計)→ PG(実装)→ QA(コードレビュー)の順に、
子セッションどうしがターンを渡す。大きな変更だけ、SE の後に QA の設計レビューが入る。
規則そのものは各 skill にあり、ここには、どの規則かと、その理由だけを書く。

- **なぜサブエージェントでなくセッションか**。利用者が開いて、口を挟み、止められる。
  SE が利用者に質問できる。終わったチームは archive で消える
- **1リポジトリに PL が1つで、チームはタスクごとに起こして閉じる**。
  サイドバーに残るのは PL と進行中のチームだけなので、セッションが散らからない
- **受け皿は、タスクが触るリポジトリ**。特定のリポジトリに紐づかないタスクは、記録だけを置く専用の
  git リポジトリ(例: `tasks`)を1つ作り、そこに PL セッションを開く。コードを書かないので worktree は要らず、
  子セッションが PL と同じフォルダで動くので、記録は main に直接コミットする(CLAUDE.md 原則1 の例外)
- **外部のシステムの設定を変える操作は、PG が実行の直前に利用者に確かめる**。アカウント・DNS・課金などの
  設定は git の外にあり、元に戻せないことがある(CLAUDE.md 原則1 の延長)
- **利用者が手を動かすときは、頼む前に、何を・なぜ・全体の進捗を説明する**。利用者は PM として
  何を・なぜを決めるが、実装の水準の前情報は持っていない。PM の水準と実装の水準をつなぐ説明が無いと、
  言うとおりにやるか、何をしているのか・大丈夫かを聞き続けるかの2択になる
- **PL は利用者が自分で開き、タスクも PL に直接書く**。別のセッションから起こされたセッションは、
  その依頼で始まった turn では子セッションを起こせない(アプリの制約。試運転で確かめた)
- **子セッション3つは、利用者が書いたターンの中で全部起こす**。子セッションの知らせで始まったターンからも
  新しいセッションは起こせない(同じく試運転で確かめた)。SendMessage は知らせで始まったターンでも使えるので、
  QA と PG は先に起こしておき、依頼はあとから送る
- **ターンの受け渡しは、PL を通さず子セッションどうしが SendMessage でする**。PL が次のターンへの依頼を
  出し忘れると、レビューや直しが終わったままチームが止まる。PL を通しても速くならず、忘れる場所が1つ増えるだけになる。
  知らせを記録のパスと読む節と頼むことだけにする(skill `task-team-messaging`)のは、QA に SE や PG の思考が入らないようにするため
- **PL は、タスクの文が受けている PL の答えを、言葉のまま SE に渡す**。
  利用者の理由は「私は、私自身、曖昧な状態のままタスクにしているし、あなたの返答を聞くことによって、タスクの要否を判断することがあるのだけど」。
  利用者が挙げた例は用語集で、「用語集について聞いたとき、「AI駆動開発に、ユビキタス言語の策定は有効ではありません」とあなたが返していたなら、用語集自体を廃止するようなタスクを作っていたと思うんだけど」
- **利用者の依頼は、決まった動きに戻すもの(エラーや、仕様・規則と違う動きを直す)だけをすぐにタスクにし、ほかは「タスクにして」と言われるまで壁打ちにする。壁打ちの後のタスクの文は、PL がまとめる**。
  利用者の理由は「一旦そこで壁打ちを挟まないと、私自身の理解が曖昧なままタスクにして、なおかつ、それがAI駆動開発に逆効果であるにもかかわらずタスクとして走り始めてしまうのが嫌なんだ」。
  「タスクにして」と言うまでは全部アイデアとして扱う案について「2. にしたほうが、あなたが導線を混乱せずに済むように思えるが、どうだろうか」
  「要件のように命令形で私が言った場合であっても、あなたが「いや、この要件は、リポジトリの命題に沿っていない」という私見を述べることができるよね」。
  すぐにタスクにする道について「明示的に即タスクにする導線も欲しいんだよな」「もう壁打ちはいらない、いいからあなたの裁量でやりなさい、みたいなケース」
  「もしこれが業務システムであるなら、「この画面で出たエラーを直して」というのは、もはやあなたの裁量でやってほしい確定タスクになるわけだよね」。
  まとめにする理由は「「言葉のまま」というのが、ちょっと曖昧で不安　壁打ちの過程で訂正した、私の誤った認識まで入る必要はないように思うのだが」
- **QA は、Anthropic 公式の code-review を1回かけるだけで、再レビューはしない**。code-review は確からしさの
  低い指摘・細かい指摘・前からある問題を出さず、1回で終わる作り。
  自作のレビュー基準のもとで AI 同士のレビューが完璧を目指して10往復以上続き、利用者に実装が届かず、
  使用量だけを食っていたため。AI だけでタスクを最後まで進めるための仕組みなので、往復の上限で利用者に戻すこともしない
- **テストを流す時と量は、継続的デリバリーのデプロイパイプラインと、テストの大きさ(小・中・大)の定石に沿う**(ADR 0009-1・0009-2・0009-3)。
  決まりはグローバルの CLAUDE.md 原則3 にあり、task-team を使わない1つだけのセッションも同じ時と量で流す。定石と、そこから外れた所の理由は、ADR にある。
  利用者が「タスクのさばけ具合が遅い」「テストやりすぎじゃない？」と感じた。原因は、全部のテストや大きい UI の
  テストを、作業中・レビュー・取り込み・リリースのたびに流し、同じ PC で複数の QA と PG が同時に流して
  互いに遅くなることだった。テストの流し方を定石を調べずにその場で足し引きしていたので、定石に揃えた
- **作るテストと作らないテストは、SE が設計のテスト一覧で決め、PG はそのとおりに作り、QA が多すぎと足りなさを指摘する**(ADR 0005-1)。
  理由は ADR にある
- **このリポジトリの目的とのずれは、PL がやるかを利用者に聞かずにタスクにして回す**。
  決まりは、目的がこのリポジトリのものなので、このリポジトリの CLAUDE.md に置く。task-team-lead には、リポジトリの決まりで
  聞かずに回すタスクの回し方だけを置く。利用者の理由は「乖離があれば、タスクを立てればいいよね？」
  「で、そのときに、私にやるべきかどうかなんて聞かなくていいよね？」「AI駆動開発　"AI"ですよ？人間じゃなくて」「なら、俺に聞かなくていいよね」
- **後から変えにくい設計の決定は、SE が ADR に提案し、QA が設計レビューで採用にしてから PG が実装する(ADR駆動)**(ADR 0004-1・0007-1)。
  利用者に採用を聞かない理由は「AI駆動開発　"AI"ですよ？人間じゃなくて」「なら、俺に聞かなくていいよね」。
  PL は設計を読まないので、採用にしない。置き場・番号・採用する人のほかの理由は、ADR にある
- **ADR で決めた所には、その ADR の番号を付け、SE はその番号から ADR を引く**(ADR 0006-1・0006-2・0006-3)。
  利用者の理由と、読む ADR の数がタスクの数に比例して増えない仕組みは、ADR にある
- **機能の今の動きは、モジュールごとの仕様1つに残し、動きを変えるタスクのたびに SE が直す(spec-anchored)**(ADR 0010-1・0010-2)。
  利用者の理由と、置き場の定石は、ADR にある
- **受け渡しは対象リポジトリの `docs/tasks/<タスク名>.md` だけ**。PL がタスクを始めるとき置き場と根拠の行を利用者に伝えるのは、
  PL が決まりを読み違えても、利用者が作業の前に気づけるようにするため。各役割は会話を共有しない。QA は SE から fork せず fresh で起こすので、
  SE の迷いや捨てた案が QA に入らず、独立したレビューになる
- **モデル**(skill `task-team-lead`)。PL は進捗管理だけなので Fable 級は要らない。
  子セッションは起こした側のモデル以下しか選べないため、PL のモデルが上限になる。
  Fable が要る設計は、利用者が SE セッションのモデルを手で上げる
- **PL は、タスクが終わるたびに、終わったタスクだけを捨てるように会話を圧縮する**(/compact)。
  空にすると(/clear)メッセージ履歴が消えて不便なので、圧縮する。圧縮なら文脈も節約でき、履歴も画面に残る。
  Claude からは圧縮を起こせないので、PL は完了報告に貼って送るだけの1行を付け、利用者が報告を読んでから送る。
  直前に開いたファイルは圧縮のあと読み直されるので、終わったタスクの記録の中身が戻ることはある。
  子はタスク1つで終わり、長引いたときだけ自動圧縮に任せる。セッションを使い回して一定割合で引っ越す運用は、
  引き継ぎ文書を最初から書くこの形なら要らない

## サンドボックス環境への自動配布

- **GitHub Codespaces**: Settings → Codespaces → dotfiles にこのリポジトリを指定すると、
  コンテナ作成時に `install.sh` が自動実行される
- **自前 Docker イメージ**: ビルド時にこのリポジトリを clone して `install.sh` を実行する
