# agent-config

目的: 新しいシステムを開発するとき、そのリポジトリの CLAUDE.md を作りこまなくても、agent-config の設定を読めば、すぐに AI 駆動開発に最適な環境ができること。

そのために、AI コーディングエージェント(Claude Code / Codex CLI)の設定として、次の3つを置く。

- 全プロジェクト共通の指示(`CLAUDE.md`・`AGENTS.md`)
- 作業ごとの手順(skill。呼ばれたときだけ読み込まれる)
- 意図しない破壊的操作を、設定で機械的に止める安全設定(deny ルール・hooks・サンドボックス)

## 構成

```
agent-config/
├── claude/
│   ├── user-settings.json     # → 各 Claude 設定ディレクトリの settings.json(マシン保護層)
│   ├── project-settings.json  # → 各リポジトリの .claude/settings.json にコピーしてコミット
│   ├── CLAUDE.md              # → 各 Claude 設定ディレクトリの CLAUDE.md(プロンプト層・全プロジェクト共通)
│   ├── skills/<名前>/SKILL.md  # → 各 Claude 設定ディレクトリの skills/<名前>/SKILL.md(手順。呼ばれたときだけ読み込まれる)
│   └── hooks/                 # → 各 Claude 設定ディレクトリの hooks/(settings.json の hooks が走らせるスクリプト)
├── codex/
│   ├── safety-snippet.toml    # ~/.codex/config.toml に手動マージする安全設定(自動配置しない)
│   ├── readonly.config.toml   # → ~/.codex/readonly.config.toml(調査専用プロファイル)
│   └── AGENTS.md              # → ~/.codex/AGENTS.md(プロンプト層・全プロジェクト共通)
├── tests/                     # hooks と skill のテスト(python -m unittest discover -s tests)
├── install.ps1                # Windows 用配置スクリプト
└── install.sh                 # WSL2 / Linux / macOS 用(Codespaces dotfiles でも自動実行される)
```

## 使い方

```
git clone <このリポジトリ> && cd agent-config
# Windows
powershell -ExecutionPolicy Bypass -File .\install.ps1
# WSL2 / Linux / macOS
./install.sh
```

- 既存ファイルと差分がある場合は diff を表示して確認してから上書きする。`-Yes`(install.sh は `--yes`)を付けると尋ねずに上書きする
- 設定は**次のエージェントセッション起動時から**有効

## 複数アカウントを使い分ける場合

Claude Code は `settings.json`・`CLAUDE.md`・`skills/` を、環境変数 `CLAUDE_CONFIG_DIR` が指す
ディレクトリから読む(未設定なら `~/.claude`)。ログイン情報もそこに保存されるため、
別ディレクトリを指定すれば別アカウントで並行して起動できる。

**そのディレクトリには安全設定が何も入っていない。** install スクリプトで配置しないと、
rm の再帰削除も force push も素通りする。

install スクリプトは `~/.claude` に加えて `~/.claude-work` にも配置する。
ただし**そのディレクトリが既に存在するときだけ**なので、他のマシンには影響しない。
別名を使うなら install.ps1 / install.sh の `.claude-work` を書き換える。

```
# 会社アカウント側を起動する例(このウィンドウの間だけ有効)
$env:CLAUDE_CONFIG_DIR = "$HOME\.claude-work"; claude
```

セッション記録と自動メモリも `CLAUDE_CONFIG_DIR` の下(`projects/`)に移る。
既存の履歴を引き継ぎたいプロジェクトは、そのプロジェクトのディレクトリだけを
ジャンクションで共有する(`mklink /J`。管理者権限は不要)。

## 運用ルール

1. **ルールの編集はこのリポジトリ側で行う**。`~/.claude/settings.json` を直接編集しない
   (マシンごとに差分が生まれ、テンプレートの意味がなくなる)
2. ただし Claude Code は許可プロンプトで「常に許可」を選ぶと `~/.claude/settings.json` に
   allow ルールを書き込むため、自然にドリフトする。install 時の diff で気づいたら、
   残したい変更はリポジトリに取り込み、不要なら上書きする
3. **秘密情報(API キー等)は絶対にコミットしない**。`env` セクションは使わない
4. 危険なコマンドがルールをすり抜けたのに気づいたら、その場でルールを追加してコミットする
5. **ゴミ箱を空にするのは人間だけ**。エージェントの削除は trash(ゴミ箱)経由なので
   間違いに気づいたら `trash-restore` で戻せる。ディスクが逼迫したら自分で
   `trash-empty` を実行する(エージェントには deny 済みで実行させない)

## 3層の守り(このリポジトリがカバーする範囲)

| 層 | 手段 | 守るもの |
|---|---|---|
| マシン保護層 | `~/.claude/settings.json` ほか(このリポジトリ) | ローカルマシン |
| ポータブル層 | 各リポジトリにコミットする `.claude/settings.json` | clone 先のあらゆる環境 |
| サーバー側 | GitHub branch protection・トークン最小権限(**このリポジトリ外**) | リモートの共有状態 |

force push などサンドボックスを捨てても取り消せない操作は、サーバー側の層でも必ず塞ぐこと。

## Claude Code テンプレートの意図

3色の信号として設計している:
**復元できる操作は allow(青)、共有状態に触れる操作は ask(黄)、復元できない操作は deny(赤)**。

- `allow`: `trash` 系(ゴミ箱への削除)。復元可能な削除は摩擦なしで通す。
  これにより「削除して」という正当な依頼はゴミ箱経由で満たされ、エージェントが
  deny を迂回して `find -delete` 等の見慣れない手段に流れる誘因もなくなる
- `deny`: rm の再帰削除(`-r` / `-R` / `-fr` / `--recursive`、フラグ後置形も含む)/
  force push(`--force` / `-f`、フラグ後置形も含む)/ `git reset --hard` / `git clean` /
  `git checkout --` / `git stash drop・clear` / `terraform destroy` /
  ゴミ箱を完全消去する `trash-empty`・`trash-rm` /
  設定ファイル自体の編集(`Edit(~/.claude/settings.json)` 等。エージェントが自分の
  ルールブックを書き換えて deny を外す経路を塞ぐ)/
  PowerShell の `Remove-Item -Recurse` 系。deny は allow やモードより常に優先され、
  ユーザーが会話で許可しても解除されない(ルール変更はこのリポジトリ経由で行う)
- `ask`: `git restore`・`git push --force-with-lease` は毎回確認。ふつうの `git push` は確認しない
  (リモートの履歴を消す push は下の PreToolUse フックが止める)。
  履歴書き換えを依頼するときは `--force-with-lease` を使い、プロンプトで承認して通す
  (素の `--force` は塞いだまま。安全版の with-lease で用が足りるため)
- パターンの仕様: ワイルドカード `*` は任意の位置に置ける。` *`(空白あり)は
  空白区切りを要求し、`*`(空白なし)は要求しない(`:*` は末尾 ` *` の別記法)
- 限界: 組み合わせ短フラグ(`rm -vrf` 等)は文字列パターンでは表現できない。push については
  `hooks/block_history_erasing_push.py`(PreToolUse)がコマンドを読み、リモートの履歴を消す push
  (`-fu`・`+main`・`:main`・`--delete`・`--mirror`・`--prune` 等)を止め、`--force-with-lease` は
  どの位置にあっても確認に回す
- 私用テンプレートのため、安全ルール以外の個人設定も user-settings.json に同居させている:
  - `extraKnownMarketplaces`: 公式プラグインカタログの登録。**マーケットプレイス登録を
    消すと、そこから入れたプラグインもアンインストールされる**仕様なので、テンプレートで
    常に維持する(削除しないこと)
  - `skipWorkflowUsageWarning`: Workflow 初回警告の抑止
  - VOICEVOX ツールの allow: `tts` MCP サーバーを設定していないマシンでは
    何にもマッチしないだけで無害

## Codex CLI テンプレートの意図

Codex は Claude Code のようなコマンド単位の deny リストではなく、
**サンドボックス境界 + 承認ポリシー**で守る設計。

**最重要の注意: `~/.codex/config.toml` は Codex 本体が状態を書き込むアプリ管理ファイル**
(プラグイン・信頼済みプロジェクト・MCP サーバー・デスクトップ設定などが入る)。
テンプレートで丸ごと上書きしてはいけない。そのため install スクリプトは config.toml に
触らず、安全設定は `safety-snippet.toml` を見ながら**手動でマージ**する。

- `approval_policy`: `"untrusted"`(毎回確認)が最も安全。`"on-request"` は緩め
- `sandbox_mode = "workspace-write"` + `network_access = false`: 作業ディレクトリのみ
  書き込み可・ネットワーク遮断。なお新方式の `default_permissions` /
  `[permissions.<name>]` プロファイルもあるが、旧方式とは併用不可
- `writable_roots` にネットワーク共有を足すと被害範囲がマシン外に広がるので慎重に
- 調査だけさせたいときは `codex --profile readonly`(一切書き込ませない)
- `shell_environment_policy` でサブプロセスに渡す環境変数を最小化
  (KEY/SECRET/TOKEN を含む変数は Codex のデフォルトでも除外される)
- `danger-full-access` + `approval_policy = "never"` は使い捨てコンテナ内以外で使わない
- プロジェクト側の対応物: `AGENTS.md`(モデルへの指示。強制力はない)と
  `.codex/config.toml`(プロジェクトを trust した場合のみ読み込まれる)

## プロンプト層(CLAUDE.md / AGENTS.md)の意図

deny ルールやサンドボックスが「実行を機械的に止める層」なのに対し、CLAUDE.md /
AGENTS.md は「モデルの振る舞いを指示で誘導する層」。

- **プロンプト層は「お願い」であって「強制」ではない**。文脈次第の逸脱や
  プロンプトインジェクションで破られ得るため、enforcement をここに移さないこと。
  役割は、deny に到達する前に安全な行動(ブランチ運用・削除前の説明・with-lease)を
  選ばせること
- **短く保つ**。項目が増えるほど1項目あたりの効きが薄まる。安全規律は10行前後を維持し、
  CLAUDE.md 全体は 200 行を超えない(Claude Code 公式の目安)。書き方と、規則を足す・消す条件は
  skill `prompt-structure`(原則 → 目的 → 目指す状態 → 規則の4段)に従う
- **手順は skill に出す**。CLAUDE.md は毎セッション全文が読み込まれるが、
  `claude/skills/<名前>/SKILL.md` は本文が呼ばれたときだけ読み込まれる。特定の作業でしか
  使わない手順(既存プロジェクトの組み替え・ファイルの置き場所・図の描き方など)は skill に置く。
  CLAUDE.md からは指さず、いつ使うかを skill の description に書く(skill の一覧と description は毎回読み込まれる)
- **CLAUDE.md の原則3「開発」は、各リポジトリを AI 駆動開発向きの形に少しずつ寄せる規則**。
  作業のついでに、動かし方・用語集・決定の記録(ADR)を足していく。
  一度に整える作業は含まない(既にあるコード・フォルダ・名前をこの形に直すのは別の変更)
- プロジェクト単位で効かせたい場合は、各リポジトリ直下に `CLAUDE.md` / `AGENTS.md` を
  コミットする(project-settings.json と同じ配布モデル)
- **作業するリポジトリの決まりは、agent-config の規則に勝つ**(ADR 0004-1)。CLAUDE.md の冒頭と AGENTS.md の最初の節に書く。
  agent-config は利用者が AI 駆動開発のために使う私的な規則で、これによって複数の人間が触るリポジトリの
  規則を逸脱するわけにはいかないため。リポジトリの決まりは、コミットされた文書(CLAUDE.md・AGENTS.md・
  README・CONTRIBUTING.md・`docs/` など)に書かれた決まりと、既にあるファイルの並び(ADR の番号など)。
  従ったときは、ぶつかった規則と従った決まりを利用者に1行で伝える。deny ルールとフックは文書の規則では外れないので、
  リポジトリの決まりに従っても、それらが止める操作は止まったまま
- **決まりの1行の長さはフックが数える**。「短く」と書くだけではモデルの判断で長い文が通るため、
  `hooks/check_rule_length.py` が、決まりの文書(名前が CLAUDE.md・AGENTS.md・SKILL.md の
  ファイルと、各リポジトリの `.claude/rule-documents.txt` に1行ずつ書いた glob)を Edit / Write で
  保存するたびに、HEAD から足された箇条書きの行を数え、60 字(`…` のコードは1字)を超えたら
  Claude に知らせる。前からある行と git の外のファイルは数えない
- **決まりの文書に足した行は、フックが問い返す**。モデルは書いている最中には冗長さに気づけず、
  1か所を指して問われると気づけるため、`hooks/ask_removable_words.py` が、決まりの文書を保存する
  たびに、その保存で足した行を並べ、消しても意味が変わらない語を探させる
- **シェルから書いた決まりの文書にも、同じ2つを掛ける**。上の2つは Edit / Write にだけ掛かり、
  Bash や PowerShell で書いた行は素通りするため、`hooks/check_rule_documents_changed_by_shell.py` が、
  コマンドの前(PreToolUse)に決まりの文書の中身を一時ファイルに写し、後(PostToolUse)に見比べて、
  そのコマンドで足された行を数え、問い返す。見るのは、フックの cwd と、コマンドに書かれた絶対パスが
  入っているリポジトリ。コマンドに出てこないパスへ書くスクリプトは、cwd のリポジトリの分しか見えない

## セッションの役割分割(PL / SE / PG / QA)の意図

skill `task-team-lead`・`task-team-se`・`task-team-pg`・`task-team-qa` は、1つのリポジトリへのタスクを、
役割ごとに分けたセッションで回す手順。コードを書くタスクも、コードの無いタスク(情シス的な作業など)も同じ仕組みで回す。利用者(PM)がタスクを PL に渡し、
PL がタスクごとにチームを起こし、SE(要件定義・設計)→ PG(実装)→ QA(コードレビュー)の順に、
子セッションどうしがターンを渡す。大きな変更だけ、SE の後に QA の設計レビューが入る。

- **なぜサブエージェントでなくセッションか**。利用者が開いて、口を挟み、止められる。
  SE が利用者に質問できる。終わったチームは archive で消える
- **1リポジトリに PL が1つ**。PL はタスクごとに SE・PG・QA の3セッションを起こし、終わったら閉じる。
  サイドバーに残るのは PL と進行中のチームだけなので、セッションが散らからない
- **受け皿は、タスクが触るリポジトリ**。特定のリポジトリに紐づかないタスクは、記録だけを置く専用の
  git リポジトリ(例: `tasks`)を1つ作り、そこに PL セッションを開く。コードを書かないので worktree は要らず、
  子セッション3つは `use_worktree: false` で PL と同じフォルダに起こす。子セッションが同じフォルダで動くので、記録は main に
  直接コミットする。この例外は CLAUDE.md 原則1の作業用のブランチの行にある
- **コードの無いタスクは、同じ節と順で回し、確認用のテストは作らない**。SE は実行する手順を操作ごとに
  設計に書き、PG は手順を実行して、受け入れ条件を確かめた結果を書く
- **外部のシステムの設定を変える操作は、PG が実行の直前に利用者に確かめる**。アカウント・DNS・課金などの
  設定は git の外にあり、元に戻せないことがある(CLAUDE.md 原則1 の延長)。PG がするのは、設計にある操作だけ
- **利用者が手を動かすときは、頼む前に、何を・なぜ・全体の進捗を説明する**。利用者は PM として
  何を・なぜを決めるが、実装の水準の前情報は持っていない。PM の水準と実装の水準をつなぐ説明が無いと、
  言うとおりにやるか、何をしているのか・大丈夫かを聞き続けるかの2択になる。SE が設計の手順に、
  操作ごとにする人を書き、利用者がする操作には、ゴールにどうつながるか・なぜ利用者の手でか・
  失敗する条件・終わったら返すことを書く。PG は頼むとき、記録の冒頭のゴール・
  進捗(チームの流れと手順の位置)・何を・なぜを手順より先に出し、ステータスを「利用者の操作待ち」にする。
  PL はそれを見て、PG の会話へのリンクと何のためかの1行を出す
- **PL は利用者が自分で開き、タスクも PL に直接書く**。別のセッションから起こされたセッションは、
  その依頼で始まった turn では子セッションを起こせない(アプリの制約。試運転で確かめた)
- **子セッション3つは、利用者が書いたターンの中で全部起こす**。子セッションの知らせで始まったターンからも
  新しいセッションは起こせない(同じく試運転で確かめた)。QA と PG は最初はターンを待つだけで起こしておき、
  レビュー・実装・直しの依頼は、あとから SendMessage で送る。SendMessage は知らせで始まったターンでも使える。
  PL は3つを起こしたら、3つのセッションの id を各子セッションに渡す
- **ターンの受け渡しは、PL を通さず子セッションどうしが SendMessage でする**。PL が次のターンへの依頼を
  出し忘れると、レビューや直しが終わったままチームが止まる。PL を通しても速くならず、忘れる場所が1つ増えるだけになる。
  PL がするのは、チームを作る・閉じること、マージと push、利用者の判断が要るものの取り次ぎ。
  本番環境に触る作業と、安全(CLAUDE.md 原則1)に触れる指摘だけは、子セッションが PL に戻し、PL が利用者に聞く。
  子セッションどうしの知らせは、記録のパスと読む節と頼むことだけにし、自分の見立てを書かない。
  QA に SE や PG の思考が入らないようにするため
- **QA は、Anthropic 公式の code-review を1回かけるだけで、再レビューはしない**。code-review は確からしさの
  低い指摘・細かい指摘・前からある問題を出さず、1回で終わる作り。設計レビューは、大きな変更(ADR を提案した
  変更・本番環境に触る変更)のときだけ。直したものは見直さず、PG が直したら PL がマージへ進む。
  自作のレビュー基準のもとで AI 同士のレビューが完璧を目指して10往復以上続き、利用者に実装が届かず、
  使用量だけを食っていたため。AI だけでタスクを最後まで進めるための仕組みなので、往復の上限で利用者に戻すこともしない
- **テストを流す時と量は、継続的デリバリーのデプロイパイプラインと、テストの大きさ(小・中・大)の定石に沿う**。
  - 書いている間(手元・PG): 変えた所の小さいテストだけ(数秒〜1分)
  - メインに入れる前: CI が小・中のテストを全部(10分以内・人は待たない)。PL は作業ブランチを push し、
    緑になってからマージする
  - メインに入った後か定時: 大きいテスト(画面を動かす・速さの計測)を CI で。赤ならそのチームがすぐ直すので、
    PL は CI が緑になってからチームを閉じる
  - リリース: テストしない。テスト済みのビルドをそのまま出し、出した後に動いているかだけ確かめる
  - レビュー役(QA)はテストを流さない。コードと記録にある PG の結果を読む

  小・中・大の中身と CI の名前は、リポジトリごとに違うので、各リポジトリの CLAUDE.md に書く。
  利用者が「タスクのさばけ具合が遅い」「テストやりすぎじゃない？」と感じた。原因は、全部のテストや大きい UI の
  テストを、作業中・レビュー・取り込み・リリースのたびに流し、同じ PC で複数の QA と PG が同時に流して
  互いに遅くなることだった。テストの流し方を定石を調べずにその場で足し引きしていたので、定石に揃えた
- **作るテストと作らないテストは、SE が設計のテスト一覧で決め、PG はそのとおりに作り、QA が多すぎと足りなさを指摘する**(ADR 0005-1)。
  基準は `task-team-se` に置き、QA はそれを読む。作るのは、受け入れ条件ごとのテスト・業務の規則の分かれ目ごとの小さいテスト(境界値分析)・
  バグを再現するテスト。内部の作りを確かめるテストは、振る舞いを変えずに作りを直しただけで壊れるので作らない。
  大きさは、確かめられる中で一番小さいもの(小さいほど速く、落ちた原因を絞りやすい)。大きさごとの割合とカバレッジの目標値は、
  どの規則を確かめたかを問わない数字で、多すぎるテストを止められないので置かない
- **後から変えにくい設計の決定は、SE が ADR に提案し、利用者が採用してから PG が実装する(ADR駆動)**(ADR 0004-1)。
  書く対象は、Nygard の5つ(構造・非機能の特性・依存・インターフェース・作り方の技法)に効く決定。
  SE が提案を書いたら、ステータスを
  「利用者の判断待ち(ADR <番号>)」にしてターンを終え、PL が利用者に採用するかを聞き、返事を言葉を変えずに SE に送る。
  本番環境に触る作業と並ぶ、利用者の判断を挟む所。採用した ADR は書き換えず、決定を変えるときは新しい ADR で置き換える。
  ADR は対象のリポジトリの `docs/adr/` にまとめて置く。人が一覧で見渡せ、AI にとっての差は小さいため。
  番号は `<タスクの番号>-<そのタスクの中の連番>`(例: `0004-1`)。タスクから、対応する ADR をすぐ引けるようにするため。
  定石(通し番号)からは外れる。タスクの番号は PL が振る4桁の連番で、記録・子セッション・ブランチの名前の頭に付く。
  task-team を通さない会話では ADR を書かず、タスクにして PL に回す
- **ADR で決めた所には、その ADR の番号を付け、SE はその番号から ADR を引く**(ADR 0006-1)。
  プロンプトは決めた行の末尾(下の行がみな同じ ADR なら見出しの末尾)に「(ADR <番号>)」、コードは決定を守らせる所か
  形にした所の1か所(lint の設定の message・アーキテクチャのテストの名前・型や API の定義のコメント)、どちらも無ければ
  モジュールの CLAUDE.md の行に付ける。SE は、設計で書き換える所に付いた番号の ADR と、新しい ADR の「置き換える: 」の行で
  たどった古い ADR だけを読み(ADR 0006-2)、QA は番号の付け忘れを見る。1つの ADR には決定を1つだけ書き、「決めたこと」は
  どの決定かが分かる1行にして、詳しい文は skill などの決まりを書く文書に任せる(ADR 0006-3)。
  利用者の理由は「タスクがスケールしたときに、1番目のタスクと3000番目のタスクで、一次関数的に、あなたが見るADRが増えてしまうと、
  私が破産する」。「対象: 」の行を「全体」で検索して全部読むやり方では、「全体」の ADR がどのタスクにも当たり、読む量が
  タスクの数に比例して増える。番号は決めた所そのものに付くので、読む ADR の数は書き換える所の数で決まる
- **受け渡しは対象リポジトリの `docs/tasks/<タスク名>.md` だけ**(置き場の決まりがそのリポジトリに
  あればそちら)。PL はタスクを始めるとき、置き場と根拠の行を利用者に1行で伝える。PL が決まりを
  読み違えても、利用者が作業の前に気づけるようにするため。各役割は会話を共有しない。QA は SE から fork せず fresh で起こすので、
  SE の迷いや捨てた案が QA に入らず、独立したレビューになる
- **モデル**: PL・SE・QA = Opus 5.5、PG = Sonnet 5.5。PL は進捗管理だけなので Fable 級は要らない。
  子セッションは起こした側のモデル以下しか選べないため、PL のモデルが上限になる。
  Fable が要る設計は、利用者が SE セッションのモデルを手で上げる
- **PL は、タスクが終わるたびに、終わったタスクだけを捨てるように会話を圧縮する**(/compact)。
  空にすると(/clear)メッセージ履歴が消えて不便なので、圧縮する。圧縮なら文脈も節約でき、
  履歴も画面に残る。終わったタスクだけを捨てるように圧縮するので、進行中のタスクのやりとりは残る。
  Claude からは圧縮を起こせないので、PL は完了報告に貼って送るだけの `/compact` の1行を付け、
  利用者が報告を読んでから送る。直前に開いたファイルは圧縮のあと読み直されるので、終わったタスクの
  記録の中身が戻ることはある。進行中のタスクは、起こしたセッションの一覧と、記録のステータスの行で分かる。
  子はタスク1つで終わり、
  長引いたときだけ自動圧縮に任せる。セッションを使い回して一定割合で引っ越す運用は、
  引き継ぎ文書を最初から書くこの形なら要らない
- **QA を Codex にする案は保留**。Codex はこのアプリのセッションとして起こせず、PL がシェルから
  回す別の仕組みになる。品質の差は確かめていない。QA の手順は skill 1つに閉じてあるので、
  差し替えるときは QA の起こし方だけ変えればよい

- **自前 Docker イメージ**: ビルド時にこのリポジトリを clone して `install.sh` を実行する
