# 原則1: 人間側の最適化

## 目的: リポジトリの目的に逆効果な変更を、利用者の理解が曖昧なまま、作り始めない

### 目指す状態: 設計は、決まった動きに戻す依頼と、利用者が進めると言った後にだけ始まっている(ADR 0056-2)

- エラーや、仕様・規則と違う動きを直す依頼は、壁打ちをせずに設計を始めている。
- PL が聞かずに進めると添えたタスクも、壁打ちをせずに設計を始めている。
- ほかの依頼は、命令の形でも、利用者が設計に進めると言うまで壁打ちにしている。
- 利用者が設計に進めると言ったら、壁打ちの途中でも設計を始めている。
- 逆効果だと思うタスクには、利用者への返答に懸念を1行だけ添えている。

### 目指す状態: 壁打ちで、利用者は、アイデアがリポジトリの目的に効くか逆効果かを、根拠つきで知っている

- 最初のターンで、チケットを作り、効くか逆効果かを答えている。
- リポジトリの目的は、`docs/概要.md` の冒頭か、CLAUDE.md が書くか指すもの。
- リポジトリの目的が見つからなければ、壁打ちの前に利用者に聞いている。
- 効くか逆効果かは、調べた根拠をつけて言い切っている。

### 目指す状態: 壁打ちで固まったことは、会話でなくチケットにある(ADR 0056-5)

- 「要件」の節に、固まった要件を、1つずつ番号と「なぜ」を付けて書いている。(ADR 0085-5)
- 決まっていない問いは、「要件」の節の「決まっていない問い」に書いている。(ADR 0085-5)
- 固まるたびに書き足し、チケットだけをコミットしている。

### 目指す状態: やらないと決まったタスクは、理由が却下の ADR に残っている(ADR 0056-3)

- 利用者がやらないと決めたら、状態「却下」の ADR を書いている。
- 却下の ADR は、「決めたこと」に見送った案を、「理由」に見送った根拠を書く。
- 変更の案が出ないまま話が済んだら、ADR を書いていない。
- どちらも、コミットし、ステータスを「取りやめ」にしている。

# 原則2: AI 側の最適化

## 目的: PG が設計を読むだけで実装でき、QA が要件を読むだけで確かめられる

### 目指す状態: チケットは、決まった形で1か所にある

- チケットは、PL が指した保存先に、この見出しの末尾のテンプレートの形で作る。(ADR 0024-1・0085-5)
- 「PC: 」には、`hostname` の値を書く。チームのいる PC を示す。(ADR 0056-5)
- テンプレートの見出しは消さず、設計を書き終えても空の見出しには「なし」と書く。(ADR 0085-5)
- 保存先に「未着手」か「検討待ち」のチケットがあれば、それを直して使う。(ADR 0047-3)
- PL がコミットされていないチケットのパスを添えたら、それを保存先へ移して使う。(ADR 0047-3)
- PL がほかの PC から続けると添えたら、チケットを読み、「PC: 」を直して続ける。(ADR 0056-5)
- ゴールの節の1行目は、何の話かが分かる1文。(ADR 0056-2)
- ゴールの節に、範囲外を1行で書いている。
- チケットに書くのは、決めたことと、決まっていない問いだけ。捨てた案は ADR だけ。
- 保存先がファイルでなければ、書き方の文書が作業の結果を書く所に、節を書く。(ADR 0051-1)
- 書き足す形なら、「ステータス: 」の行と節を一緒に書き足す。(ADR 0051-1)
- 同じ節が2つ以上あれば、いちばん新しいものを読む。ステータスも同じ。(ADR 0051-1)
- 書き方の文書のほかの決まり(本文の形・進捗の示し方)にも従う。(ADR 0051-1)
- 書き方の文書の決まりとテンプレートがぶつかったら、書き方の文書の方に従う。(ADR 0085-5)
- 保存先がファイルでなくても、ADR は ADR の保存先に書く。(ADR 0024-1)

````markdown
# <タスク名>

ステータス: <壁打ち中 か 設計中>
PC: <hostname の値>

## 進捗

- 利用者待ち: なし
- [ ] 1. やり方を決める(完了条件: <事実>)

## 難しさ

- SE: 高(<理由>)

## ゴール

<何の話かが分かる1文>

範囲外: <1行>

## 要件

### R1 <要件の名前>

- 要件: <利用者と合意した内容>
- なぜ: <利用者と合意した理由>
- 受け入れ条件 R1-1: <テスト名に使える文>

### 分けたタスク

### 決まっていない問い

## 設計

### ADR

### 置くファイルと名前・データ

### 手順

### テスト一覧

| テスト名 | テストサイズ | 受け入れ条件 |
|---|---|---|

### サブタスクの前提

## 実装

## レビュー
````

### 目指す状態: 進捗の節から、サブタスクのつながりと今の状態が図に描ける(ADR 0035-1)

- 進捗の節は、チケットを作るときに、利用者待ちの行と設計のサブタスクだけで作っている。
- 残りのサブタスクは、設計を書くときに足している。
- その下に、サブタスクを `- [ ] <番号>. <サブタスク>(依存: <番号>)(完了条件: <事実>)` の形で並べている。
- 依存には、先に済んでいなければならないサブタスクの番号を「・」で並べている。
- 依存先のサブタスクが無いサブタスクには、`(依存: …)` を書いていない。
- サブタスクのステータスは、まだが `[ ]`、作業中が `[/]`、済みが `[x]`。
- サブタスクは、設計・設計レビュー・利用者が確かめるサブタスク・実装レビューの順。
- 設計のサブタスクの名前は「やり方を決める」。
- 設計レビューのサブタスクの名前は「やり方を見直す」。
- 実装レビューのサブタスクの名前は「できたものを見直す」。
- 設計レビューのサブタスクは、大きな変更のときだけ置いている。
- サブタスクの名前は、利用者が目にする言葉で書いている。
- 完了条件は、件数のような、確かめて言い切れる事実にしている。
- 利用者がするサブタスクは、名前の頭に「あなた: 」を付けている。
- 書き方の文書に進捗の示し方があれば、サブタスクはその形で書いている。
- その形でも、依存と作業中のステータスは、この節の書き方で足している。
- そのときの利用者待ちの行は、「PC: 」の次の行に置いている。

### 目指す状態: サブタスクは、利用者が確かめる単位で切れ、確かめる順に並んでいる(ADR 0035-3)

- サブタスクは、利用者が確かめる単位(データの種類など)で切っている。
- 番号は、利用者が確かめる順に振っている。
- 1つのサブタスクは、完了条件1つで確かめられる大きさにしている。

### 目指す状態: 1つのタスクは、SE・PG・QA のどれも1つの会話で終えられる大きさ(ADR 0085-8)

- 設計の最初に、仕様とコードを読み、この大きさに収まるかを見積もっている。
- 収まらなければ、利用者が確かめる単位で、話題を2つ以上のタスクに分けている。
- 自分のタスクには利用者が最初に確かめるものを残し、ゴールの節を直している。
- 残りは、「要件」の節の「分けたタスク」に、確かめる順に1つずつ見出しを立てている。
- 見出しの下には、ゴールの1文と、そのタスクの要件を、番号と「なぜ」を付けて書く。
- 分けたことは、利用者への返答に1行で書いている。

### 目指す状態: 画面のあるシステムでは、完了条件が利用者の画面に出るもの(ADR 0035-4)

- 完了条件は、利用者が見る画面に出るもの(一覧の件数など)にしている。
- その画面の名前と開き方を、設計の節に書いている。

### 目指す状態: 利用者が SE の会話で聞いて分かった前提が、チケットのサブタスクに残っている(ADR 0056-1)

- 利用者にサブタスクを聞かれたら、答えで分かった前提を、設計の節の「サブタスクの前提」に書き足している。
- 書き足す行は、`<サブタスクの番号>. <前提>` の形。
- チケットがファイルなら、書き足したら、チケットのファイルだけをコミットしている。

### 目指す状態: コードの無いタスクは、手順を実行して結果を確かめている

- 設計の節には、実行する手順を操作ごとに書いている。
- 確かめ方は、手順を実行した結果だけ。受け入れ条件は、実行後に確かめて言い切れる文。

### 目指す状態: 利用者がする操作は、頼むときの説明の元が設計に書いてある

- 設計の手順には、操作ごとに、する人(PG か利用者)を書いている。
- 利用者がする操作には、何を・ゴールにどうつながるか・なぜ利用者の手でかを書いている。
- 同じ操作に、手順と、終わったら利用者が返すことを書いている。
- 元に戻せない操作には、そう書いている。

### 目指す状態: 画面が変わるときだけ、設計に図がある

- 図は、skill `ui-mockup` で描いている。
- 図は SVG か PNG で、チケットと同じフォルダの `<チケットのファイル名(拡張子なし)>/` に置く。
- チケットがファイルでなければ、図と画像は書き方の文書の添付の仕方で付ける。(ADR 0051-1)
- 添付の仕方が無ければ、`docs/tasks/<タスク名>/` に置き、チケットから指す。(ADR 0051-1)

### 目指す状態: 受け入れ条件は、テスト名で言える

- 受け入れ条件は、用語集の言葉で、テスト名に使える文。

### 目指す状態: 要件と意図が、正確に届いている(トレーサビリティ)(ADR 0085-5)

- 利用者と合意した内容は、「要件」の節にだけ書き、ほかの節へ写していない。
- 受け入れ条件は、要件1つに1つ以上を、その要件の下に、番号を付けて書いている。
- 置くファイルと手順の行と、テスト一覧のテストには、元の要件か受け入れ条件の番号を付けている。
- どの要件にも、番号で指す設計の行かテストが、1つ以上ある。

### 目指す状態: 作るテストは、設計のテスト一覧に、数とテストサイズまで決まっている(ADR 0005-1)

- 設計の節に「テスト一覧」の表を置き、テスト名・テストサイズ・受け入れ条件の番号を並べている。
- 受け入れ条件1つに、テスト1つ以上。
- 業務の規則の分かれ目(分岐・計算)ごとに、小のテストを1つ。
- 分かれ目の値の境目は、前後の値も確かめている(境界値分析)。
- バグは、再現するテストを1つ。
- テストサイズは、確かめられる中で一番小さいもの。
- 中は、外部(DB・ネットワーク)との連携を確かめるときだけ。
- 大は、利用者の主な使い方1本につき1つまで。

### 目指す状態: テスト一覧に、要らないテストが無い(ADR 0005-1)

- 一覧のテストは、どれも、1つ前の見出しの規則のどれかで作るもの。
- テストは、このリポジトリのコードを公開インターフェースから呼び、外から見える結果を確かめる。
- 文書だけ・設定だけの変更は、テストを作らず、確かめ方を一覧に書く。

### 目指す状態: 設計は、短く、置く場所と名前まで決まっている

- 設計の節には、置くファイルと名前(skill `module-layout`)・データだけを書いている。

### 目指す状態: 機能の今の動きは、機能ごとに分けた仕様1つにある(ADR 0045-2)

- 動きを変えるときは、設計のコミットで仕様を直している。
- 仕様の無い機能は、タスクで作っている。
- 作るときは、そのタスクで読んだコードの今の動きを書いている。
- 冒頭は `# <機能の名前>`。節は、`## ADR` と `## 動き`。
- 「ADR」の節には、番号と ADR の題を1行ずつ並べる。(ADR 0010-2)
- 2つ以上の機能に効く番号は、効く機能の仕様のどれにも並べる。(ADR 0045-2)
- 仕様には外から見える動きだけを書く。
- 「動き」の節の行は、業務の規則を用語集の言葉で書いた1文。
- SKILL.md などプロンプトがモジュールの中身なら、その文書が仕様。
- プロンプトが仕様なら、番号は行と見出しにだけ付ける。(ADR 0010-2)
- 仕様で足した行・変えた行は、同じ文で受け入れ条件に入れている。

### 目指す状態: 新しい仕組みの前に既にあるものを探す語は、チケットから選んでいる(ADR 0068-1)

- 新しい仕組みの前に探す語は、チケットに出る利用者の語と、新しく作るものの名前。
- 利用者の語は、用語集があれば、そのリポジトリの言葉に引き直して足している。

### 目指す状態: 設計で読む ADR は、書き換える所と、探して当たった所に付いた番号の ADR だけ(ADR 0006-1・0068-1)

- 設計の最初に、書き換える行と、その見出しに付いた ADR の番号を集めている。
- 既にあるものを探して当たった所に付いた番号も集めている。(ADR 0068-1)
- コードを書き換えるときは、仕様の「ADR」の節の番号も集めている。(ADR 0010-2)
- 仕様が無ければ、そのモジュール・テスト・lint の設定を「ADR」で検索している。(ADR 0010-2)
- 書き換えるコードに効く所の番号も集め、作る仕様に並べている。(ADR 0010-2)
- 読むのは、その番号の ADR と、「置き換える: 」でたどった古い ADR だけ。(ADR 0006-2)
- ADR で決めた行には、末尾に「(ADR <番号>)」を付ける設計にしている。
- 見出しの下の行がみな同じ ADR なら、番号は見出しの末尾に付ける。
- ADR が2つ以上なら、「(ADR <番号>・<番号>)」と並べる。
- コードでは、決定を守らせる所か形にした所の1か所に付ける。
- その1か所は、lint の設定の message・アーキテクチャのテストの名前・型や API の定義のコメント。
- 名前に空白や「-」を使えなければ、`ADR_0006_1` の形にする。
- どれにも当たらない決定は、そのモジュールの CLAUDE.md の行に付ける。
- コードか CLAUDE.md に番号を付けたら、仕様の「ADR」の節にも並べる。(ADR 0010-2)
- 決定を置き換えたら、古い番号を新しい番号に付け替える設計にしている。

### 目指す状態: 後から変えにくい決定は、採用した ADR にある(ADR 0004-1・0007-1)

- ADR は、設計の残りより先に、状態「提案」で書いている。
- ADR の直しを頼まれたら、「提案」のまま直すか、「却下」にしている。(ADR 0085-7・0086-1)

### 目指す状態: ADR は、決まった形で1つのフォルダにある

- 保存先は `docs/adr/<ADR の番号>-<英語の短い題>.md`。(ADR 0004-1)
- ADR の番号は `<タスクの番号>-<そのタスクの中の連番>`(例: `0004-1`)。(ADR 0004-1)
- 冒頭は、題の見出しと、「状態: 」「日付: 」「対象: 」の3行。
- 節は、決めたこと / 捨てた案 / 理由。
- 1つの ADR には、決定を1つだけ書く。(ADR 0006-3)
- 決めたことは、どの決定かが分かる1行。詳しい文は skill などに任せる。(ADR 0006-3)
- 捨てた案は、案ごとに1項目で、案と、選ばなかった根拠を書く。(ADR 0050-1)
- 理由は、根拠ごとに1項目で、決めたことを選んだ根拠だけを書く。(ADR 0050-1)
- 状態は、提案・採用・却下・廃止・置き換え済み(<ADR の番号>)。
- 対象は、直すモジュールの名前を「・」で並べるか、「全体」。
- 採用した ADR で書き換えるのは、状態の行だけ。

### 目指す状態: 置き換えた古い ADR へ、新しい ADR からたどれる(ADR 0006-2)

- 決定を変えるときは、新しい ADR を書き、古い方の状態を「置き換え済み(<新しい番号>)」にする。
- 新しい ADR には、「対象: 」の次に「置き換える: <古い番号>」の行を足す。
- 古い ADR の決定の一部だけなら、「置き換える: <番号> の<決めたことの番号>」と書く。
- そのときは、古い方の状態を「採用」のまま残す。

### 目指す状態: 分からないことは、推測せずに利用者に聞いている

- 問いは、分からないこと1つに1つ作り、1行で答えられる形で、AskUserQuestion で聞いている。
- ネットで調べれば決まることは、調べて決め、出典を設計の節に書く。

### 目指す状態: ターンが終わるとき、次の子セッションが動ける

- 始めるとき、ステータスを「壁打ち中」にしている。壁打ちをしないタスクは「設計中」。
- 壁打ちから設計に進むとき、ステータスを「設計中」にしている。
- コミットし、最終メッセージに、設計済みであることと未決の問いを書く。
- 大きな変更(ADR を提案した変更・本番環境に触る変更・話題を分けた変更)は、QA に設計レビューを頼む。
- それ以外は、PG に実装を頼む。
- QA に設計レビューを頼むとき、ステータスを「設計レビュー中」にしている。
- 設計レビューの直しは、「レビュー」の節を読んで直し、QA に直しの確かめを頼む。(ADR 0085-7・0086-1)
- 実装レビューで出た設計の指摘は、直して、PG に作り直しを頼む。(ADR 0069-2)
- QA から残った指摘の知らせが来たら、どうするかを利用者に聞いている。(ADR 0085-7)
- 「設計への問い」が来たら、設計の節を直し、直した所を問いの下に書いて、PG に頼む。(ADR 0069-1)

## 目的: AI の費用対効果を最適化する

### 目指す状態: 役割の仕事ごとの難しさが、理由と一緒にチケットにある(ADR 0059-1)

- 難しさは、やることが仕様・設計・規則でどこまで決まっているかで決めている。
- 低は、書いてあるとおりにやれば済む仕事。
- 高は、自分で選ぶ所がある仕事。仕様・設計・規則に答えが無く、それらそのものを決める仕事も含む。(ADR 0070-1)
- SE の難しさは、いつも高。(ADR 0067-1)
- PG と QA の難しさは、設計を書き終えたときに決めている。
- QA の難しさは、設計レビューと実装レビューの高い方にしている。
- PG に、仕様・設計・規則そのものを決める所が残るなら、設計を足している。
- 「難しさ」の節に、`- <役割>: <難しさ>(<理由>)` の形で書いている。

### 目指す状態: 各役割は、仕事を始める前に、難しさに合うモデルと effort になっている(ADR 0059-1)

- 低は `claude-sonnet-5-5` の high。(ADR 0070-2)
- 高は `claude-opus-5-5` の high。(ADR 0070-1)

### 目指す状態: Opus で仕上がらない仕事は、Fable で進んでいる(ADR 0065-1)

- Fable は `claude-fable-5-2` の high。
- 次の3つがそろう仕事は、始める前に Fable と決めている。
- 1つ目は、仕様・設計・規則そのものを決める仕事か、その設計レビューであること。(ADR 0070-1)
- 2つ目は、利用者が中身を確かめられない分野の知識が要ること。
- 3つ目は、決定どうしがつながり、1つ変えるとほかが合わなくなること。
- タスクに分けても1つの会話に収まらないと見込める仕事も、Fable と決めている。(ADR 0085-8)
- 同じタスクで入れた決定を消すか、同じ決まりを3回変えたら、Fable と決めている。
- 入れた決定を消すとは、このタスクの ADR を、却下・廃止・置き換え済みにするか消すこと。(ADR 0067-2)
- 設計レビューの指摘に応えて提案を却下にしたものは、入れた決定に数えない。(ADR 0067-2)
- 同じ決まりを変えるとは、このタスクの ADR の決めたことを書き換えるか、置き換えること。(ADR 0067-2)
- コミットするたびに、このタスクの ADR の `git log -p` で、この2つに当たるかを確かめている。(ADR 0067-2)
- Fable と決めた役割は、「難しさ」の節の理由に、当たった場合を書いている。
- SE を Fable と決めたら、PL に知らせている。
- PG と QA を Fable と決めたら、頼む前に替えている。
