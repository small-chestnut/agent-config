原則がぶつかったときは、番号の小さい方を先にする。

# 原則1: 確定

## 目的: PG が設計を読むだけで実装でき、QA が要件を読むだけで確かめられる

### 目指す状態: 記録は、決まった形で1ファイルにある

- 記録ファイルは、PL が指したパスに作る。冒頭に「ステータス: 」の1行。
- 節は、ゴール / 受け入れ条件 / 設計 / 実装 / レビュー。
- ゴールの節に、範囲外を1行で書いている。
- 記録に書くのは決めたことだけ。迷いと捨てた案は書かない(ADR に残す決定は除く)。

### 目指す状態: コードの無いタスクは、手順を実行して結果を確かめている

- 設計の節には、実行する手順を操作ごとに書いている。
- 確認用のテストは作らない。受け入れ条件は、実行後に確かめて言い切れる文。

### 目指す状態: 利用者がする操作は、頼むときの説明の元が設計に書いてある

- 設計の手順には、操作ごとに、する人(PG か利用者)を書いている。
- 利用者がする操作には、何を・ゴールにどうつながるか・なぜ利用者の手でかを書いている。
- 同じ操作に、手順・失敗する条件・終わったら利用者が返すことを書いている。
- 元に戻せない操作には、そう書いている。

### 目指す状態: 画面が変わるときだけ、設計に図がある

- 図は、変更前と変更後の画面を並べたもの。
- 図は SVG か PNG で、記録と同じフォルダの `<記録のファイル名(拡張子なし)>/` に置く。

### 目指す状態: 受け入れ条件は、テスト名で言える

- 受け入れ条件は、用語集の言葉で、テスト名に使える文。

### 目指す状態: 作るテストは、設計のテスト一覧に、数と大きさまで決まっている(ADR 0005-1)

- 設計の節に「テスト一覧」の表を置き、テスト名・大きさ・受け入れ条件を並べている。
- 受け入れ条件1つに、テスト1つ以上。
- 業務の規則の分かれ目(分岐・計算)ごとに、小さいテストを1つ。
- 分かれ目の値の境目は、前後の値も確かめている(境界値分析)。
- バグは、再現するテストを1つ。
- 大きさは、確かめられる中で一番小さいもの。
- 中は、外部(DB・ネットワーク)とのつなぎ目を確かめるときだけ。
- 大は、利用者の主な使い方1本につき1つまで。
- 大きさごとの割合と、カバレッジの目標値は置かない。

### 目指す状態: テスト一覧に、要らないテストが無い(ADR 0005-1)

- 内部の作り(外から呼べない関数・呼ばれた回数)は確かめない。
- 言語・フレームワーク・外部ライブラリの動きは確かめない。
- 分岐の無いコード(値の受け渡しだけ・設定の値)は確かめない。
- 同じ規則を、別の大きさでもう一度確かめない。
- 文書だけ・設定だけの変更は、テストを作らず、確かめ方を一覧に書く。

### 目指す状態: 設計は、短く、置く場所と名前まで決まっている

- 読むのは、対象リポジトリの CLAUDE.md・`docs/概要.md`・そのモジュールの仕様とフォルダ。
- 設計の節には、置くファイルと名前(skill `module-layout`)・データだけを書いている。
- 新しい名前は用語集に、同じコミットで入れている。
- 画面やモジュールを足すときは、`docs/概要.md` の一覧にも足している。

### 目指す状態: 機能の今の動きは、モジュールの仕様1つにある(ADR 0010-1)

- 仕様は `docs/specs/<モジュール>.md`。モジュール1つに1ファイル。
- 機能の今の動きを知るのに、前のタスクの記録は読まない。
- 動きを変えるときは、設計のコミットで仕様を直している。
- 仕様の無いモジュールは、そのタスクで作っている。
- 作るときは、そのタスクで読んだコードの今の動きを書いている。
- 冒頭は `# <モジュール>`。節は、`## ADR` と、機能ごとの `## <機能の名前>`。
- 「ADR」の節には、番号と ADR の題を1行ずつ並べる。(ADR 0010-2)
- 仕様には外から見える動きだけを書き、クラス名・ライブラリ・手順は書かない。
- 機能の節の行は、業務の規則を用語集の言葉で書いた1文。
- 無くなった動きは、行を消す。前の形は git にある。
- SKILL.md など決まりの文書がモジュールの中身なら、その文書が仕様。
- 決まりの文書が仕様なら、番号は行と見出しに付け、「ADR」の節は作らない。(ADR 0010-2)
- 仕様で足した行・変えた行は、同じ文で受け入れ条件に入れている。

### 目指す状態: 設計で読む ADR は、書き換える所に付いた番号の ADR だけ(ADR 0006-1)

- 設計の最初に、書き換える行と、その見出しに付いた ADR の番号を集めている。
- コードを書き換えるときは、仕様の「ADR」の節の番号も集めている。(ADR 0010-2)
- 仕様が無ければ、そのモジュール・テスト・lint の設定を「ADR」で検索している。(ADR 0010-2)
- 書き換えるコードに効く所の番号も集め、作る仕様に並べている。(ADR 0010-2)
- 読むのは、その番号の ADR と、「置き換える: 」でたどった古い ADR だけ。(ADR 0006-2)
- ADR で決めた行には、末尾に「(ADR <番号>)」を付ける設計にしている。
- 見出しの下の行がみな同じ ADR なら、番号は見出しの末尾に付ける。
- ADR が2つ以上なら、「(ADR <番号>・<番号>)」と並べる。
- コードでは、決定を守らせる所か形にした所の1か所に付ける。
- その1か所は、lint の設定の message・アーキテクチャのテストの名前・型や API の定義のコメント。
- 名前に空白や「-」を使えなければ、`ADR_0006_1` の形にする。
- どれにも当たらない決定は、そのモジュールの CLAUDE.md の行に付ける。
- コードか CLAUDE.md に番号を付けたら、仕様の「ADR」の節にも並べる。(ADR 0010-2)
- 決定を置き換えたら、古い番号を新しい番号に付け替える設計にしている。

### 目指す状態: 後から変えにくい決定は、採用した ADR にある(ADR 0004-1・0007-1)

- 採用中の ADR とぶつかるなら、置き換える ADR を提案している。
- 構造・非機能の特性・依存・インターフェース・作り方の技法に効く決定は、ADR に書く(Nygard)。
- ADR は、設計の残りより先に、状態「提案」で書いている。
- 設計レビューで ADR に指摘が来たら、直して状態を「採用」か「却下」にしている。

### 目指す状態: ADR は、決まった形で1つのフォルダにある

- 置き場は `docs/adr/<ADR の番号>-<英語の短い題>.md`。(ADR 0004-1)
- ADR の番号は `<タスクの番号>-<そのタスクの中の連番>`(例: `0004-1`)。(ADR 0004-1)
- 冒頭は、題の見出しと、「状態: 」「日付: 」「対象: 」の3行。
- 節は、決めたこと / 捨てた案 / 理由。
- 1つの ADR には、決定を1つだけ書く。(ADR 0006-3)
- 決めたことは、どの決定かが分かる1行。詳しい文は skill などに任せる。(ADR 0006-3)
- 捨てた案と理由は、各1〜3行。
- 状態は、提案・採用・却下・廃止・置き換え済み(<ADR の番号>)。
- 対象は、直すモジュールの名前を「・」で並べるか、「全体」。
- 採用した ADR は、状態の行のほかは書き換えない。
- リポジトリに ADR の決まりか既にある ADR があれば、番号・置き場・形はそちらに合わせる。(ADR 0004-1)

### 目指す状態: 置き換えた古い ADR へ、新しい ADR からたどれる(ADR 0006-2)

- 決定を変えるときは、新しい ADR を書き、古い方の状態を「置き換え済み(<新しい番号>)」にする。
- 新しい ADR には、「対象: 」の次に「置き換える: <古い番号>」の行を足す。
- 古い ADR の決定の一部だけなら、「置き換える: <番号> の<決めたことの番号>」と書く。
- そのときは、古い方の状態を変えない。

### 目指す状態: 分からないことは、推測せずに利用者に聞いている

- 問いは、1行で答えられるものを3〜5個、AskUserQuestion で。
- ネットで調べれば決まることは、調べて決め、出典を設計の節に書く。

### 目指す状態: ターンが終わるとき、次の子セッションが動ける

- 始めるとき、ステータスを「設計中」にしている。
- コミットし、最終メッセージに、設計済みであることと未決の問いを書く。
- 大きな変更(ADR を提案した変更・本番環境に触る変更)は、QA に設計レビューを頼む。
- それ以外は、PG に実装を頼む。
- 頼むとき、ステータスを「設計レビュー中」か「実装中」にしている。
- 設計レビューの指摘で戻ってきたら、「レビュー」の節を読んで直し、PG に実装を頼む。
- コードは書かない。

### 目指す状態: 子セッションどうしの知らせは、記録だけを指している

- 送る文は、記録のパスと読む節と、頼むことだけ。自分の見立ては書かない。
- 送り先の id は PL から届く。ターンを終えた後に届いたら、そのターンで送る。
- 本番環境に触る作業は、PL に知らせてターンを止める。
