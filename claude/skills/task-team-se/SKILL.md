# 原則1: 確定

## 目的: PG が設計を読むだけで実装でき、QA が要件を読むだけで確かめられる

### 目指す状態: 記録は、決まった形で1か所にある

- 記録は、PL が指した置き場(ファイルのパスかチケット)に作る。冒頭に「状態: 」の1行。
- 節は、ゴール / 仕様 / 要件 / 設計 / レビュー(設計) / 実装 / レビュー(実装)。
- 記録に書くのは決めたことだけ。迷いと捨てた案は書かない(ADR に残す決定は除く)。

### 目指す状態: コードの無いタスクも、同じ節と順で回っている

- コードの無いタスクでは、実装を手順の実行と読み替えている。
- テストを確認手順と読み替え、手順を実行する前に書いている。
- 受け入れ条件を、確認して言い切れる文と読み替えている。
- 設計の節には、実行する手順を操作ごとに書いている。

### 目指す状態: 利用者がする操作は、頼むときの説明の元が設計に書いてある

- 設計の手順には、操作ごとに、する人(PG か利用者)を書いている。
- 利用者がする操作には、何を・ゴールにどうつながるか・なぜ利用者の手でかを書いている。
- 同じ操作に、手順・失敗する条件・終わったら利用者が返すことを書いている。
- 元に戻せない操作には、そう書いている。

### 目指す状態: 利用者が、仕様の節の図を見て、どんな機能が入りどう動くかを掴める

- 仕様の節には、入る機能ごとに次の3つをこの順に書いている。
  - 「### <機能の名前>」
  - 図の行
  - 決まりの箇条書き
- 図は、実装後に利用者が見る画面か、利用者がする操作の流れ。
- 画面を変えるときは、変更前と変更後を並べている。
- 図は SVG か PNG で、記録と同じフォルダの `<記録のファイル名(拡張子なし)>/` に置く。
- 図は `![<説明>](<記録のファイル名>/<図のファイル名>)` の1行で指している。
- 記録がファイルでないときは、図を置き場の決まりにある添付の仕方で付けている。
- 決まりの箇条書きは、図に振った番号で始めている。
- 仕様の節には、図の行のほかに、実際の名前を書いていない。
  - ファイル名・コマンド・関数名・ブランチ名・テストの件数。

### 目指す状態: 要件は、受け入れ条件がテスト名で言える

- 要件の節には、ゴール・範囲外・受け入れ条件がある。
- 受け入れ条件は、用語集の言葉で、テスト名に使える文。

### 目指す状態: 設計は、置く場所と名前まで決まっている

- 読むのは、対象リポジトリの CLAUDE.md・`docs/概要.md`・そのモジュール。
- 設計の節には、置くファイルと名前(skill `module-layout`)・データ・テスト一覧がある。
- 新しい名前は用語集に、同じコミットで入れている。
- 複数モジュールに及ぶ決定は ADR に、同じコミットで入れている。
- 画面やモジュールを足すときは、`docs/概要.md` の一覧にも足している。

### 目指す状態: 分からないことは、推測せずに利用者に聞いている

- 問いは、1行で答えられるものを3〜5個、AskUserQuestion で。
- ネットで調べれば決まることは、調べて決め、出典を設計の節に書く。

### 目指す状態: 番が終わるとき、次の役割が動ける

- 始めるとき「状態」を「設計中」に、終わるとき「設計レビュー中」にしている。
- コミットし、最終メッセージに、設計済みであることと未決の問いを書く。
- レビューの指摘で戻ってきたら、「レビュー(設計)」の節を読んで直し、同じ手順で終える。
- コードは書かない。
