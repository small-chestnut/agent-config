# 原則1: 人間側の最適化

## 目的: 利用者が、タスクの途中で、ずれに早く気づける

### 目指す状態: サブタスクは、利用者が把握できる単位と順で進んでいる

- サブタスクの済みは利用者に説明するので、サブタスクの単位を説明の単位に揃える形にしている。

## 目的: 利用者の理解が曖昧なまま、リポジトリの目的に逆効果なタスクが作られ始めない

### 目指す状態: 利用者は、SE の答えを聞いてから、設計に進めるかを決めている

- 命令の形の依頼にも、SE が私見を返す壁打ちを残している。
- 決まった動きに戻す依頼は、壁打ちなしで設計に入る道を残している。

### 目指す状態: 壁打ちは、その話題だけが入った会話で進んでいる

- PL の1つの会話に話題が混ざると、PL が説明を誤る。
- 壁打ちを PL がまとめて渡す受け渡しが無いので、要件と「なぜ」がずれない。

### 目指す状態: チケットに残る利用者の「なぜ」は、利用者の言葉ではなく、利用者が一番やりたいこと

### 目指す状態: 会話を持たない別の SE が、チケットだけで続きから進められる

- セッションの会話は、ほかの PC に移せない。
- 利用者は、PC が変わっても、チケットの要点から作業を続けたい。

# 原則2: AI 側の最適化

## 目的: AI の費用対効果を最適化する

### 目指す状態: モデルと effort は、仕事の難しさで決まっている

- 性能が難しさに足りないと仕事が仕上がらず、余ると使用量を損なう。
- ADR の有無・頼んだ人・レビューの種類は、難しさのざっくりした目安にしかならない。
- 難しさは、タスクごとでなく、役割の仕事ごとに違う。
- 難しさを決めるのは、仕事の中身を読む SE にしている。
- 割り当ては、Anthropic が測った費用と性能の数字から決めている。
- Fable は、3段の割り当てに入れていない。測定で費用に見合ったのは、長いコードの作業と大きな資料の作業だけ。
- Opus で仕上がらない仕事は、その場かぎりの対応が重なって破綻し、利用者が出力をつかめなくなる。
- そうなると見込める仕事と、その印が出た仕事にだけ、Fable を使う形にしている。
- Haiku は、割り当てに入れていない。合うのは、結果を確かめられる大量の作業。
- モデルは、会話の途中でなく、仕事を始める前に替える形にしている。
- SE を途中で Fable にするのは、キャッシュを失うより、破綻の方が高くつくから。
