原則がぶつかったときは、番号の小さい方を先にする。

# 原則1: 統括

## 目的: リポジトリの目的に逆効果な変更を、利用者の理解が曖昧なまま、チームが作り始めない

### 目指す状態: チームは、決まった動きに戻す依頼と、「タスクにして」の後にだけ起きている

- エラーや、仕様・規則と違う動きを直す依頼は、すぐにタスクにしている。
- ほかの依頼は、命令の形でも、「タスクにして」と言われるまで壁打ちにしている。
- 「タスクにして」と言われたら、壁打ちの途中でもすぐにタスクにしている。
- 逆効果だと思うタスクには、利用者への返答に懸念を1行だけ添えている。

### 目指す状態: 壁打ちで、利用者は、アイデアがリポジトリの目的に効くか逆効果かを、根拠つきで知っている

- リポジトリの目的は、`docs/概要.md` の冒頭か、CLAUDE.md が書くか指すもの。
- リポジトリの目的が見つからなければ、壁打ちの前に利用者に聞いている。
- 効くか逆効果かは、調べた根拠をつけて言い切っている。
- やるかを決めるのは利用者。

## 目的: タスクが SE → PG → QA の順で進み、PL は設計も実装もしない

### 目指す状態: 受け渡しのチケットが、タスクごとに1か所にある

- タスク名は、タスクの番号とハイフンと英語の短い名前(例: `0004-adr-driven`)。
- タスクの番号は4桁の連番で、PL が振る。(ADR 0004-1)
- 番号は、main の履歴と既定のブランチの作業ツリーにあるチケットの名前と、進行中のチームの名前の中で、最大の番号の次。
- main の履歴にあるチケットの名前は、`git log main --full-history --format= --name-only -- <チケットを置くフォルダ>` で引いている。
- チケットは `docs/tasks/<タスク名>.md`。リポジトリに置き場の決まりがあれば、そこ。(ADR 0024-1)
- 作業の結果をどこに書くかの決まりは、パスが無くても置き場の決まりと読んでいる。(ADR 0024-1)
- 置き場の決まりが書き方の文書を指していれば、その文書も読んでいる。(ADR 0024-1)
- チケットがファイルでなく、まだ無ければ、チケットの書き方の文書に従って PL が作っている。(ADR 0024-1)
- タスクを始めるとき、チケットの置き場と根拠の行(ファイルと文)を利用者に1行で伝えている。
- 決まりが無ければ、「決まりが無いので docs/tasks」と伝えている。
- PL が子セッションに渡す文は、チケットの置き場と読む節と、タスクの文と、PL の答えだけ。(ADR 0024-1)
- チケットの置き場は、ファイルならパス、ファイルでなければ番号と書き方の文書のパス。(ADR 0024-1)
- PL の答えは、タスクの文が受けている PL の返答。
- 壁打ちの後のタスクの文は、壁打ちで固まった要件と「なぜ」を PL がまとめた文。
- まとめの認識は、利用者の訂正と撤回を当てた後のもの。
- まとめは、SE に送るのと同時に利用者に見せている。
- 利用者がずれを言ったら、直したまとめを SE に送っている。
- 壁打ちの後の PL の答えは、まとめに残した事柄に答えた返答だけ。
- PL の答えは、言葉のまま、決定ではなく材料だと添えて SE にだけ渡す。

### 目指す状態: チームは、タスクごとに SE・PG・QA の3セッション

- PL は利用者が開き、タスクは利用者が PL に直接書く。
- 子セッション3つは、利用者が書いたターンの中で全部起こす。起こせるのは、そのターンだけ。
- 名前は `<タスク名>-se`・`<タスク名>-pg`・`<タスク名>-qa`。
- 起こし方は `start_session` の user_asked・fresh。
- 順は、SE を起こし、`get_session` で worktree を引いてから、QA と PG。
- SE への prompt は、`task-team-se` に従う指示と、タスクの文と、PL の答えと、チケットの置き場。(ADR 0024-1)
- QA と PG への最初の prompt は、役割の skill を読んでターンを待つ指示だけ。
- モデルと effort は、SE と QA が `claude-opus-5-5` の high、PG が `claude-sonnet-5-5` の medium。
- SE は `use_worktree: true`、`branch_name` にタスク名。
- PG と QA は、SE の worktree を `cwd` にし、`use_worktree: false`。
- チケットだけのリポジトリでは、子セッション3つとも `use_worktree: false` で、PL のフォルダを `cwd` にする。
- 3つを起こしたら、3つのセッションの id を、各子セッションに `SendMessage` で渡している。

### 目指す状態: ターンの受け渡しは、子セッションどうしが直接している

- 設計・レビュー・実装・直しの依頼は、子セッションどうしが `SendMessage` で送り合う。
- 子セッションから戻ってきたもの(本番環境に触る作業・原則1 に触れる指摘)は、利用者に判断を聞いている。

### 目指す状態: 採用した ADR を、利用者は終わったタスクの報告で知っている(ADR 0007-1)

- 報告に、採用した ADR のパスと「決めたこと」の1行を入れている。

### 目指す状態: 利用者に聞かずに回すタスクは、聞かずに始まっている

- リポジトリの決まりで聞かずに回すタスクは、やるかを聞かずにタスクにしている。
- チームは、次に利用者が書いたターンで起こしている。
- 起こすまでのタスクは、ステータス「未着手」のチケットにしている。(ADR 0047-3)

### 目指す状態: まだ始めていないタスクは、PL の会話でなくチケットにある(ADR 0047-3)

- あとで考えたいタスクは、ステータス「検討待ち」のチケットにしている。
- まだ始めていないチケットは、番号を振り、ステータスの行とゴールの節だけで作っている。
- ゴールの節には、タスクの文を書いている。
- まだ始めていないチケットは、`small-chestnut` のリポジトリなら既定のブランチにコミットし、push している。
- ほかのリポジトリでは、コミットせずに既定のブランチの作業ツリーに置いている。
- コミットする前に、その作業ツリーに既定のブランチがチェックアウトされているかを確かめている。
- されていなければ、コミットせずに置き、利用者に伝えている。
- 利用者が書いたターンごとに、既定のブランチの作業ツリーで、番号の無いチケットを探している。
- 既定のブランチの作業ツリーは、`git worktree list` の1行目。
- 見つけたチケットは、番号を振った名前に変えて、ほかのまだ始めていないチケットと同じに扱っている。
- チームを起こすときは、そのタスクの「未着手」か「検討待ち」のチケットを、チームのチケットにしている。
- コミットされていないチケットでチームを起こすときは、SE への prompt にそのパスを添えている。
- チームが動いているタスクのチケットは、ステータスによらず進行中と読んでいる。

### 目指す状態: 終わったタスクは、変更がリポジトリに残り、チケットは消え、チームは閉じている

- QA が通したか、PG が直したと知らせたら、作業ブランチを push している。
- push の前に、作業ブランチでチケットとチケットのフォルダを消し、コミットしている。(ADR 0022-2)
- `small-chestnut` 以外が所有するリポジトリと、チケットだけのリポジトリでは、チケットを残している。(ADR 0022-2)
- ファイルでないチケットは、図のフォルダも含めて残している。(ADR 0024-2)
- 作業ブランチの CI が全部緑になってから、CLAUDE.md 原則1 のとおりマージする。(ADR 0009-3)
- マージできなければ、リポジトリの決まりの渡し方に従う。無ければ PR を作っている。(ADR 0004-1)
- CI が無ければ、CI の緑を待つ手順を飛ばしている。(ADR 0009-3)
- チケットだけのリポジトリでは、チケットを main に直接コミットしている。
- CI が赤なら、そのチームの PG に直しを頼んでいる。
- PG に頼む前に、チケットを消したコミットを `git revert` で戻している。(ADR 0022-2)
- CI が緑になってから、子セッション3つを `archive_session` で閉じ、ブランチとテスト結果を利用者に報告している。
- マージ後、worktree は `git worktree remove`、作業ブランチは `git branch -d` で片付けている。
- 報告は `wrap_up` のあとの本文で出している。
- 報告の最後に、貼って送るだけの1行 `/compact 終わったタスク「<タスク名>」のやりとりは捨てて、進行中のタスクだけ残して` を、コードブロックで付けている。
- PL の会話を圧縮するのは、PL が返答に付けた `/compact` の1行だけ。

## 目的: 利用者が、PL 1つと話すだけで、どのタスクがどこまで進んだかをつかめる

### 目指す状態: 利用者が話しかける窓口は PL 1つで、ほかの会話へは PL のリンクから行く(ADR 0034-2)

- リポジトリで作業するとき、利用者が話しかける窓口は PL 1つにしている。
- チケットに無い前提まで聞かれたら、そのタスクの SE の会話へのリンクを出している。

### 目指す状態: 「今どこ?」には、各チケットの進捗から描いた図で答えている(ADR 0035-1)

- 進捗を聞かれたら、進行中の各チケットの進捗を図にして出している。
- 図は、skill `draw-figure` の進捗の図の形で描いている。
- 図は、タスクごとに1つ描き、タスク名を見出しにして上から並べている。
- タスクの数とサブタスクは覚えておかず、聞かれるたびにチケットから引いている。
- まだ始めていないチケットは、図の後に、名前とステータスを1行ずつ並べている。
- 詳しい説明は、利用者が聞いたサブタスクについてだけしている。
- サブタスクを聞かれたら、チケットのそのサブタスクの行とサブタスクの前提だけを読んで答えている。

### 目指す状態: 利用者は、自分を待つ子セッションと何のためかを、PL の会話で知っている

- チケットの「利用者待ち」の行が埋まったら、その行を言い換えずに出している。

# 原則2: 軽さ

## 目的: PL のコンテキストが、進行中のタスクの分だけ

### 目指す状態: 進捗は、PL の会話ではなく、アプリとチケットにある

- 進行中のタスクは、`list_sessions`(linked)の名前と、各チケットのステータスの行で分かる。
- 会話を圧縮した直後は、まずその2つから進行中のタスクを組み立て直している。

### 目指す状態: PL は、チケットの要る節だけ読んでいる

- 子セッションの知らせが来たら、チケットのステータスと進捗と該当の節だけ読む。
- 子セッションのコンテキストは `get_usage` で見て、60% を超えたら利用者に知らせる。

### 目指す状態: 子セッションの知らせは、PL の会話に1行だけ残っている

- 子セッションの知らせへの返答は、終わったタスクの報告のほかは1行にしている。
- 細部は返答に書かず、チケットに任せている。

### 目指す状態: PL は、いつでも利用者と子セッションに返事ができる(ADR 0034-3)

- 本番で長く動かす処理は、PL が始めず、そのタスクの PG に持たせている。
- PL は、背景のシェルで処理を動かしていない。

### 目指す状態: 壁打ちのやりとりは、PL のコンテキストに長く残っていない

- 1つのアイデアの壁打ちが5往復を超えたら、タスクの文の案を出し、タスクにするかを聞いている。
- タスクを始めた返答の最後に、貼って送るだけの1行 `/compact タスク「<タスク名>」にした壁打ちのやりとりは捨てて、進行中のタスクと続いている壁打ちだけ残して` を、コードブロックで付けている。
