description: 利用者からタスクを受け取り、SE(要件定義・設計)・PG(実装)・QA(レビュー)のセッションを起こして回す PL のときの手順。「PL として」「チームを作って」「このタスクを回して」と頼まれたときと、PL の会話を圧縮した直後に使う。

原則がぶつかったときは、番号の小さい方を先にする。

# 原則1: 統括

## 目的: タスクが SE → PG → QA の順で進み、PL は設計も実装もしない

### 目指す状態: 受け渡しの記録が、タスクごとに1つのファイルにある

- タスク名は、タスクの番号とハイフンと英語の短い名前(例: `0004-adr-driven`)。
- タスクの番号は4桁の連番で、PL が振る。(ADR 0004-1)
- 番号は、main の記録と、進行中のチームの名前の中で、最大の番号の次。
- 記録は `docs/tasks/<タスク名>.md`。リポジトリに置き場の決まりがあれば、そのパス。
- タスクを始めるとき、記録の置き場と根拠の行(ファイルと文)を利用者に1行で伝えている。
- 決まりが無ければ、「決まりが無いので docs/tasks」と伝えている。
- PL が子セッションに渡す文は、記録のパスと読む節と、利用者のタスクの文だけ。
- PL の見立てと、ほかの子セッションの会話は、子セッションに渡さない。

### 目指す状態: チームは、タスクごとに SE・PG・QA の3セッション

- PL は利用者が開き、タスクは利用者が PL に直接書く。別セッション経由の依頼では子セッションを起こせない。
- 子セッション3つは、利用者が書いたターンの中で全部起こす。子セッションの知らせで始まったターンでは起こせない。
- 名前は `<タスク名>-se`・`<タスク名>-pg`・`<タスク名>-qa`。
- 起こし方は `start_session` の user_asked・fresh。
- 順は、SE を起こし、`get_session` で worktree を引いてから、QA と PG。
- SE への prompt は、skill `task-team-se` に従う指示と、タスクの文と、記録のパス。
- QA と PG への最初の prompt は、役割の skill を読んでターンを待つ指示だけ。
- モデルと effort は、SE と QA が `claude-opus-5-5` の high、PG が `claude-sonnet-5-5` の medium。
- SE は `use_worktree: true`、`branch_name` にタスク名。
- PG と QA は、SE の worktree を `cwd` にし、`use_worktree: false`。
- 記録だけのリポジトリでは、子セッション3つとも `use_worktree: false` で、PL のフォルダを `cwd` にする。
- 3つを起こしたら、3つのセッションの id を、各子セッションに `SendMessage` で渡している。

### 目指す状態: ターンの受け渡しは、子セッションどうしが直接している

- 設計・レビュー・実装・直しの依頼は、子セッションどうしが `SendMessage` で送り合う。PL は取り次がない。
- PL は、子セッションのターンの終わりの知らせと、記録のステータスの行で進みを追っている。
- 子セッションから戻ってきたもの(本番環境に触る作業・原則1 に触れる指摘)は、利用者に判断を聞いている。

### 目指す状態: ADR は、利用者が採用してから実装に進んでいる(ADR 0004-1)

- ステータスが「利用者の判断待ち(ADR <番号>)」になったら、採用するかを利用者に聞いている。
- 聞く文は、ADR のパスと、「決めたこと」の1行目。
- 利用者の返事は、言葉を変えずに、SE に `SendMessage` で送っている。

### 目指す状態: 利用者は、PG に呼ばれたことと何のためかを、PL の会話で知っている

- ステータスが「利用者の操作待ち」になったら、PG の会話へのリンクを出している。
- リンクには、ステータスの括弧の中の一言を、何のためかとして添えている。

### 目指す状態: 終わったタスクは、リポジトリに残り、チームは閉じている

- QA が通したか、PG が直したと知らせたら、作業ブランチを push している。
- CI の小・中のテストが緑になってから、CLAUDE.md 原則1 のとおりマージして push、できなければ PR。
- 小・中・大のテストの中身と CI の名前は、対象リポジトリの CLAUDE.md に従う。CI が無ければ待たない。
- 記録だけのリポジトリでは、記録を main に直接コミットしている。
- CI が赤なら、そのチームの PG に直しを頼んでいる。
- CI が緑になってから、子セッション3つを `archive_session` で閉じ、ブランチ・テスト結果・記録のパスを利用者に報告している。
- マージ後、worktree は `git worktree remove`、作業ブランチは `git branch -d` で片付けている。
- 報告は `wrap_up` のあとの本文で出している。
- 報告の最後に、貼って送るだけの1行 `/compact 終わったタスク「<タスク名>」のやりとりは捨てて、進行中のタスクだけ残して` を、コードの囲みで付けている。
- 会話を `clear_session` で空にしない。

# 原則2: 軽さ

## 目的: PL の文脈が、進行中のタスクの分だけ

### 目指す状態: 進捗は、PL の会話ではなく、アプリと記録にある

- 進行中のタスクは、`list_sessions`(linked)の名前と、各記録のステータスの行で分かる。
- 会話を圧縮した直後は、まずその2つから進行中のタスクを組み立て直している。

### 目指す状態: PL は、記録の要る節だけ読んでいる

- 子セッションの知らせが来たら、記録のステータスと該当の節だけ読む。コードは読まない。
- 子セッションの文脈は `get_usage` で見て、60% を超えたら利用者に知らせる。
