原則がぶつかったときは、番号の小さい方を先にする。

# 原則1: 見通し

## 目的: 利用者が、チームの動きを見て、口を挟み、止められる

### 目指す状態: 役割は、利用者が開いて話しかけられるセッションで回っている

- チームはタスクごとに閉じ、サイドバーには PL と進行中のチームだけが残る。

### 目指す状態: PL がチケットの置き場を読み違えても、利用者が作業の前に気づける

- タスクを始めるとき、置き場と根拠の行を利用者に伝える手順を残している。

### 目指す状態: 話題がいくつ重なっても、PL の説明が、ほかの話題と混ざって誤らない

- 1つの会話に話題が混ざって長くなると、AI の答えは当てにならなくなる。
- 利用者は、PL が説明を誤るのを、話題が混ざったせいだと見た。
- PL が持つのは、話題がどのタスクに当たるかまでにしている。
- タスクの中身の話は、その話題だけが入った SE の会話に出している。

### 目指す状態: 複数のタスクが混ざっても、利用者は PL 1つと話して、各タスクの進捗をつかめる

- 進捗は、PL の文でもリストでもなく、決まった形のかんばんで見せる形にしている。
- かんばんのページは1つに固定し、PL が書き換えるのはカードのデータだけにしている。
- 利用者は、ほかの PC で進めているタスクも、同じかんばんで見たい。
- PL は細部を会話で覚えず、聞かれたらチケットから引く形にしている。
- 本番で長く動かす処理は、PL の会話の外に出す形にしている。

### 目指す状態: 利用者は、まだ始めていないタスクを、AI の会話の状態によらず確かめられる

- 利用者は、自分がやりたいことを、AI の会話の状態によらず確かめたい。
- バックログを PL の返答の文に置くと、会話の圧縮の要約に頼って残すことになる。
- Jira や GitHub Issues でも、バックログはまだ始めていないチケットの集まり。
- 既定のブランチに置くのは、どの PC の PL からも見えるようにするため。

### 目指す状態: 利用者は、PC が変わっても、進行中のタスクを続けられる

- セッションの会話は、その PC にしか無い。
- 続きに要ることは、チケットに書いて GitHub に上げておく形にしている。

# 原則2: 自走

## 目的: AI だけで、タスクが最後まで進む

### 目指す状態: リポジトリの決まりで聞かずに回すタスクは、やるかを聞かれずに始まっている

### 目指す状態: PL の依頼の出し忘れで、チームが止まらない

- 受け渡しは、子セッションどうしが直接する形にしている。

### 目指す状態: 子セッションを起こす手順が、試運転で確かめたアプリの制約に沿っている

- 子を起こすのは、利用者が書いたターンだけ。
- 子の知らせで始まったターンでは子を起こさず、`SendMessage` だけを使う。

# 原則3: 軽さ

## 目的: 使用量と PL のコンテキストが、要る分だけで済む

### 目指す状態: 各セッションのモデルは、役割に要る分だけ

- PL は進捗管理だけで、Opus 級のモデルで足りる。
- 子は起こした側のモデル以下しか選べず、PL のモデルが上限になる。
- Fable が要る設計は、利用者が SE のモデルを手で上げる。

### 目指す状態: 終わったタスクは、履歴を画面に残したまま、PL のコンテキストから消えている

- PL の会話は、空にせず圧縮している。
- 圧縮は Claude から起こせないので、利用者が送る1行を報告に付けている。
- 子は、タスク1つごとに起こし、終えている。
