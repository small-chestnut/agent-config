# 原則1: AI 側の最適化

## 目的: AI だけでタスクを最後まで進め、利用者に実装を届ける

### 目指す状態: SE が作った本質的におかしな設計は、利用者より先に、設計レビューで止まっている

- 利用者は、SE が作った本質的におかしな設計を、自分で見張らずに止めてほしい。
- 求めるのは必要十分なレビューで、SE と QA が何往復もすると、レビューの意味が無くなる。
- code-review は、設計の文の食い違いとテストの抜けは拾うが、ゴールと既にあるものには照らさない。
- 見る所は、レビューを通ってしまった本質的な誤りの型に絞り、1回で終える形にしている。

### 目指す状態: 実装は、利用者が合意した設計と照らされている

- 利用者は、SE のやり方に納得した後で、PG の解釈のずれで誤った実装が通るのを怖れている。
- code-review は差分の中の誤りを探し、設計とのずれは探さない。
- プロンプトが中身のリポジトリでは、仕様は PG が書いた文書なので、照らす相手は設計の節だけ。
- 照らすのは合意した時点の設計の節で、PG が書き換えた後の節ではない。
- 問いへの SE の直しは問いの下に書かせ、合意の後に入った正しい直しと見分けている。
- 二通りに読める所は、どちらが合意した中身かを知る SE に返している。
- 実装レビューの設計の指摘は、SE と PG が直し、もう一度は見ない。往復を増やさないため。

### 目指す状態: QA のレビューは、1回で終わる

- レビューは、公式の code-review と、設計レビューの3つの見る所と、実装と設計の照らし合わせだけでしている。

## 目的: AI の費用対効果を最適化する

### 目指す状態: Opus で仕上がらない仕事は、Fable で進んでいる

- SE が気づかなくても、別のセッションの QA が印を確かめ、PL に届く形にしている。
- 印が出る ADR は大きな変更にだけあり、大きな変更には設計レビューがある。
