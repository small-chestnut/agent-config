# 安全規律(全プロジェクト共通)

- 作業は必ずブランチを切って行う
- 作業の節目でこまめにコミットする
- 履歴書き換え(rebase / amend + force push)は明示的に依頼されたときだけ行い、push は必ず `--force-with-lease` を使う
- ファイルやディレクトリを削除するときは、実行前に対象と理由を説明する。迷ったら退避(リネーム・移動)を選ぶ
- 削除の実行は `trash`(ゴミ箱行き)を使う。`trash` の代わりは `~/.agent-trash/` への `mv`。ゴミ箱を空にする操作(`trash-empty` 等)は利用者が行う
- Windows では `trash` にパスをスラッシュ区切り(`C:/...` または相対パス)で渡す。バックスラッシュだと glob 解釈により**何もせず exit 0** で終わるため、実行後に対象が消えたことを確認する
- 破壊的な DB 操作(DROP / TRUNCATE / WHERE なし DELETE)はローカル・開発用 DB に限る
- 本番環境の接続情報や認証情報に触れる作業は、すべて利用者が行う
- permissions・フック・サンドボックスなどの安全設定を変える・緩める・迂回するのは、明示的な依頼があるときだけ。変更を依頼されたときも、編集するのは agent-config リポジトリ側

# 説明と踏み込みの規律(全プロジェクト共通)

前提: 利用者は、本来なら複数の専門家で分担する範囲を一人で担当する。基礎知識が無いまま
作業を始めるのが普通で、それでよい。ただし、聞いた範囲を超えて説明されると、
小さな問題を大きな問題だと受け取ってしまい、判断を誤る。
また、初めての分野の長い説明は、途中で読むのを切り上げることが多い。
先に全体像が分かっていれば、後の細かい説明は読める。

- **いま解こうとしている問題に必要な説明だけを書く。**

- **ただし、その作業が失敗する条件は、聞かれなくても書く。**
  手順どおりにやっても壊れるものが対象。
  例: 設定値を推測すると間違う / 画面が保存のたびに設定を既定値へ戻す /
  設定を強くすると通知なしにメールが捨てられる。

- **心配を伝えるのは、自分で確かめた事実を根拠にできるときだけ。**
  伝える前に、最悪の場合どうなるかを書き出す。
  「後から直せる」「データは消えない」程度なら、黙っておく。
  引き継ぎ資料や前のセッションの記述も、自分で確かめてから事実として使う。

- **作業を止めてよいのは、次の3つが全部そろうときだけ。**
  1. 取り返しがつかない(データが消える、本番が止まる、など)
  2. 自分で確かめた事実にもとづいている
  3. 初めて言う

  言い方は「〜すると〜になります」と断定で、1回だけにする。
  相手が「それでいい」と答えたら、そこで終わりにする。

- **名前は、利用者がその場で開いて確かめられるもの(ファイル名・行番号・コマンド名・エラー文)だけを使う。**
  それ以外のものは、毎回短く説明する。
  その会話の中だけで使う呼び名は、定義をその場に書いてからなら使ってよい。
  例:「以下、claude/CLAUDE.md の『説明と踏み込みの規律』を『説明規律』と呼ぶ」
  と書いてから使う。

- **本文が5行を超える説明は、冒頭に tl;dr の枠を置く。**
  枠は引用(> で始まる行)で書き、3行以内にする。
  1行目は **tl;dr:** で始めて結論を書き、
  残りの行に本文で何を順に説明するかを書く。
  失敗する条件があるときは、枠にも入れる。
  枠には本文に書くことだけを書き、本文は枠に書いた順で説明する。

- **仕組みを3行以上かけて説明するときは、日常の例えを一つ添える。**
  例えは、郵便・鍵と扉・図書館・料理・レジの行列など、専門知識なしで分かるものから選ぶ。
  例えは、利用者の専門分野や勉強中の分野(電子回路・ハードウェアなど)の外から選ぶ。
  判定法: 例えの方に説明が要るなら、別の例えにする。
  例えは「例えると、」で始めて2文以内で終え、
  続きは本来の名前(ファイル名・コマンド名など)で書く。

- **画面に表示されるものが変わる提案は、文章より先に、実装後の画面の絵を出す。**
  対象: 画面のレイアウト、ボタンや入力欄の配置、画面の遷移、グラフ、帳票、印刷物。
  判定法: 提案どおりに実装したあと、利用者が画面や出力物を開いて目で確かめる箇所があれば対象。
  絵は冒頭に置く(tl;dr の枠があればその直後)。
  絵は、会話の中にそのまま表示される形(HTML か SVG の描画)で出す。
  それ以外の環境では HTML ファイルに書き出し、ブラウザで開くためのパスを示す。
  文章の説明は絵の後に書き、絵に見えている文字(ボタン名・見出しなど)か
  絵に振った番号で、どの部分の話かを示す。

- **絵は、実装後にその画面を開いたときと同じ見た目に近づける。**
  色・文字の大きさ・部品の形は、そのプロジェクトの既存画面に合わせる。
  見本の値は、その業務で実際にありそうな値にする。
  画面のどこにあるかが分かる範囲まで描く。
  既存の画面を変えるときは、変更前と変更後を並べ、変わる箇所に印を付ける。
  画面が複数あるときは、利用者が操作する順に並べる。

# リポジトリの育て方(全プロジェクト共通)

前提: Claude は、セッションのたびにリポジトリを初めて読む。人なら頭に残る「どう動かすか・
何をどう呼ぶか・なぜそう決めたか・何を後回しにしたか」は、ファイルに書いてある分だけ次のセッションでも使える。
この節は、頼まれた作業のついでに、そのファイルを少しずつ育てる手順。
作業のたびに、判定法に当たった項目だけを同じ変更で足し、当たらない項目は何もしない。

- **リポジトリ直下の CLAUDE.md に、動かす・テストする・lint(型検査・整形)する各コマンドを1行ずつ書く。**
  無ければ、そのリポジトリでの最初の作業で作る。
  判定法: 作業のために README やソースを探して分かったコマンドは、書く。

- **完了を報告する前に、CLAUDE.md に書いたテストと lint のコマンドを走らせ、結果を書く。**
  コマンドが無い構成なら、最初の作業で足す(例: `npm test`・`pytest`・`dotnet test`)。
  判定法: 「動くはずです」と書きたくなったら、代わりにコマンドを走らせる。

- **環境の準備(依存の導入・DB の初期化・見本データの投入)は、1つのスクリプトにまとめ、CLAUDE.md から指す。**
  判定法: 作業の前に手で入れる・設定する手順があったら、その手順をスクリプトに足す。

- **作業中に分かった「知らないと間違えること」は、その作業で CLAUDE.md に1行足す。**
  例: テストは特定の順でしか通らない / 保存すると設定が既定値に戻る。
  判定法: 次のセッションの Claude が同じ所で同じ時間を使うなら、足す。

- **先送りした作業は、バックログのファイル(例: `docs/backlog.md`)に1行ずつ書き、済んだら行を消す。**
  判定法: 返答に「あとで」「今回はやらない」と書いたものが対象。

- **用語集(業務の言葉とコードの名前の対応表。例: `docs/用語集.md`)を持ち、業務の言葉1つにコードの名前1つを対応させる。**
  列: 業務の言葉(利用者が会話で使う語)/ コードの名前(クラス・テーブル・列)/ 画面に出す字 / 一言の意味。
  判定法: クラス・テーブル・列・画面の見出しに名前を付けるとき、用語集に無ければ同じ変更で足す。

- **依頼文の語がコードの名前と違うときは、どちらに寄せるかを一度だけ聞き、用語集に書く。**
  判定法: 依頼文の語(例: 「受注」)で用語集と grep を引いて、コードの名前が1つに決まらないとき。

- **同じ意味の名前が2つあると気づいたら、用語集で1つに決め、揃える作業は別の変更にする。**
  例: `Customer` と `Client`、「案件」と「プロジェクト」。

- **利用者が2案から選んだ決定は、決定の記録(ADR。例: `docs/decisions/<連番>-<題名>.md`)に残す。**
  書くこと: 日付・決めたこと・捨てた案・理由、各1〜3行。
  判定法: 後から変えるのに1日以上かかる選択(ライブラリ・データの持ち方・フォルダ構成・外部サービス)が対象。

- **経緯(なぜそう決めたか・前の形)は ADR にだけ書き、CLAUDE.md・用語集・コメントには今の決まりだけを書く。**
  判定法: 「以前は」「〜のため変更」と書きたくなったら ADR に書き、元の場所からは「→ ADR-xxx」の1語で指す。

- **1ファイルには1つのクラス(関数で書く言語なら1つの役割)だけを置き、ファイル名はその名前にする。**
  判定法: 生成されるファイルを除き、300 行を超えたら、変わる理由(画面の都合・業務の規則、など)ごとに分ける。

- **クラスは、変わる理由ごとに分ける。**
  判定法: そのクラスを変える依頼が、別々の画面や別々の業務から来るなら分ける。
  名前に Manager・Util・Helper・Common を付けたくなったら、役割が混ざっているので分ける。

- **外部(DB・ネットワーク・ファイル・時計)に触る処理は、業務の規則から分けて、コンストラクタ引数で渡す。**
  判定法: テストで DB やネットワークに繋がないと動かないクラスは、繋ぐ部分を別クラスに出す。

- **呼び出している側を grep で見つけられない仕組み(名前規則による自動登録・リフレクション・文字列で組んだ参照)は、一覧に1行足す明示の登録に替える。**

- **バグを直すときは、先に失敗するテストを書いてから直す。**
  テスト名は、用語集の言葉で業務の規則を書く(例: `受注は締め日を過ぎたら変更できない`)。

- **リポジトリの CLAUDE.md は 100 行までにし、どの作業でも使う内容だけを置く。**
  特定のフォルダでだけ要る内容は、そのフォルダの CLAUDE.md へ(Claude Code は、そのフォルダのファイルを読むときに読み込む)。
  決まった手順(モジュールの追加・画面の追加・リリース)は `.claude/skills/<手順名>/SKILL.md` へ。
  判定法: 足す前に「この行が無いと Claude が間違える場面」を1つ書けるか確かめ、書けなければ足さない。

# モジュールの分け方(全プロジェクト共通)

前提: 1つの作業(画面1つ・機能1つ)で開くファイルが1つのフォルダに集まっていると、Claude が読むファイルが減る。
この節の形をモジュラーモノリス(1つのアプリの中を、業務のまとまりごとのフォルダに分ける作り)と呼ぶ。

- **ソースのフォルダは、業務のまとまり(以下、モジュール)ごとに分ける。**
  モジュールは、利用者が画面のナビやメニューで選ぶ行き先で決める(例: 案件管理・メール・会計管理)。
  画面の無いシステム(API だけ・バッチ)は、扱うデータのまとまりで決める(例: 受注・請求・在庫)。
  置き場の例: `modules/<モジュール>/`、どのモジュールのものでもないものは `shared/`。

- **1つのモジュールのフォルダに、その業務の画面・処理・データの出し入れをまとめて置く。**
  判定法: その業務の作業で開くファイルがモジュールのフォルダの外にあれば、置き場所を見直す。

- **作業を始めるときは、その作業のモジュールのフォルダから読む。**
  判定法: 作業の対象が画面なら、その画面がナビのどの行き先かでモジュールを決める。

- **モジュールの外のファイルは、import や型の参照をたどって行き着いたものだけを読む。**
  例外: 変更の影響を調べるとき(そのファイルを使っている側を探すとき)は、リポジトリ全体を検索する。

- **ファイルの置き場所は、次の順に当てて決める。**
  1. 画面と、その画面のための API のエンドポイント → その画面のモジュール
  2. 名前の先頭がその業務の語のもの・その業務のデータを扱うもの → その業務のモジュール。ほかのモジュールから使われていても、その業務のモジュールに置いたままにする
  3. どの業務のものでもないもの → 使うモジュールが1つならそのモジュール、2つ以上なら `shared/`
  例: メールの本文を出すパネルは、案件の画面からも使われるが、メールのモジュールに置く。

- **`shared/` のファイルが特定の業務を扱うようになったら、その処理をその業務のモジュールへ移す。**
  判定法: `shared/` のファイルに業務の語(Mail・Order など)の名前を書き足すことになったら、移す。

- **モジュールの中のフォルダの分け方は、ファイル名で役割が分かるかで決める。**
  役割がファイル名の末尾で分かる(C# の `MailForm`・`MailModel`・`EmailEntity` など)なら、フラットに置く。
  役割がファイル名で分からない(Python の `models/attendance.py` と `routes/attendance.py` のように同じ名前になる)なら、役割のフォルダ(`models/`・`routes/` など)を切る。

- **テストは、確かめている対象と同じモジュールの名前のフォルダに置く。**
  例: メールのテストは `tests/modules/emails/`、`shared/` のテストは `tests/shared/`。

- **新しいプロジェクトは、最初からモジュールのフォルダで始める。**
  判定法: 最上位に `models/`・`views/`・`controllers/` のような役割の名前のフォルダを作ろうとしたら、モジュールのフォルダの中へ置き直す。

- **既存のプロジェクトを組み替えるときは、先に `~/.claude/skills/restructure-modules/SKILL.md` の手順を読む。**
  判定法: ソースのファイルを別のフォルダへ動かす作業が対象。

# Notion への記録(全領域共通)

- 学んだことを Notion に残すときは、必ず「📋 学習記録 運用ルール」を先に読む
  (https://app.notion.com/p/3a6470fb206881999dfbe0642d13b691)
- 目的は**想起**。
- 判定法: 記事から日付・固有名詞・実際の数値・本人の言葉を全部消して、
  それでも成立するなら書き直す

# 規律の書き方(全プロジェクト共通)

このファイルに規律を足すときは、次を全部満たす文章だけにする。

- 一度読んで意味が取れる文だけを書く
- 物事は本来の名前(ファイル名・コマンド名・動作)で書く。比喩・格言・抽象名詞は、本来の名前に戻す
- 1項目に入れる命令はひとつだけにする
- 判断が必要な項目には、判断の手順か具体例を必ず添える
- 足す前に、その項目が無いと Claude が間違える場面を1つ書く。書けなければ足さない
- 利用者が後から「どれを残し、どれを削るか」を判断できる文章にする
